**Date:** 2026-06-10 · **Against:** branch `analysis/cluster-topology-audit` (= rc1 `dd5a2187f` + audit/spec commits)
**Method:** 4 survey agents (spec inventory ×44, subsystem×design matrix, cross-cutting production readiness, application-surface/foundation/toolchain/examples gap-fill), synthesized. Companion to the 2026-06-10 topology audits and worker-membership spec.

## Scope baseline

~70 Maven modules, >300k LOC Java: core 26.9k · consensus 12.7k · deployment 15.1k · slice+api 15.5k · CLI 18.3k · streams 9.5k · invoke 8.1k · metrics 8.1k · net 8.8k · config 8.5k · db 18.3k · pg-tools ~113k · JBCT ~59k (parser 34.8k) · forge 6.9k · plus resources, examples, environments, dashboard, TTM. Design surface: 44 specs, 16 RFCs, 14 architecture chapters, 13 slice-developer docs (6.8k lines), 8 operator docs, 6 runbooks.

## Verdict

Design completeness is **strongly layered, not uniform** — and the variance follows a clear law: **specs in this repo follow incidents, not construction.** The most turbulent area (membership/topology) accumulated six overlapping specs and now has the best design discipline in the repo (ratified keystone + waves + disposition table). The most stable code (core, statemachine, slice-processor) has the least formal design — its semantics are implicit, which is exactly what the membership saga proved dangerous. Spec status of 44: ~24 landed, ~7 designed-only ("approved-and-ready" with zero code), ~5 superseded, ~13 with rotten status headers (9 stale-pessimistic: shipped but marked Draft/Planned; 4 stale-optimistic: Ready but unimplemented).

## The five meta-patterns

1. **Specs follow incidents.** Design effort concentrates where churn hurt (membership: 6 specs; streams: 6 specs), leaving stable foundations spec-less. Rational short-term; the membership saga (3 mis-diagnoses against implicit semantics) is the documented cost.
2. **Header rot in both directions, no lifecycle.** Cloud providers say "Planned" for shipped code; declarative-http-client/fluid-migration/interactive-scaffolding say "Approved — ready" with zero code for ~8 weeks; only the membership lineage marks supersession. The repo has release-check tooling that could lint spec headers — nothing enforces them today.
3. **Debt concentrates in seams, not subsystems.** Every audit this week found *severed wires* (worker actuation, spokesman ignition, transport↔SWIM feedback, examples↔CI, docs↔code) rather than missing designs. Seam ownership is the systematic weak point.
4. **Verification is the least complete design artifact relative to ambition.** A 10K-node-ambition runtime verified almost entirely by 16 Docker suites: no DST harness, Ember dormant (6 files), the highest-leverage codegen thinly tested, ONNX untested. The overhaul's transition-journal + deterministic-FSM-simulation direction is the right corrective — currently designed, unbuilt.
5. **Breadth itself is a risk dimension.** Seven "approved" specs with no code are open commitments; half-wired subsystems (worker tier, AHSE, Tier-2) read as features but don't function. The GA bar needs an explicit in/out decision per dormant commitment.

## Top 10 gaps, ranked by risk

1. **Stream data is volatile — and the missing piece is one wire, not an engine.** The AHSE engine is real (57 classes: tiers, content addressing, single-flight, write-behind, GC, snapshots, AES-GCM/LZ4/Zstd) and live for artifacts; but the stream seal path has **no production writer** (`SegmentSealer`/`StorageSegmentSink` constructed only in tests), the DHT tier is RAM-backed (`MemoryStorageEngine`), GC/demotion is wired as `noOp()`, `RemoteTier` (S3 — the only durable tier) has no construction path, and #99's slice ContentStore resource regressed (provisioning requires a `StorageInstance` extension nobody registers) despite the ticket being closed. Suite 14 green-stickers all of this (warn+pass on absent functionality). Full-cluster restart = total stream loss; survival rests on replication only. **Ticketed 2026-06-10, all rc1: #248 (seal-path wiring), #249 (durable tier path), #250 (GC/demotion noOp), #251 (#99 regression), #252 (metadata vs spec §7.4), #253 (encryption key management), #254 (suite-14 hardening).** Note: KV/Rabia in-memory is *not* part of this gap — deliberate design (see strengths).
2. **Topology/membership lifecycle mid-flight** — known, planned (overhaul waves + worker spec), but until Waves 2–8 land, #245-class incidents and role-blind counting remain live.
3. **No node-version-skew design** — `Hello` carries no version field; codecs have no evolution rules; no rolling node-binary-upgrade story, no ticket. Cheap now, expensive after GA freezes the wire.
4. **Verification depth** — no DST, dormant Ember, slice-processor/jbct under-tested, no backup/DR or node-upgrade suites; 4 rc1 test-infra tickets open.
5. **Security findings untracked** — 2 Critical + 2 High open (silent policy substitution; plaintext bootstrap API key; StrictHostKeyChecking=no; ONNX-path RCE) existing only in a store-dir markdown; only #209/#205 are ticketed.
6. **Resource governance is partially structural, partially unfinished** — true per-slice memory/CPU containment is **not achievable in a shared JVM** (no per-thread heap accounting); the in-JVM trusted-slice model makes it a structural non-goal that should be *documented* as such, not a gap. What IS achievable and unfinished: the off-heap stream budget spec (rc1, unimplemented, ~7-stream exhaustion cliff today), concurrency caps / rate limiting (#144), and observability-driven placement. No ticket covers the achievable subset.
7. **Application-surface fragmentation** — 4 DB stacks with no choosing guidance, 7/8 untested, jOOQ dormant; "three built-in qualifiers" doc bug; missing @Scheduled/jOOQ/@Http-primary examples.
8. **Observability philosophy is implemented but undocumented as a design.** Aether deliberately rejects classic observability (continuous bulk telemetry export — traffic that interferes with normal operation). Instead, slice assembly is instrumented: every injection point is wrapped in a dynamic `Aspect` (structurally enforced — every generated slice factory method's first parameter must be an `Aspect`, `SliceFactory.java:121`), runtime-switchable into any combination of metrics/logging/tracing; request-id correlation (`InvocationContext` ScopedValue + MDC + `X-Request-Id`) covers the cross-node story. The gap is purely documentary: the stale 07-observability chapter doesn't articulate this philosophy, so reviewers (including this assessment's first pass) measure Aether against the classic OTel yardstick it intentionally rejects. Cheap fix, prevents recurring mis-assessment.
9. **Design-doc lifecycle** — header rot, fragmented docs tree (operator/ + operators/, dual runbooks/), website-correction backlog unverified, no spec→code traceability outside membership (streaming-read-forwarding's own `SPEC:` round-trip convention: 0 matches).
10. **Foundation reference debt** — core (rc1!) has no versioned API reference; statemachine no semantics doc; HLC undocumented after its move; in-house PBT library undocumented.
11. **Dashboard requires major overhaul (maintainer-confirmed)** — beyond the zero-JS-test finding: fixes plus missing parts, including an observability panel and an operations control panel (deployment control, stuck DB migrations, rolling updates, …). The whole documentation estate likewise needs a dedicated pass — acknowledged as its own epic, deferred deliberately.

## What is notably strong

The slice model end-to-end (annotations → processor → blueprint → deployment FSM, RFC-implemented, well-documented); **the aspect-based observability design** (every injection point runtime-switchable into metrics/logging/tracing combinations — zero-cost when off, no telemetry firehose, a genuine differentiator vs classic observability); **the deliberately in-memory consensus/KV** (Rabia, unlike Raft, carries no transaction log as an algorithmic artifact — recovery is state transfer from live replicas; no fsync on the commit path, no disk-health coupling to consensus health, trivial node replacement; durability = replication + the git-backed backup loop for operator-grade DR. `StorageBackedPersistence` being unused is by design, not a severed wire); the integration harness (16 charter'd suites, multi-tenant parallelism, readiness contract); the deployment lineage; KV backup/restore (full loop: routes + CLI + git-backed persistence); security wiring (validators live, audit log, cert rotation suite); the CLI's breadth; examples-as-CI-gate (where included); and — as of this week — the membership design discipline (ratified keystone, wave gating, disposition table, invariants). That keystone pattern is the repo's own best practice, ready to replicate.

5. **Raise verification at the leverage points**: slice-processor golden tests, jbct-core/cli baseline, then the DST/simulation direction the overhaul already ratified for FSMs.
6. **Adopt seam ownership**: every spec names its consumer-facing wires (the worker spec's §11 interface-contract section is the template) so "engine without ignition" can't pass review again.

Server-side multi-statement execution (PG simple-query protocol) noted as fallback mode only. Runtime verifies per-statement checksums so a hand-edited blueprint cannot desync what executes from what was validated.
