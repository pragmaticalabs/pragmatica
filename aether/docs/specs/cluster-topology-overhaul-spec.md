## 2. The problem in one sentence

Liveness truth is co-owned by three layers (QUIC transport, SWIM, MembershipFsm) joined by circular feedback, and membership lives in six concurrent views that agree by timing rather than by construction; every recent incident (#94 flap, #245 under-load, connectedPeerCount=3, three SWIM mis-diagnoses) is a manifestation of that one structural property — and the same multi-authority pattern recurs in miniature in the worker tier, where role-blind counting lets a worker inflate quorum/heal/role-assignment. This overhaul collapses the views to a single per-node authority, makes every layer a single-emission-source / pure-projection, makes counting role-correct, and deletes the machinery the multi-authority model required.

### 3.1 Hard constraint (non-negotiable, bisect-proven)

Membership-delta emission **must be decoupled** from BOTH:

1. `evaluateQuorumState`'s quorum-presence `ClusterStateNotification` routing (per-tick or per-promotion invocation regressed READY-convergence 0–20s → 600s, 2026-06-09; the promotion-edge `onMemberPromoted → ReevaluateMembership` variant caused a catastrophic restore-READY flap with evictInactiveLink storms — stash `wip-#1-onMemberPromoted`), and
2. `publishCoreMembershipDelta`'s `removeNode → DisconnectNode` side-effect.

`evaluateQuorumState` is **load-bearing and timing-sensitive** — it is invoked ONLY on its existing five triggers (`addNode`, `removeNode`, `handleSetClusterSize`, `handleReevaluateMembership`, `start`) and is **narrowed**, never broadened, by this spec. The sanctioned direction (audit item 4) is: the **FSM emits a typed membership-delta event on its own promotion/death edges**, and a **pure projection** consumes it to maintain the `previousCoreMembers` baseline and route `MembershipDecision` — structurally separate from `evaluateQuorumState`. Why the promotion-edge `evaluateQuorumState` invocation flapped is not fully pinned; the spec treats it as forbidden and routes around it.

### 4.2 Invariants (the spec is "done" only when all hold)

- **A1 — Single alive-authority.** SWIM probe-ack is the sole "alive" truth. Transport may report death (bias the suspect timer / drop a link), never life. (Already enforced by death-ward; never regress.)
- **A2 — Single membership authority.** `MembershipFsm` per-member state is the only answer to "is N a member, and in what state?" Every other view (PresenceSampler set, TopologyObserver `coreNodeIds`, QUIC `peers`, LeaderElection topology) is either a sensor feeding the FSM or a projection of it — never a competing authority.
- **A3 — Single emission source per layer.** `PeerState` transitions → exactly one typed transport event each (including evictions and dial-failures). FSM membership edges → exactly one `MembershipDelta` each. Consumers are pure projections that re-derive, never re-decide.
- **A4 — Edge-driven, never per-tick.** No periodic re-evaluation of quorum/membership. Reconciliation is level-triggered against current state (the transport executor) or edge-triggered (delta emission). Respects §3.1.
- **A5 — State reconstructible.** Per-member FSM state is reconstructible from SWIM snapshot + KV (leader handoff rebuilds it). Leader-scoped components (LeaderReconciler/CTM) are dormant on followers, active on the leader.
- **A6 — Delete more than we add.** Six views → fewer; ten SWIM maps → one per-member record; three role vocabularies → one; dead code stripped. The net line count must fall. (The transition journal §5.1 and the activation-gated replay §5.8 are the only structural additions; both are bounded and replace ad-hoc machinery.)
- **A7 — Leader-canonical decisions, local-view derivation (Enrichment B).** Every node runs the `MembershipFsm` as a *local* view of membership and drives its *own* transport executor from it. Cluster-canonical `MembershipDecision` deltas (`NodeJoined`/`NodeRemoved`, the cluster's agreed membership statements) are emitted **only from the quorate leader** — a non-quorate or follower observer must not advertise membership decisions the majority has not committed. This is already structurally enforced (delta emission is quorum-gated via `inQuorum()`/minority-suppression, and only the leader's `MembershipDeltaProjector` routes); A7 states it as an explicit invariant so no future consumer re-derives cluster-canonical membership from a follower's local view. A follower's local FSM view drives only local concerns (its own transport dial-set, local routing, local quorum-liveness) — all self-correcting — never a cluster-wide statement.
- **A8 — Role-correct counting; one role vocabulary (Wave 2).** Quorum, auto-heal deficit, role assignment, and `QuorumLossDetector` count **CORE-role members only** — a WORKER never contributes to a quorum/heal/role-assignment count or fills a core deficit. The FSM exposes an explicit role-scoped projection (`coreCountedMembers()` built on the existing `coreMembers()`); every `countedMembers()` call site is deliberately assigned the right projection (§5.2 call-site audit). The cluster standardizes on the config role vocabulary **CORE/WORKER/SPOT** carried in `MemberDescriptor`; the transport `ACTIVE/PASSIVE` vocabulary is vestigial (never produced) and is deleted in the strip wave. `CORE_ONLY` placement is structurally impossible on a worker.

### 4.3 The two state machines (the clean seam)

| | **MembershipFsm** (authority) | **Transport executor** (mechanical) |
|---|---|---|
| States | OBSERVED → MEMBER → SUSPECT → DEPARTING → DEAD | INIT → CONNECTING → CONNECTED → EVICTED → REMOVED |
| Owns | who is a member, role (CORE/WORKER/SPOT) / source, incarnation fencing, the **desired connection-set**, the **delta edge** | dial, single-dialer direction, offline-buffer, reconnect-backoff, per-lane streams, write, **one typed event per transition** |
| Driven by | SWIM observations + PresenceSampler debounce + executor connect/disconnect feedback | the FSM's `desiredConnections()` (reconcile actual→desired) |
| Per-node? | yes, always-on | yes |

The FSM answers *who*; the executor answers *how*. The executor's phase machine is mechanical delivery state with no membership opinion — so it cannot become a third authority.

## 5. Per-wave design

Each wave is independently revertable and gated by a Docker validation run (§12). Waves are ordered so the worker-hygiene + #245 live bugs land early, structural simplification follows, and the riskiest SWIM-internal surgery is in the middle (after the Wave-1 instrumentation answers the empirical open questions). **Wave 1 (instrumentation + transition journal) ships first and stays in-tree permanently** (ratified D2). **Wave 2 (worker hygiene) and Wave 3 (dialer identity) touch disjoint code and are parallel-eligible**, both landing before the #245 delta wave (Wave 4) so its gate is not polluted by W3-class role mis-assignment under churn.

### Wave 1 — Instrumentation, transition journal & truth-capture (no behaviour change)

**Goal:** answer the audit's empirical open questions (§6.1, §6.6), detect the §6.4 future-history hazard, and make every subsequent wave verifiable from a log read, not code-tracing. The 2026-06-10b hard lesson: capture the live failing-test timeline; a constant failure timing ⇒ a fixed timer you have not identified.

**Changes (diagnostic; no control-flow effect):**
1. **Per-node persistent TRANSITION JOURNAL (Enrichment A) — permanent.** A bounded, in-memory, structured per-node ring buffer that appends **every `MembershipFsm` transition AND every `PeerState` transition** as a record `(monotonicSeq, wallClockMs, layer=FSM|PEER, nodeId/peerId, from, to, cause, incarnation?, role?, ageNanos?)`. Properties:
   - **Bounded** (configurable cap, default e.g. 4096 entries per layer; oldest evicted) — survives until process exit, not just the current test window.
   - **Dumpable on demand** via a management endpoint (`GET /api/cluster/journal?layer=fsm|peer&limit=N`) and on a `WARN`/`ERROR`-class transition (auto-flush the tail to the log).
   - **Not consensus, not KV** — pure local observability, lost on crash (a crash replays KV next boot anyway, §5.8). The diagnostic substrate that would have turned #245's multi-day archaeology into a single journal read.
   - **Permanent**, not temporary instrumentation — the standing record the spine's explicit state machines make cheap (FSM/PeerState transitions are already single-chokepoint, so journaling is one append at each chokepoint).
2. **Dialer-side expected-vs-actual sender log** at `QuicClusterClient.completePeerConnection` (`:536-537`): log `(dialedPeerId, hello.sender(), resolvedAddress)` on every completed outbound handshake (and journal it). The §6.1 diagnostic + the precursor to the Wave-3 identity check.
3. **FSM membership-edge + baseline trace**: the journal carries OBSERVED→MEMBER and →DEAD edges; add a periodic (diag-only) dump of `previousCoreMembers` vs `coreMembers()` vs `presenceSampler.currentMembers()` — proves the #245 baseline gap empirically before Wave 4 fixes it.
4. **SWIM FAULTY-residency trace** (§6.6 / H8): log + journal the interval between `transitionToFaulty` stamping `suspectTimestamps` and `cleanupFaultyMembers` removing the member; confirm whether the designed `suspectTimeout×3` residency is honoured or the same-tick sweep defeats it.
5. **Boot-time future-history sanity check (§6.4, detect-only).** On boot, after the node learns the cluster's reported Rabia term/logIndex, compare against its OWN persisted Rabia term/logIndex. If the node's persisted term/logIndex **exceeds** what the joined cluster reports ("I have a future this cluster never saw" — the mixed-wipe / `down -v` hazard), emit `WARN` + a journal entry. **Detect-only** — recovery design stays RC2 (§6.4).
6. **`/api/cluster/topology` diagnostic extension**: expose per-member FSM state + incarnation + descriptor (role/source) (already partly via `memberStates()`/`memberDescriptors()`), so a remote run reads membership truth without `docker logs`.

**Closes:** prerequisite for C3, C4, H8, #245, W1–W6 verification; detection for §6.4. No findings closed directly.

### Wave 2 — Worker accounting hygiene (Class 1, W1–W6) — the worker-tier echo of "one denominator"

**Goal:** close the six live correctness bugs by which a single worker inflates role-unfiltered counts. These are small, role-filter-shaped fixes to landed code (companion audit §2 Class 1), the worker analogue of audit item 6 (one quorum denominator). They land EARLY — they are live bugs, and leaving W3-class role mis-assignment in place would pollute the #245 gate (a transient over-count under 02-chaos churn can mis-assign a REPLACEMENT as WORKER at the `coreMax` boundary, plausibly contributing to observed replacement-readiness weirdness). Parallel-eligible with Wave 3 (disjoint code).

**The role-scoped projection (Q1 resolved — do NOT leave a role-blind parallel authority).** Build on the FSM's existing `coreMembers()` (MEMBER+SUSPECT minus `role=="worker"`, `MembershipFsm:450-457`): add an explicit **`coreCountedMembers()`** (the core-scoped count). Then **audit every `countedMembers()` call site** and deliberately assign each consumer the right projection — quorum / heal / role-assignment / `QuorumLossDetector` → **core-scoped**; any genuinely role-agnostic consumer stays and is documented as such. This follows `membership-fsm-unification §6` (`QuorumLossDetector → role=core, MEMBER-only strict`). The call-site audit table:

| Call site | Today | Becomes | W# |
|---|---|---|---|
| `TopologyObserver.haveQuorum` / `healthyOnDutyCount` (`PresenceMembershipView:40-52`, `TopologyObserver:666-679`) | `members.size()` role-blind | core-scoped count | W1 |
| `QuorumLossDetector` numerator | role-blind | core-scoped, MEMBER-only strict (§6 direction) | W1 |

**The six fixes:**
1. **W1 — quorum role-blind.** `healthyOnDutyCount = members.size()` (role-blind) and the `QuorumLossDetector` numerator must count **CORE role only**. A 1-core + 2-worker cluster must NOT pass `haveQuorum` for a 3-core config (Rabia has no voter majority). Fix via the core-scoped projection above.
2. **W2 — heal deficit role-blind.** Heal deficit compares role-blind `countedMembers()`/`effective()` to `configuredCoreCount` — workers fill the gap arithmetically, so a dead core is never replaced once workers exist. Fix: deficit reads `coreCountedMembers()`.
3. **W3 — role assignment miscounts.** `currentCoreCount = activeNodes().size()` includes workers → would-be cores below `coreMax` mis-assigned WORKER. **Note:** under 02-chaos churn the transient over-count (ghost + replacement) can mis-assign a REPLACEMENT as WORKER at the `coreMax` boundary — flagged as a possible contributor to observed replacement-readiness weirdness. Fix: count core-role members only.
4. **W4 — provisioning never stamps worker role.** `provisionReplacement` hardcodes `"core"` (`ClusterTopologyManagerRecord:455-478`); user-data hardcodes `aether-role=core` and inherits `AETHER_ROLE` from the bootstrapping host (`UserDataTemplate:227, 262-271`). Since the SWIM `role` label is the ONLY worker classifier, a provisioned worker looks like a core to every projection. Fix: the provisioned node carries its **intended role explicitly** (passed through `provisionReplacement` → user-data → `AETHER_ROLE` label → descriptor), not inherited/hardcoded.
5. **W5 — runtime worker scale corrupts core size.** `ClusterConfigApplier` ignores `scale.role()` — `ScaleUp(source, WORKER, n)` calls `setDesiredSize` (core) (`ClusterConfigApplier:48-74`). Fix: **role-route the scale op**; a WORKER-scale must NOT touch core sizing. **Decision:** worker provisioning is not yet wired (Class 2, out of scope), so for RC1 a WORKER-targeted scale is **rejected with a clear operator error** (logged + non-success `Result`), not silently applied to core. (When worker provisioning lands in #241 it becomes a real worker-pool op.) Stated explicitly so the behaviour is not a silent no-op.
6. **W6 — CDM `activeNodes()` includes workers.** The `isPassive` filter is structurally always false → a READY worker enters `allocatableNodes()` and both `AllocationPool.coreNodes` and `mainWorkers`; `CORE_ONLY` can land on a worker. Fix: `CORE_ONLY` placement filters to core-role members; a worker can never be a `CORE_ONLY` target. **Spec'd unconditionally** — correct regardless of whether an observation-mode worker can report READY today (Q2). ### Wave 4 — Close the #245 membership-delta baseline gap (the live bug)

**Goal:** make `NodeRemoved`/`NODE_FAILED` fire for a victim that joined while OBSERVED, **without** invoking `evaluateQuorumState` on promotion (§3.1).

**Root (empirically pinned this session, confirmed in code):** `MembershipDecision` is emitted ONLY by `TopologyObserver.publishCoreMembershipDelta` (`:730`), which diffs `coreMemberIds()` against `previousCoreMembers`, and `previousCoreMembers.getAndSet` runs only inside that method, called only from `evaluateQuorumState` (5 triggers). ### 5.8 The activation-gated notification replay (sync → activate → replay) — AMENDED 2026-06-11

> **AMENDED 2026-06-11 (user design, ratified): the consumer-side action log is SUPERSEDED by an engine-level inversion of the boot order.** The first Wave-8 cut implemented the action log as spec'd below the rule; it worked as built (gate-RCA-verified), but it distributes a *discipline* — "remember KV may fire before ACTIVE" — across every present and future consumer, and the codebase had already grown three ad-hoc replay-on-restore mechanisms compensating for the same ordering (`GossipKeyRotationHandler.replayFromStore`, the `LeaderKey` snapshot-replay re-fire for viewSequence seeding, the ActionLog itself). One engine-level mechanism replaces the class.

- **Problem (unchanged):** a component (NDM, CDM, route registry, …) observing a KV event while `RabiaEngine` is **not yet ACTIVE** (cold boot, re-sync after a `ConsensusPassive` edge) cannot safely act yet.
- **Mechanism (inverted order):** `sync → activate → replay`.
  1. **Sync installs KV state SILENTLY** — snapshot install / catch-up applies populate storage but fire NO notifications.
  2. **Activate** — the engine becomes ACTIVE (consensus participation; correctness depends only on the synced log/state, never on consumer reactions).
  3. **Replay** — the engine walks the synced store and fires one synthetic `ValuePut` per key as the **first work on the apply path**, live applies queued behind it. Consumers receive a totally-ordered stream — world-as-of-N, then N+1 onward — indistinguishable from having been online the whole time.
- **Invariant bought:** *a KV notification implies Rabia is ACTIVE.* No consumer checks activation status, ever. The barrier is structural, not disciplinary.
- **Constraints (required):**
  - **Subscribe-before-start** — all KV subscribers register before the engine starts (one central wiring rule, replacing N consumer guards).
  - **Level-triggered subscribers only** — replay delivers the current value per key, not history; a consumer needing every transition belongs on streams, not KV notifications.
  - **Mid-life snapshot install** (an already-ACTIVE lagging node catching up) does **diff-replay**: puts for new/changed keys, removes for vanished ones, same apply-path ordering.
  - **Idempotency / precondition re-check stays a consumer property** — a replayed put may describe an already-satisfied state; converging consumers no-op. (Normal convergence-loop hygiene, not a boot rule.)
- **Subsumes (delete on rework):** the ActionLog, `replayFromStore` (gossip keys arrive as replayed puts), the `LeaderKey` re-fire special case (viewSequence seeding observes the replayed put), and every per-consumer "is the engine active yet?" guard.
- **Relation to A6:** net-negative — one engine-level gate replaces three ad-hoc mechanisms plus scattered guards.

### 5.9 M5 — rejoin/boot as convergence to KV desired state (Wave 8.6)

1. **Boot/rejoin = KV replay → NDM redeploys KV-claimed ACTIVE self-instances.** Instead of trusting (or distrusting) stale local slice state, the node **converges to the KV desired state**: it reads the KV-claimed ACTIVE instances for itself and (re)deploys them. Heals a `down -v` wipe (local empty, KV has claims → redeploy) AND any local-vs-KV divergence (local stale, KV authoritative → reconcile to KV). No separate "detect phantom ACTIVE" path — convergence to KV makes phantom entries impossible by construction.
2. **No gating needed at NDM (amended with §5.8):** by the time ANY KV notification reaches a consumer, the engine is ACTIVE — the boot replay delivers the KV-claimed ACTIVE self-instances as ordinary puts on NDM's normal route, and the idempotent precondition re-check (still the claimed owner? still ACTIVE in KV? already deployed → no-op) makes the burst safe. The previously-spec'd per-consumer action log is superseded (§5.8 amendment).
3. **Boot-epoch (per-process ULID under a stable NodeId, to distinguish continued-vs-restarted) stays RC2** (§6.5d) — future work. RC1 convergence-to-KV is idempotent whether the node continued or restarted, so it does not need it.
