## THE REAL #131 BLOCKER (traced live, confirmed, OPEN)
Scenario: 12-network S05/S06 — 2 non-leader minority `docker network disconnect`+`connect` (5s, < 8s self-drain) → reconnect on a NEW IP (same ULID).
- Model C un-fences them → they rejoin membership, `/health/ready=200` on all 5, `ConsensusActive` logged. SWIM-health "5 healthy cores" passes in ~2s.
- **BUT only 2 followers publish `NodeReportedState=READY` to the lifecycle KV** (the check counts that, needs ≥4 of 4 followers; leader is normally absent). The minority can't commit their reportedState Put through consensus.
- **Why:** leader DIALS the rejoined node fine — `connectPeer` uses the **configured hostname** (`aether-b-node-3`), Docker-DNS-resolved to the CURRENT IP → Hello handshake completes, "8 lanes registered". **The dial address is NOT the problem.** ~0.5s later `evictStaleConnection` fires "evicted stale (inactive) link" (no inbound traffic on the leader's link) → reconciler re-dials → **loop every ~5s; `connectedPeerCount=3`**. The rejoined node connects OUTBOUND to the leader too (its server logs "Hello handshake complete with peer node-1") but does NOT carry **bidirectional consensus** on the leader's link → it goes inactive.
- **Conclusion:** the blocker is **QUIC connection management after a same-ULID reconnect** — the established link gets no return traffic and is torn down as inactive. The address-relearn (Part 2) cannot fix this because the address was never the leader-side problem. **QUIC idle-timeout is DISABLED (`MAX_IDLE_TIMEOUT_MS=0`)**, so `connection.isActive()` flips false on a genuine close, surfaced at the 1Hz consensus write (`writeToStream:1020`→`evictStaleConnection:1165`).

1. **Connection-direction/dedup after reconnect** — `ConnectionDirection.shouldInitiate` (`QuicClusterNetwork:767`) makes only the deterministic side dial.
