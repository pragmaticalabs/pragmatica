### Fixed (2026-09-28 — #1640: cluster events were dropped when the cluster-events partition's owner died)
- **A cluster event whose publish does not land is held and re-sent, not dropped.** When the partition-0 owner dies, every forward to it times out as `PublishOutcomeUnknown`. Two Ember runs measured 2,216 failed publishes after an owner kill, all of them this cause. Events raised in that window, such as `LEADER_ELECTED`, `NODE_FAILED`, auto-rollback decisions and operator warnings, used to be logged and lost. They are now re-sent once a second (backoff up to 8 s, immediately on a new owner) for up to 5 minutes. At most 1,024 are held, and overflow drops the oldest. Every drop is counted by reason, one WARN line names the dropped event types, and the first expiry logs once at ERROR. [verified: aether/node/src/test/java/org/pragmatica/aether/api/ClusterEventRedeliveryTest.java — unit-level]
- **The emit gate is not re-applied on a retry**, because the producing node is typically no longer the owner after a failover. [verified: `ClusterEventAggregatorTest.emit_firstPublishFails_ownershipMovesAway_retryStillLands` — re-applying the gate turns it red]
- **No event is read twice.** Each event is stamped with `details.eventId` (`<per-process ULID>:<sequence>`) on its first delivery. A re-sent event keeps that id, and `events()` removes duplicates by it; events without an id fall back to `at`. This is not a wire change: `details` is an existing map. `at` alone was not an identity, because two distinct events can share it. [verified: `ClusterEventAggregatorTest.events_sameEventLandedTwice_isReadOnce`, `events_twoDistinctEventsWithTheSameAt_areBothKept`] Reads are sorted by `at`, because a re-sent event lands after later ones. [verified: `events_landedOutOfAtOrder_areReadInAtOrder`] The live event feed has no time window: each poll sends whatever in the retained log it has not sent, so an event is broadcast exactly once however late it lands. That also closes a pre-existing gap for events that landed after the poll covering their time. [verified: aether/node/src/test/java/org/pragmatica/aether/api/EventWebSocketPublisherTest.java] **The raw stream read endpoint does not de-duplicate or sort**; de-duplicate by `details.eventId`.
- **At most 1,024 events are held, waiting and in flight together.** The bound used to cover the waiting queue only, so it could reach 2,048. [verified: `ClusterEventRedeliveryTest.deliver_withRetriesInFlight_heldNeverExceedsCapacity`]
- **Limit: redelivery needs the partition to get a new owner.** On this release a dead cluster-events owner is not re-placed: two Ember runs saw no new owner within 120 s even after the member reached DEAD, because stream placement follows the installed voter set (#1550, fixed by #1555). Until #1555, held events expire after 5 minutes, counted and logged. A partition flagged for an operator (#1596) refuses publishes the same way. [verified: aether/forge/forge-tests/src/test/java/org/pragmatica/aether/forge/ClusterEventOwnerFailoverTest.java]
- [unverified: duplicate from an unknown outcome that landed] The read-side dedup is pinned by a unit test. Ember never produced such a duplicate (0 removed on read in 4 runs), because on this release no retry can land without a new owner. Whether the case occurs, and that dedup removes it end to end, waits for #1555.
- **Also measured, not caused by redelivery:** in every Ember run, 2 events that the owner had ACKED before it died are not in the log. The stream is EVENTUAL with min-sync 1, so the owner acks before replicating, and events it acked but never replicated die with it. [verified: `ClusterEventOwnerFailoverTest`, which asserts the log holds no more than was delivered]
