### Fixed (2026-09-28 — #1640: cluster events were dropped when the cluster-events partition's owner died)
- **A cluster event whose publish does not land is held and re-sent, not dropped.** When the partition-0 owner dies, every forward to it times out as `PublishOutcomeUnknown`. Two Ember runs measured 2,216 failed publishes after an owner kill, all of them this cause. Events raised in that window, such as `LEADER_ELECTED`, `NODE_FAILED`, auto-rollback decisions and operator warnings, used to be logged and lost. They are now re-sent once a second (backoff up to 8 s, immediately on a new owner) for up to 5 minutes. At most 1,024 are held, and overflow drops the oldest. Every drop is counted by reason, one WARN line on the next successful publish names the dropped event types, and the first expiry logs once at ERROR. [verified: aether/node/src/test/java/org/pragmatica/aether/api/ClusterEventRedeliveryTest.java — unit-level]
- **The emit gate is not re-applied on a retry**, because the producing node is typically no longer the owner after a failover. [verified: `ClusterEventAggregatorTest.emit_firstPublishFails_ownershipMovesAway_retryStillLands` — re-applying the gate turns it red]
- **A redelivered event is not read twice.** Each event is stamped with `details.eventId` (`<per-process ULID>:<sequence>`) once, when the aggregator accepts it and before its first publish attempt, through `ClusterEvent.withDetail`, which every variant implements (compile-checked, no reflection). A re-sent event keeps that id, and `events()` removes duplicates by it; events without an id fall back to `at`. This is not a wire change: `details` is an existing map. `at` alone was not an identity, because two distinct events can share it. [verified: `ClusterEventWithDetailTest.withDetail_everyClosedVariant_addsTheDetail_andKeepsEverythingElse`, `ClusterEventAggregatorTest.emit_firstAttemptLandsButFails_retryCopyHasTheSameId_andIsReadOnce`, `events_sameEventLandedTwice_isReadOnce`, `events_twoDistinctEventsWithTheSameAt_areBothKept`] `GET /api/v1/events` reads are sorted by `at`, because a re-sent event lands after later ones. [verified: `events_landedOutOfAtOrder_areReadInAtOrder`] The live event feed follows an offset cursor: each poll reads from the offset after its last read (less a 16-event overlap), and a redelivered event is appended beyond it, so it is sent however old its `at` is; the feed sends in landing order, not `at` order. After a cluster-events owner failover the new owner can reuse offsets the feed already read, so the feed re-reads the new log from its oldest retained offset when the node applies the ownership change or when the log it reads moves back below the cursor. The feed sends each event once for as long as its first copy is retained: it remembers every `eventId` it sent, with its offset, until retention trims that offset, so neither the overlap, a re-read after a failover, nor a re-sent copy is sent again. A copy landing after its first copy was trimmed would be sent twice (a duplicate, never a miss). [verified: aether/node/src/test/java/org/pragmatica/aether/api/EventWebSocketPublisherTest.java, `ClusterEventAggregatorTest.eventsFrom_readsFromTheGivenOffset_andReportsTheNextOne`, `feed_wiredToTheAggregator_readsFromTheCursor` — unit-level; the failover re-read is not reproduced end to end] **The raw stream read endpoint does not de-duplicate or sort**; de-duplicate by `details.eventId`. **Limit: at-least-once across an ownership handover.** An owner-gated fact (a deployment, scale or threshold event every node can derive) raised on both sides of a cluster-events ownership handover is delivered twice, with distinct `eventId`s, because the owner gate is each node's own view of ownership; `eventId` collapses only redeliveries of one raise. This holds within the redelivery horizon (5 min) and capacity (1,024 held events); see guarantees.md row 14b. The converse window, where neither node passes the gate, loses the fact; both are tracked as #1671. [verified: `ClusterEventAggregatorTest.emit_ownerHandover_bothOwnersRaiseOneFact_eachRaiseIsDeliveredAtLeastOnce` — unit-level]
- **At most 1,024 events are held, waiting and in flight together.** The bound used to cover the waiting queue only, so it could reach 2,048. [verified: `ClusterEventRedeliveryTest.deliver_withRetriesInFlight_heldNeverExceedsCapacity`]
- **Limit: redelivery needs the partition to get a new owner.** On this release a dead cluster-events owner is not re-placed: two Ember runs saw no new owner within 120 s even after the member reached DEAD, because stream placement follows the installed voter set (#1550, fixed by #1555). Until #1555, held events expire after 5 minutes, counted and logged. A partition flagged for an operator (#1596) refuses publishes the same way. [verified: aether/forge/forge-tests/src/test/java/org/pragmatica/aether/forge/ClusterEventOwnerFailoverTest.java]
- **A duplicate from an unknown outcome that landed is removed end to end.** With #1555 re-placing a dead owner, the Ember owner-and-leader-death test produced one such duplicate and read it once: sent 796, landed 796, dropped 0, 1 duplicate removed on read. [verified: `ClusterEventOwnerFailoverTest.eventsRaisedAcrossOwnerAndLeaderDeaths_eachLandOnceOrAreCountedDropped`, CI forge-tests job 109373978948 at 1508a4726 merged with rc4 4201f14bc] [unverified: ownership-change drain in a with-#1555 cluster; the owner is replaced before events wait, and the drain route was pinned only on a head without #1555]
- **Also measured, not caused by redelivery:** in each measured Ember run of the owner-kill test, 2 events that the owner had ACKED before it died were not in the log. The number depends on timing, not a rate: a later run on #1555 lost 0 of 474. The stream is EVENTUAL with min-sync 1, so the owner acks before replicating, and events it acked but never replicated die with it. [verified: `ClusterEventOwnerFailoverTest`, which asserts the log holds no more than was delivered]
