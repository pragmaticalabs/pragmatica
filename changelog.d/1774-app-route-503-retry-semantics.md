### Fixed (2026-09-30 — #1737: docs and changelog for the app-route 503 mapping)
- **The app-route 503 documentation now states what 503 does and does not promise.** 503 means "transient, retry later", not "not executed": `Cause.Transient` includes timeouts where the call may already have run (slice invocation `TimeoutError`, `HttpClient`/JDBC timeouts, `CoreError.Timeout`), so retrying a 503 on a non-idempotent operation can repeat its effect — use an idempotency key or server-side dedup, or retry only refusals the API documents as pre-execution. `PublishOutcomeUnknown` stays 500 because its outcome is unknown.
- **Corrected #1765's "explicit mapping always wins" claim:** an explicit mapping to a status other than 500 is kept, but an explicit `500` mapping of a transient cause answers 503, because a generated `default` cannot be told apart from an explicit one.
- **Corrected #1765's changelog comparison with #1735:** the Management-API publish path answers 503 only for an allow-list (`NOT_ENOUGH_REPLICAS`, `RemotePublishRetryable`), not for every transient cause, and answers 500 for `STREAM_MEMORY_EXCEEDED`; app routes answer 503 for every `Cause.Transient`.
