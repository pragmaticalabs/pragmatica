### Fixed (2026-10-29 — #686, #1726: an apply recorded no VM it created)
- **A VM created by `aether cluster apply` had no ledger row until after the provider answered, and the apply kept the created VMs only in memory**, so a crash between the provider's answer and any write left a billed VM nothing could find, and a later failure of the apply listed only what that process still remembered. Each node is now recorded write-ahead: an `INTENDED` row is written durably before the provider create (a failed write means no create call), the `CREATED` row with the provider's server id after it, and every terminate is preceded by a `TERMINATING` row. [verified: `WaveExecutorLedgerTest.createThenKill_everyVmTheProviderHoldsHasALedgerRow`, `killAtEveryStepAndOccurrence_neverLeavesAVmWithoutARow_andTheLeakCheckHoldsOutsideTheLookupWindow`, `intentWriteFails_noProviderCall_noVm`]
- Every VM an apply creates now carries an `aether-apply=<apply id>` label next to `aether-cluster`, `aether-source`, `aether-role` and its node id, and the apply checks after the create that the VM carries it: a provider that silently drops a label (Hetzner drops a label it does not accept, without an error) no longer leaves a billed VM invisible to every later audit; such a VM is terminated at once and, if the terminate fails, named STILL RUNNING AND BILLED. Docker is checked through the daemon's label filter, because the Docker provider re-stamps its answer from `docker inspect`. [verified: `WaveExecutorLedgerTest.providerDropsTheApplyLabel_failsAndTerminatesTheVm`, `dockerContainerWithoutTheApplyLabel_failsAndIsTerminated`]
- Docker nodes are created one container per call with the node id minted before the call (the group call minted ids inside the provider layer, after the point where the row has to exist). The create spec is unchanged except for the added labels. [verified: `WaveExecutorLedgerTest.dockerPerNodeSpec_isTheGroupPathsSpecForTheSameNodeId_plusOnlyTheLabels`]
