### Added (2026-09-19 — #1302: durable-entity checkpoint-lag metric and alert threshold)
- **A stalled entity checkpointer was visible only as a flat `writes` counter**; nothing measured how far a partition's recovery would have to replay, and nothing alerted as that distance grew toward the slow sealed-storage recovery path (#1240).
- `GET /api/v1/entity/checkpoints` (and `aether entity checkpoints`) now reports `checkpointLag` per partition this node folds: the log head offset minus the COMMITTED checkpoint in consensus KV, for partitions this node OWNS. Partitions it does not own — a replica's, or one it has released — are absent rather than 0, and the baseline is never this node's own save record, which a fenced save leaves claiming coverage the cluster refused (#700). A takeover therefore raises no spurious alert. `[mechanism: EntityCheckpointDriver computes head − committed per owned partition on read, with the committed pointer supplied by EntityCheckpointLagMetric.committedCheckpoints]`, pinned by `EntityCheckpointDriverLagTest`.
- The lag is reported after every tick, including one whose checkpoint work throws, so a stalled checkpointer cannot freeze the metric; a partition whose head cannot be read is left out of that tick rather than taking the report down. The sink and the committed-checkpoint lookup are named node bindings (`EntityCheckpointLagMetric.sinkFor` / `committedCheckpoints`), and a test pins that the lag lands in the collector under the exact alert metric name and raises then clears the alert through the production evaluation loop.
- The node's largest lag is published every checkpoint tick as the metric `entity.checkpoint.lag.max` and evaluated by the threshold alert path, which raises and clears with hysteresis. The default threshold is WARNING 5,000 / CRITICAL 10,000 records: half the entity ring, and the ring (10,000 records per partition), past which recovery must read sealed storage. Configure it with `[alerts] entity_checkpoint_lag_warning` / `entity_checkpoint_lag_critical`; it is seeded only when the cluster holds no threshold for the metric, so `POST /api/v1/thresholds` overrides it. `[mechanism: seeded in AlertManager.bindAlertConfig; evaluated by AlertManager.checkThreshold]`, pinned by `AlertManagerThresholdEventTest.EntityCheckpointLag`.
- `[unverified: the tick → metric → alert path has not run on a live cluster]`. The node binding of the lag sink is pinned by `AlertingWiringLivenessTest.entityCheckpointLagSinkIsBoundByProductionCode` (dead-surface gate).
