### Fixed (2026-11-07 — #811: deploy preflight did not bind topic sections, so an unknown key surfaced at slice activation)
- **A topic section that holds an unknown or dashed key now fails the deploy, not the slice activation.** The deploy preflight (`ConfigSectionPreflightValidator`) only required generic resource sections to exist and excluded topic sections. It now also binds every topic section a slice publishes to or subscribes from (`TopicSectionPreflight`) through `ProviderBasedConfigService.config(section, TopicConfig.class)` over the view the slice loader binds from, the binder activation uses. An `@StrictKeys` refusal (`ConfigError.UnknownKey`, with the nearest-key suggestion), an inert stream knob on an ephemeral topic and any other `TopicConfig` bind refusal are reported per slice and section, all of them, in one failure. An ABSENT topic section stays legal (it provisions an ephemeral topic, #396); activation keeps its own refusal as the backstop. [verified: `ConfigSectionPreflightValidatorTest$TopicSections`, `BlueprintServiceTest$TopicSectionPreflight`]
- **`POST /api/v1/blueprints/validate` now runs the deploy preflight.** It was a DSL parse only. It now also expands the blueprint's slices from the repository and runs the same preflight as the publish route (pub/sub, topic tier, route collisions, config sections including topic sections, replication) through `BlueprintService.validateDeployable`, storing nothing; a refusal answers `valid: false` with the cause's message. **Behaviour change:** a blueprint whose artifacts cannot be resolved from the repository, which this route used to accept, is now reported invalid, because a publish would refuse it. [verified: `BlueprintServiceTest$TopicSectionPreflight.blueprintWithDashedKeyInTopicSectionRefusedAtValidate`]
- Limits: only sections the deploy can see are bound (the node composite on the leader and the slice jar's `META-INF/resources.toml`); with neither, the check is skipped, as the section-presence check is. Checks that need the cluster's replication defaults stay in `ReplicationPreflight`.
