### Changed (2026-10-31 — #2201 C-02: the segment sealer seals evicted events in runs, not one segment per event)
- **A full ring no longer seals one segment per evicted event.** Each append to a full ring evicts about one event, and each eviction used to become its own segment: two fsyncs and a DHT quorum put per event, so a node sealed as many blocks per second as its streams took events. The sealer now holds a partition's queued evictions as one RUN and seals it as one segment once its bytes reach `[streaming] seal_run_bytes` (1 MiB), its events `seal_run_events` (4096), or its oldest event's wait `seal_run_age` (5 s); a backlog that queued behind a slow seal becomes one block of up to `seal_merge_bytes` (4 MiB). All four defaults are guesses, settled by a baseline run. `[verified: SegmentRunFormingTest; SegmentSealingGranularityTripwireTest (the three C-02 real assertions, both admission paths)]`
- **A read of a pending offset seals its run at once** (`EvictionListener.holdsUnsealedForRead`, used by `StreamPartitionManager.sealInFlight` and the entity log substrate), so it waits for the seals ahead of it, not for `seal_run_age`. A failed seal is retried as the same run. `[verified: SegmentRunFormingTest]`
- **A spilled seal reads its WAL range with a bounded buffer.** `AppendLog.replay` scans the file in a 64 KiB buffer and checks each record's CRC chunk by chunk before it materializes it, instead of reading the whole file per seal (which failed past 2 GiB); a corrupt length that fits the file ends the valid prefix without being buffered. `[verified: AppendLogTest#replay_ofALargeLog_allocatesABoundedBuffer_notTheFile, AppendLogTest$ReplayValidity#replay_aCorruptLengthThatFitsTheFile_stopsWithoutBufferingIt]`
- **Without a WAL, a crash can lose up to `seal_run_age` more of the acknowledged-but-unsealed events.** A graceful node stop seals everything the sealer holds first (the seal in flight and the runs behind it), waiting up to 5 s; a range it could not seal is raised as the `stream-seal-stop-incomplete` operator warning. `guarantees.md` (Restart without a WAL) states the window. `[mechanism: SegmentSealer.ready; verified: SegmentRunFormingTest$GracefulStop, StreamSealerWiringBootTest]`
- **`seal_merge_bytes` is refused above 256 MiB and `seal_run_age` above one day** at config load (a merged block is one array; an age near the long range overflows the age timer deadline into a timer that re-fires at once; both bounds are guesses). `[verified: ConfigLoaderTest#loadFromString_sealMergeBytesAndSealRunAge_areBounded_theBoundLoads_andAValuePastItIsRefused]`
- **Known limits.** Once the sealer's heap copies reach half the pending cap, every partition's run is sealed at once, quiet ones included; a run with k entries spilled to the WAL reads the WAL k times per attempt; an attempt that lands in the index but reports failure lets WAL truncation pass the run, and a retry that must rebuild a spilled entry then fails `WalRangeMissing` (terminal) every cycle, holding the partition's later runs behind it `[unverified: by reading only]`.
