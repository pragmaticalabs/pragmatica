### Changed (2026-10-31 — #2201 C-02: the segment sealer seals evicted events in runs, not one segment per event)
- **A full ring no longer seals one segment per evicted event.** Each append to a full ring evicts about one event, and each eviction used to become its own segment: two fsyncs and a DHT quorum put per event, so a node sealed as many blocks per second as its streams took events. The sealer now holds a partition's queued evictions as one RUN and seals it as one segment once its bytes reach `[streaming] seal_run_bytes` (1 MiB), its events `seal_run_events` (4096), or its oldest event's wait `seal_run_age` (5 s); a backlog that queued behind a slow seal becomes one block of up to `seal_merge_bytes` (4 MiB). All four defaults are guesses, settled by a baseline run. `[verified: SegmentRunFormingTest; SegmentSealingGranularityTripwireTest (the three C-02 real assertions, both admission paths)]`
- **A read of a pending offset seals its run at once** (`EvictionListener.holdsUnsealedForRead`, used by `StreamPartitionManager.sealInFlight` and the entity log substrate), so it waits for the seals ahead of it, not for `seal_run_age`. A failed seal is retried as the same run. `[verified: SegmentRunFormingTest]`
- **A spilled seal reads its WAL range with a bounded buffer.** `AppendLog.replay` scans the file in a 64 KiB buffer and never materializes a skipped record, instead of reading the whole file per seal (which failed past 2 GiB). `[verified: AppendLogTest#replay_ofALargeLog_allocatesABoundedBuffer_notTheFile]`
- **Without a WAL, a crash can lose up to `seal_run_age` more of the acknowledged-but-unsealed events.** A graceful node stop seals what is queued first, best effort. `guarantees.md` (Restart without a WAL) states the window. `[mechanism: SegmentSealer.ready, SegmentSealer.flushAll]`
