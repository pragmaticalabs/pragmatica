### Changed (2026-11-23 — #3390: a declared `[hot] max_bytes` below `max_event_size` is refused at stream create)
- **A stream whose declared `[hot] max_bytes` is smaller than its `max_event_size` is no longer accepted.** It was created, and the ring's effective maximum silently became the hot window (an event between the two was refused as `EventTooLarge` at the ring). Create now refuses it before any ring is built or byte reserved, with the typed `StreamError.HotWindowBelowMaxEvent` naming both values (HTTP 400), for plain and `entity:` streams; `hot == max_event_size`, `hot > max_event_size` and an absent `[hot] max_bytes` (default window, at least one maximal event) are accepted. A stream already committed with such a window is not re-checked. `[verified: aether/aether-stream/src/test/java/org/pragmatica/aether/stream/StreamRingWindowTest.java HotBelowMaxEvent]` `[mechanism: StreamPartitionManager.checkHotHoldsMaxEvent in createFreshStream, the one create admission every create path passes]`
- **The ring-level `EVENT_DROPPED` for a legal event is now pinned at the ring, not the manager.** The manager-level pins (`StreamPartitionManagerFrozenRingDropTest`, one `DefaultStreamPublisherBatchTest` case, the disabled #1233 entity pin) asserted a path no create can reach once a ring holds one maximal event; they are deleted, and the ring's drop (single and batch, DROP_OLDEST and REJECT_WHEN_FULL) is pinned in `OffHeapRingBufferTest.FrozenRingDrop`. Residual, not changed here: an unclustered manager keeps incarnation 0, so a same-name recreate with a smaller `max_event_size` replays the old WAL (#3616).
