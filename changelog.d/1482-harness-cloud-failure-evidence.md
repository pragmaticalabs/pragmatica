### Fixed (2026-09-24 — #1482: cloud integration runs kept no evidence of their failures, and the restore gate could pass with a core missing)
- **Failed cloud suites captured no node logs.** `capture_node_logs` had no `cloud` branch: it wrote a "captured" manifest and returned, so all 8 failed suites of the 2026-09-23 rc4 run had a manifest and nothing else, and the VMs that ran them were reaped by mid-run recovery before the run ended. The cloud branch now ssh's to every VM of the cluster **at suite end** (after each test's own cleanup restore — not at the instant of failure, so a restore that re-bootstrapped the cluster leaves only the new generation) and saves each node's log since the suite started, plus the leader's provisioning snapshot. Each ssh is bounded (90s, plus 60s on the remote command). The manifest records every VM's rc and "captured N of M"; zero VMs, a failed enumeration, refused ssh or a missing `AETHER_SSH_KEY` each say so instead of reading as a capture. [verified: `aether/tests/integration/test/test-restore-gate.sh` C1-C5, stubbed ssh and enumeration; a probe with the real `_run_with_timeout` bounded two hanging VMs to 4s at a 2s limit] [unverified: not yet exercised on a live cloud run]
- **The restore gate could pass with a core missing.** Its "whole" test was `deficit == 0 && reachedFullMembership`. The product's `deficit` subtracts an `effective` count that includes a dispatched-but-not-joined replacement, and `reachedFullMembership` is a latch, so four members plus one in-flight replacement passed. The gate now also requires the leader's `countedCoreMembers` to reach the target, and on success logs the measured counted/effective/deficit instead of printing the target. A cluster stuck below target now fails restore with the provisioning snapshot in the message, so later destructive suites may be quarantined where they used to run degraded. [verified: `test-restore-gate.sh` R1-R5 — the in-flight 4-of-5 snapshot fails, a whole cluster passes, and removing the new clause turns R2 red] [unverified: which snapshot shape passed on 2026-09-23 was never recorded — the gate logged nothing measured on success. A second shape also fits: `countedCoreMembers` is MEMBER + SUSPECT, so a dead core still held as SUSPECT passes both the old and the new gate]
- **Partition firewalls leaked where no reaper could see them.** They were created without labels, and `cloud-reaper.sh` selects on `aether-cluster`; two were left behind on 2026-09-23. They now carry `aether-cluster=<cluster>` and `aether-role=partition`, and a firewall reused under its deterministic name from an earlier run is relabelled. [verified: `test-restore-gate.sh` F1-F2; and on the real Hetzner API a firewall with these labels is listed by `cloud-reaper.sh --cluster <name>`]
