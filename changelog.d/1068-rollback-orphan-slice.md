### Fixed (2026-09-13 — #1068: a rolled-back blueprint deploy could leave a slice instance that was re-deployed and served with no owning blueprint)
- **A rollback's UNLOAD is its own consensus round and can fail, and nothing behind it asked whether the version was still wanted.** Measured in CI run 34772700962 (`StreamCrashDurabilityTest`): the blueprint rolled back, `handleAppBlueprintRemoval` removed the `SliceTargetKey`, the UNLOAD commands timed out (`Consensus apply timed out after 30000ms`), and 123ms later a node logged "KV claims ACTIVE … not loaded locally — redeploying" and served the slice. Three producers, all fixed here: the node's KV-convergence redeploy, pending-LOAD replay and live ACTIVATE started a slice on the strength of a `NodeArtifactKey` alone; the orphan sweep walked the leader's in-memory `sliceStates` and dropped the entry BEFORE issuing the UNLOAD, so one timeout meant the key was never looked at again; and the unload chain's endpoint "unpublish" wrote `NodeArtifactValue(ACTIVE, methods=[])` between the UNLOADING put and the key removal — a claim the redeploy path then healed into a running slice.
- One predicate, `CommittedSliceTarget.permits`, read from the committed KV store and never from a projection: a version is permitted while the committed `SliceTargetKey` names it, or while a rolling update's `VersionRoutingKey` names it as the old or new version. An absent target permits nothing. [mechanism: `aether/aether-deployment/src/main/java/org/pragmatica/aether/deployment/CommittedSliceTarget.java`]
- The node refuses to load, activate or redeploy a version the predicate does not permit, and writes nothing on refusal. [verified: `aether/aether-deployment/src/test/java/org/pragmatica/aether/deployment/node/fsm/NodeDeploymentStateRollbackOrphanTest.java` — `RedeployAfterRollback`, `LoadAndActivateAfterRollback`, each with a positive control showing the same drive reaches the `SliceStore` when the target is committed]
- **A refusal is deferred, not final.** The first CI run of this fix (34785390505, `SliceMediaTypeTest`) showed a follower applying the leader's LOAD 4 ms before it applied the `SliceTargetKey` put the leader had already acted on; the gate refused and nothing re-checked, so the slice never loaded. The store a node reads is the one the consensus applier writes (the same `KVStore` instance `RabiaNode` drives), but a follower's applied set can still lack an earlier put when a later command runs. So a refused start is parked in `NodeDeploymentState.Active.deferredStarts` and re-driven through the same gate when a `SliceTargetKey` or `VersionRoutingKey` for that artifact base arrives (`NodeDeploymentManager.onSliceTargetPut`/`onVersionRoutingPut`, wired in `AetherNode`); a newer put or a removal for the key drops the deferral, so the leader's UNLOAD for a rollback leftover wins over any later target. The deferral rides a quorum cycle with the suspended slices (`Dormant` carries it into the next `Active`): an ACTIVATE or an ACTIVE claim has no other route back, since the leader re-issues neither and only LOAD keys are rescanned on re-entry. `Dormant` ignores puts and removals, so on re-entry every carried deferral whose key the committed store no longer holds at the deferred state is dropped — a leftover the sweep removed meanwhile is not re-driven into a slice the leader never allocated. [verified: `NodeDeploymentStateRollbackOrphanTest.DeferredStart` — LOAD/ACTIVE-claim/old-version applied before the target or routing entry, re-driven on its arrival; a target for another base or another version does not re-drive; an UNLOAD in between is not undone by a later target; `DeferredStartAcrossQuorumCycle` — ACTIVATE and ACTIVE-claim deferrals survive `QuorumDisappeared`/`QuorumEstablished`; a deferral whose key was removed during Dormant is not re-driven] The `AetherNode` wiring of the two observations is pinned through a booted single-node cluster, applying the puts through the node's own `KVStore` and reading the FSM's own log lines. [verified: `aether/node/src/test/java/org/pragmatica/aether/node/DeferredStartRedriveWiringBootTest.java`]
- The leader substitutes UNLOAD for ACTIVATE under the same predicate when a LOADED slice reports in. [verified: `ClusterDeploymentStateActiveTest.RollbackActivateSubstitution`]
- `StaleEntryCleaner.cleanupOrphanedSliceEntries` now walks the committed `NodeArtifactKey` entries and re-issues UNLOAD (or the removal, for a key already at UNLOAD or UNLOADING) on every reconcile tick until the key is absent from the store. UNLOADING is deliberately included: the node's own key removal spends its consensus retries under a timing-out consensus and nothing else re-issues (measured in CI run 34788864919, a key stuck at UNLOADING for the whole 4-minute wait). Keys of departed nodes stay with `cleanupStaleNodeArtifactEntries`. [verified: `ClusterDeploymentStateActiveTest.RollbackOrphanSweep` — re-issue on a second sweep, stop once the key is gone, no-op while core membership is unresolved, re-issue after a failed consensus write, UNLOADING removed until gone]
- The core node's teardown chains no longer write an ACTIVE claim. The `unpublishEndpoints` step is removed from the unload, deactivate, force-cleanup and activation/reactivation-failure chains: `EndpointRegistry` ignores empty-method puts, the transitional put before it already carries an empty method list, and the unload's Remove is what unregisters. [verified: `NodeDeploymentStateRollbackOrphanTest.UnloadPath.unload_neverPutsActive`]
- A rolled-back rolling update now removes its `VersionRoutingKey` in the rollback batch, after restoring the old target — the same end `complete` gives a finished update. `ROLLED_BACK` is terminal, so nothing else would ever remove it, and while it existed the rolled-back new version stayed permitted to start and stayed allocated (the leader skips deallocation while `activeRoutings` holds the base). Request routing never read the entry (`activeRouting` filters terminal deployments). The order inside the batch is load-bearing: the leader's `handleRoutingRemoval` deallocates every version the committed target does not name at that moment. [verified: `aether/aether-invoke/src/test/java/org/pragmatica/aether/update/SliceTargetOverridePreservationTest.java` `rollback_removesTheRoutingEntry_afterRestoringTheOldTarget`; `aether/aether-deployment/src/test/java/org/pragmatica/aether/deployment/CommittedSliceTargetTest.java`]
- `KVStore.installSilently` overlays the restored snapshot and then drops the keys it lacks, instead of `clear()` then `putAll()`: a concurrent reader never sees an empty store mid-install. [verified: `integrations/cluster/src/test/java/org/pragmatica/cluster/state/kvstore/KVStoreInstallOverlayTest.java` — the restored map's iterator reads the store back on every step of the install]
- **Guarantees, stated per mechanism, with their preconditions.** A node that has *applied* the rollback's `SliceTargetKey` removal never starts that version again: every start reads the committed store after that apply, and Rabia's total order places any later LOAD/ACTIVATE/ACTIVE put after the removal. The precondition is doing the work — the follower in run 34785390505 lacked an earlier put while holding a later one, and whether that anomaly can also apply a Remove late or drop it is not established here (ticket drafted in the fix report). The gate does not by itself keep a legitimate deploy from starting: a start refused before its target is applied is re-driven when the target arrives. Orphaned keys are removed *eventually*, and only while a leader holds quorum and consensus progresses — the sweep runs inside the leader's `Active` state, refuses to act until core membership is resolved, and each UNLOAD is a consensus write that can fail and be re-issued on the next tick. No time bound is claimed.
- Not changed here: the worker's own teardown (`WorkerDeploymentManager.teardownSlice`) still forwards the same ACTIVE-with-no-methods put before its removal — a separate ticket is drafted in the fix report. The typed "no target" `StreamAddressError` for a slice whose owning blueprint is gone is deferred until #1066 (PR #1071) merges; until then the bare-alias fallback in `BlueprintStreamAddresses.engineKeyFor` is unreachable from a deployed slice only because the node no longer starts one. `[design intent — unverified]`
- Fixture corrections in existing tests, each stated: `NodeDeploymentFsmTest.KvConvergenceRedeploy`, `ActivationRaceNotFatalTest` and `NodeDeploymentManagerTest` drove starts with an empty KV store, which after this change is the rollback-leftover state rather than a live deployment; they now seed the committed target they always described. `RetryExhaustionTerminalTest`'s "terminal must hold" assertion rejected any command for the artifact; after this change the reconcile issues an UNLOAD for the leftover LOAD key (a teardown, the opposite of a re-drive), so it now rejects LOAD/ACTIVATE only.
