### Fixed (2026-09-14 — #588: terminated workers lingered as UNKNOWN membership ghosts in cluster status)
- **A dead worker was never forgotten by the two rosters the status routes read, so it stayed listed with `derivedStatus: "UNKNOWN"` indefinitely.** A core node's death travels on `MembershipDecision.NodeRemoved`, which `ClusterSyncCollector.removeNode` (the pong roster — `allMetrics()` is the node list `GET /api/v1/cluster/status` serves) and `TopologyObserver.pruneDeparted` (the transport topology — the node list `GET /api/v1/status` serves, the discovery-gossip set and the dial set) both consume. A worker's death travels on the separate `WorkerLeaveDecision` channel (#731), and that channel reached only the cluster deployment FSM. Membership had already declared the worker dead; the rosters were simply never told. [mechanism: `MembershipDeltaProjector.emitWorkerLeave` emitted the leave and did not prune; `AetherNode` routed `WorkerLeaveDecision` to `clusterDeploymentManager::onWorkerLeave` only; `TopologyObserver.addNode` admits a worker from the same SWIM `JoinAnnounced`/`MemberDiscovered` edges as a core, with no role filter, and `removeNode` is reachable only through `pruneDeparted`]
- `emitWorkerLeave` now prunes the departed worker from the transport topology exactly as the core removal arm does, and `AetherNode` routes `WorkerLeaveDecision` to `metricsCollector.removeNode` alongside the existing `NodeRemoved`/`NodeDecommissioned` routes. [verified: `WorkerRosterPruneBootTest.routedWorkerLeaveDecision_removesTheWorkerFromThePongRoster` — a real booted node, roster seeded through the collector's pong ingress and asserted present first; reverting the route entry alone reddens it. `MembershipDeltaProjectorTest.workerRemoval_prunesTheWorkerFromTheTransportTopology` pins the projector hunk. Also `TerminatedWorkerGhostTest` (3 cores + one hard-killed worker), which is `Heavy`] `[unverified: the Heavy test is NOT in the default CI gate — `ci.yml` passes `-Dfailsafe.excludedGroups=Heavy` and `heavy-forge-tests` reports `skipped`; the two unit pins above are what the merge gate actually runs]`
- **The leader's ping re-installed a worker a follower had already removed, so the ghost survived on every node but the leader.** `ClusterSyncState.handlePingTick` makes ping dispatch leader-only and a pong is addressed to the pinger alone, so a follower's `remoteMetrics` is fed by nothing but the leader's ping — and `onClusterSyncPing` MERGED that ping into the roster instead of retaining the roster to it. Each node projects a death on its own membership verdict, so a follower that pruned the worker at t_F took it straight back from a ping the leader issued before its own verdict at t_L > t_F, and no later ping evicted it again. `remoteMetrics` had no TTL, no sweep and no key-diff; `removeNode` was its only eviction. [mechanism: `ClusterSyncContext.broadcastPing` stamps `collector.allMetrics()` unfiltered, which is correct — the leader cannot filter on a verdict it has not reached yet, so the fix belongs on the receiving side]
- `onClusterSyncPing` now calls `retainPingRoster` before storing, dropping every node the accepted ping does not carry through the same `removeNode` the leader itself ran. The follower converges on the first ping after the leader's own prune whatever order the two verdicts landed in, so its local prune is no longer load-bearing. The retain sits BEHIND the term fence, so a deposed leader's stale-term ping cannot empty a live roster. [verified: `ClusterSyncCollectorPingRosterRetentionTest.pingWithoutTheWorker_evictsAWorkerAnEarlierPingInstalled` — red at the round-1 head, and reverting `ClusterSyncCollector.java` reddens exactly it across 2891 tests of `aether-metrics` + `aether-deployment` + `aether/node`; two sibling tests pin that the retain keeps everything the ping carries and that a fenced-out ping evicts nothing]
- **A member that died without ever joining stayed in both rosters on every node, leader included.** `MembershipFsm.enteredDead` emits the REMOVED delta only when `everJoined`, so a member reaped OBSERVED→DEAD by the join-grace reaper — which is the reap's whole point — emitted no delta at all and neither roster arm above could ever see it. The rosters do not wait for promotion: `TopologyObserver.addNode` admits on the SWIM discovery edge and `remoteMetrics` on the first ping or pong carrying the node, both before MEMBER. `enteredDead` now fires a dedicated `onNeverJoinedDeath` listener on that arm, which `AetherNode` wires to `topologyObserver.pruneDeparted` plus `metricsCollector.removeNode`. [verified: `MembershipFsmTest$NeverJoinedDeath.neverHealthyReap_firesTheRosterPruneOnceAndStillEmitsNoDelta` and `.neverHealthyReapOfAWorker_firesTheRosterPrune` — reverting the `enteredDead` arm reddens exactly those two and nothing else across the same 2891 tests; a third test pins that a JOINED member's death still takes the REMOVED delta and does NOT fire this arm, so the projector's prune cannot become dead code] `[unverified: the AetherNode install site itself — deleting the `membershipFsm.onNeverJoinedDeath(...)` wiring reddens 0 of aether/node's 1450 tests. Reaching the lambda from a booted node needs a second QUIC peer that handshakes and then never goes SWIM-healthy; the FSM's OBSERVED ingress is the SWIM observation tap and the QUIC peer-state listener, neither routable through `AetherNode.route`]`
- **The join-grace window is unchanged, deliberately.** It exists to stop a booted-but-not-yet-SWIM-healthy joiner being reaped mid-join — `MemberTracking.joinGraceReapDeferred` refuses to reap while the transport link is live, because a boot deploy-storm can starve the first probe-ack — and shortening or bypassing it would trade this ghost for killed legitimate joiners. Only the reap's fan-out grew; its timing and its deferral predicate are untouched. [design intent — unverified: no measurement of joiner survival under a deploy storm was taken in this change]
- **No durable record can resurrect the worker into either roster.** Both are in-memory and presence-derived: `remoteMetrics` is a `ConcurrentHashMap` fed only by ping/pong, `nodeStatesById` only by SWIM discovery. [mechanism: search space is the `sealed interface AetherKey`, compiler-exhaustive in one file — no member carries node-membership or roster state; `TopologyObserver` states the same ("membership is presence-derived in v2, with no node-state KV write")] The one durable record that CAN resurrect a worker is `ActivationDirectiveKey(nodeId)`, which `ClusterDeploymentState.restoreWorkerNode` rebuilds into `workerNodes` on activation — #731 already deletes it in the SAME `apply(consensusCommands)` batch as the node's slice, artifact and route keys, with `sweepDeadRestoredWorkers` as the rebuild-path backstop. Nothing in this change alters that batch.
- Not changed: the other consumers a core `NodeRemoved` reaches and a worker leave still bypasses — `DeploymentMetricsCollector` (per-node deployment metrics), `SliceInvoker` (pending invocations to the dead node are retried on `NodeRemoved`; for a worker they wait for the 20s timeout, tracked as #1137), `httpRouteRegistry.evictNode`, `appHttpServer.onNodeRemoved`, `controlLoop`, `eventAggregator`, `lbm`. None produces the status ghost; they are listed for a separate ticket rather than widened into this fix. `[unverified: whether any of those retains observable state for a dead worker beyond the KV-driven cleanup #731 already performs]`
- The earlier projector test assertion that the prune "must not run for a worker" was wrong, not the code it now fails against: it described the prune as core-only, but the topology it prunes is not core-only. It is replaced by the test above; the core-channel emptiness assertions in the same test are unchanged.
