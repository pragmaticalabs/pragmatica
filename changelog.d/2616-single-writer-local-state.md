### Fixed (2026-11-03 — #2616: AlertManager, ObservabilityConfigRegistry and LogLevelRegistry re-applied a committed value in the apply continuation, overwriting a later commit)
- **The alert-threshold map, the observability config map (and its live cells) and the log-level registry (and the logger configuration) are written only by the commit's own notification handler.** `AlertManager.setThreshold`/`removeThreshold`, `ObservabilityConfigRegistry.setConfig`/`removeConfig` (and so `setDepth`/`removeDepth`) and `LogLevelRegistry.setLevel`/`resetLevel` used to write the same state a second time in the apply continuation. If another commit to the same key was absorbed between commit A and A's continuation, the continuation put A's older value over the newer one, silently and without notifying anyone, and the node's state disagreed with the store until the next change. The continuations now keep only their log line and failure handling. This is the hazard `DynamicConfigManager` already closed (F4/W-9) [verified: `AlertManagerStaleContinuationTest`, `ObservabilityConfigStaleContinuationTest`, `LogLevelRegistryStaleContinuationTest`, each committing A then B before A's continuation runs].
- **Read-your-write on the originating node now rests on the notification, not on the continuation.** At this tree the store publishes the notification inside the commit, before the apply promise resolves, so a request that reads back after the write returns still sees it. Once notifications are delivered off the apply thread that ordering has to be provided by the delivery path [mechanism: `KVStore` publish inside `mutate`; `AetherNode` registers `onAlertThresholdPut`, `onObservabilityConfigPut`, `onLogLevelPut` and the matching removes]. The in-tree tests that wrote and read back now drive the commit's own notification through `ObservabilityCommittingStub`.
