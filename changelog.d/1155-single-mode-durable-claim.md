### Fixed (2026-10-18 — a SINGLE-mode scheduled task no longer runs twice when leadership changes mid-fire, #1155)
- **Before:** the in-flight guard of a scheduled task was a set inside each node's scheduler. A leader elected while the previous leader's fire was still running started with an empty set and fired on its next tick, so one schedule ran twice; the old leader also wrote the task row when its run ended, as a non-leader.
- **Now:** a SINGLE-mode fire is claimed in cluster state before it runs (`ScheduledTaskClaimKey`/`ScheduledTaskClaimValue`, tags 2166/2167, recorded in the wire baseline) and the claim is given up when it settles. A leader that finds a held claim does not fire; the tick is a recorded skipped overlap. The claim row is `HolderFenced`: the applier takes a write only as the immediate successor of the committed row, and a release only over a row carrying the releaser's own per-acquisition token (the version alone is not enough: a task removed and registered again restarts its chain, and an old fire's release would be the immediate successor of the new holder's row). A claim older than `max(interval, completionBound + max(1 s, completionBound / 10))` (11 minutes with the default 10-minute bound) is taken over by the next leader; the old run's release is then refused by the applier and its outcome is not recorded, so one run is recorded per claim.
- **Guarantee, and what it is not:** at most one run is STARTED per claim while its holder is alive, and at most one run's outcome is recorded. A run that is overridden has already executed (the invocation cannot be cancelled), so after a leader is lost mid-fire the callee can run twice, once recorded. A leader lost mid-fire also costs its task up to the bound above. Claim time is the claimant's wall clock read against the evaluator's, so clock skew moves the bound by the skew. `/trigger` and `/inject` take the same cluster claim and answer 409 while it is held.
- **The state row is fenced to the claim too:** a SINGLE-mode fire's outcome write (success, failure, unknown) carries its claim token (`ScheduledTaskStateValue.boundHolder`) and the applier refuses it once a newer acquisition is committed, so a superseded fire cannot overwrite the row of the fire that replaced it. A write bound to no claim (a skipped tick, `/inject`, the late resolution of an UNKNOWN outcome, task clean-up) and a per-node ALL-mode row are not gated. **Wire (additive):** `ScheduledTaskStateValue` gains one trailing component (`boundHolder`) under a NEW wire tag (2168). The old tag (1634) keeps decoding the previous twelve-component shape, as the current type with no bound holder, so a snapshot or persisted state written by an older build still restores (the restore decodes the snapshot as one unit, so an undecodable row would have failed it whole). Encoding always writes 2168. The claim types are new (2166/2167). Mixed-version operation of rc builds is otherwise not supported.
- **Cost:** SINGLE-mode only. One claim row per task (removed with the task, not per fire) and two extra writes per fire (claim and release) next to the one state-row write. ALL-mode is unchanged. A claim write that cannot be committed skips the tick.
- Mechanism: `ScheduledTaskClaims`, `ScheduledClaimStore` (`aether-invoke`); the applier arms `HolderFenced`, `HolderGuarded`, `HolderBound` (`KVStore`); `AetherNode` wires the committed store.
