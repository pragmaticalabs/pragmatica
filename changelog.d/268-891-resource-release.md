### Fixed (2026-09-06 — #268, #891: no provisioned resource was ever closed at slice unload — production `provide()` bypassed the cache, and the default close could not see the project's own close conventions)

- **Every resource provisioned by generated slice code leaked at unload, and `releaseAll` reported success (#268 R1).** Generated code reaches the CONTEXT `provide()` overload; only the plain overload wrote `promiseCache`, so `releaseAll` drained a map nothing had populated and a close was never *attempted*. Both overloads now take one lifecycle path that memoizes the provisioned resource, registers its consumer BEFORE provisioning (so a release racing an in-flight provision cannot close what the caller is about to receive), and releases through the cache
  [verified: `SpiResourceProviderLifecycleTest$SliceScopedLifecycle#releaseAll_closesResource_provisionedThroughContextOverload`, `#provide_provisionsOnce_whenOneSliceProvidesTwice`; making the context overload bypass the cache again turns 7 of the module's 138 tests red — the list is in the pull request].
- **The context overload is cached PER PROVISIONING SLICE — key `(type, section, sliceId)` — deliberately, not per node.** That overload is codec-scoped: `SliceLoadingContext.CodecAwareResourceProvider` injects the deployed slice's own codec as `Serializer`/`Deserializer` on every call, because it is the only codec that knows the application's record types. A key without a slice dimension would hand slice B the resource slice A built with A's codec, making B's application-typed stream events and DHT entries unencodable — #526 reintroduced by a leak fix. `PublisherFactory` is a second, independent reason: it derives a topic's namespace from the provisioning slice's `Artifact`. Not a behaviour change: the context path was uncached before, and generated code provisions once per slice inside its static create path, so each slice already received its own instance; what is new is that the instance is memoized within the slice and released when that slice unloads. **Recorded consequence: DB connection pools are per-slice, not per-node.** That is today's behaviour, so it is not a regression — a genuinely shared pool is a deliberate design change needing its own ticket, not something to acquire from a cache key
  [verified: `SpiResourceProviderLifecycleTest$CodecScopingSurvivesCaching#secondSlice_receivesItsOwnCodec_notTheFirstSlices` — two slices, same type and section, different codecs; drops the slice dimension and slice-b receives codec-a; `$SliceScopedLifecycle#provide_givesEachSliceItsOwnInstance`, `#releaseAll_closesOnlyTheReleasingSlicesResource`].
- **The plain (context-free) overload keeps its shared `(type, section)` cache, and its resource is never released by any slice's unload.** A plain-overload caller carries no identity the provider can attribute to a slice, so no slice's unload may close its resource — the old code did exactly that, closing a cached resource a plain-path holder still used once the context-path consumer set emptied (#268 R2, use-after-close on a live pool). The unattributed scope is now pinned as a bounded leak, which is the safe direction. **This departs from #268's amended acceptance item 1**, which asked for refcount and close-on-last-consumer on this path: without a caller identity there is no "last consumer" to count, so the ticket stays open on that item for the CTO to accept this resolution or reopen it
  [verified: `SpiResourceProviderLifecycleTest$UnattributedScopeIsSharedAndPinned#provide_sharesOneInstance_acrossPlainOverloadCallers`, `#releaseAll_neverCloses_theUnattributedScopesResource` — releasing the unattributed scope's own literal as a slice id also closes nothing].
- **Close goes through the factory that built the resource, not the head of the priority list (#268 R3).** `releaseAll` used `factoryList.getFirst()`; for `SqlConnector`, where the async, R2DBC and JDBC factories all answer and are ordered by priority, that is a different object from the one whose `supports()` matched. The matched factory is now remembered alongside the resource and is the one that closes it
  [verified: `SpiResourceProviderLifecycleTest$ClosesThroughTheProvisioningFactory#releaseAll_closesThroughMatchingFactory_notTheHighestPriorityOne`].
- **A failed provision is no longer memoized (#268 R4).** `computeIfAbsent` cached the failed promise forever, so an `Intermittent` failure the slice-loading FSM retried with backoff handed back the same poisoned promise on every retry. The failing entry now evicts itself and the retry provisions again
  [verified: `SpiResourceProviderLifecycleTest$FailedProvisioningIsNotMemoized#provide_retriesProvisioning_afterAFailedAttempt` (the factory fails once), `SpiResourceProviderTest$Provide#provide_retriesProvisioning_afterAFailedAttempt` (the config loader fails once — the other origin of the same eviction path)].
- **The drop-to-empty test on the consumer set is atomic (#268 R5, in part).** It was a check-then-act over `consumers`; it is now a `computeIfPresent` returning `null`, so exactly one racing release observes the transition and hands the entry to exactly one closer
  [mechanism: `SpiResourceProvider.dropConsumer` inside `ConcurrentHashMap.computeIfPresent`; no test pins the race itself]. **Not addressed from R5:** partial-provision cleanup — a factory whose `provision` allocates and then fails leaves the allocation behind. Per the #891 audit, 2 of 23 factories unwind today (`JdbcSqlConnectorFactory`, `JdbcJooqConnectorFactory`); `AsyncSqlConnectorFactory` builds a Netty pool and leaks it if the connector constructor throws. That is a per-factory change outside this path.
- **The default close could not see the project's own close convention, and reported success anyway (#891).** `ResourceFactory.close` dispatched on the JDK's `AutoCloseable` only; a resource implementing `AsyncCloseable` (`org.pragmatica.lang.io`, `Promise<Unit> close()`) fell through to `unitPromise()`. Dispatch now recognises `AsyncCloseable` first and awaits its promise, then `AutoCloseable` synchronously; a failed close is absorbed and logged in both branches so one bad resource cannot block the release of the rest. A resource implementing NEITHER is a named outcome (`noCloseConvention`) logged at DEBUG rather than a silent success, so a further convention cannot repeat this quietly
  [verified: `SpiResourceProviderLifecycleTest$DefaultCloseConventionDispatch#releaseAll_closesAsyncCloseableResource_throughDefaultDispatch`, `#releaseAll_stillClosesAutoCloseableResource_throughDefaultDispatch`, `#releaseAll_succeeds_forResourceImplementingNeitherConvention`; dropping the `AsyncCloseable` arm turns 4 of 138 tests red — listed in the pull request. The log line for the neither-convention case is not asserted by any test]. **Stated plainly:** before this change no provisioned resource type implemented `AsyncCloseable`, so this arm changes the behaviour of zero resources by itself; it is what the next two bullets dispatch through.
- **All seven `@Sql` connector factories now stop their pools at release.** `DatabaseConnector` declared a THIRD convention, `Promise<Unit> stop()`, and extended neither closeable interface; none of the six concrete connectors (`JdbcSqlConnector`, `PgAsyncSqlConnector`, `R2dbcSqlConnector`, `JdbcJooqConnector`, `R2dbcJooqConnector`, `AsyncJooqConnector`) implements either, so every pool — Hikari, the Netty pg pool, R2DBC — was left open at unload while the close reported success. `DatabaseConnector` now extends `AsyncCloseable` with `close()` delegating to `stop()`: one interface change, zero implementor changes, reaching all seven factories (`db-jdbc`, `db-async` ×2, `db-r2dbc`, `db-jooq`, `db-jooq-async`, `db-jooq-r2dbc`) and the `slice-testkit` fakes that share the interface
  [verified: `DatabaseConnectorCloseTest#releaseAll_stopsTheConnector_throughTheInheritedDefaultClose` — a factory with NO close override, released through the provider, must observe `stop()` having run; `#close_delegatesToStop`; `#connector_isAsyncCloseable_soReleaseDispatchCanSeeIt`. The real connectors' `stop()` overrides are pre-existing and unchanged, and no test in this change drives a real pool].
- **The `@Http` resource is itself `AsyncCloseable`, so releasing it reaches the Netty event loop.** Dispatch sees only the resource OBJECT. `JdkHttpClient` implemented `HttpClient` only and HELD an `HttpOperations` that, with the Netty backend, is the `NettyHttpOperations` owning the `EventLoopGroup` — a closeable one field down is invisible to any dispatch, however wide. `JdkHttpClient` now implements `AsyncCloseable`, closing its operations when they are closeable and succeeding when they are not (the JDK backend owns nothing releasable)
  [verified: `JdkHttpClientCloseTest#client_isAsyncCloseable_soReleaseDispatchCanSeeIt` (both backends), `#close_succeeds_withNettyBackend`, `#close_succeeds_withJdkBackend` — these pin the type and that close succeeds; they do NOT observe the event loop] [mechanism: `JdkHttpClient.close` → `NettyHttpOperations.close`, which calls `eventLoopGroup.shutdownGracefully()`; the thread-count measurement is #895, and see the next heading for why it is blocked].
- **Unattributable claim, retired:** `SpiResourceProviderCompositeTest#provide_withoutCompositeExtension_doesNotEnableCompositePath` asserted that two plain-overload calls returned the same promise; `String.class` has no factory, so what it pinned was a memoized FAILURE (R4 above, as a test expectation). Renamed to `#provide_withoutCompositeExtension_usesConstructorSuppliedLoader` and rewritten to assert the loader routing it is named for.

**Not fixed here — read before expecting a close in production**

- **This change still produces no close on a deployed node.** `releaseAll`'s slice identity can never match a registered consumer: the generated `stop()` passes a two-segment `group:artifact-kebabSlice` coordinate, while registration uses the three-segment `Artifact.asString()` (`group:artifact:version`) — 0 of 34 generated factories on disk can match (**#892**, filed by this work, needs a slice-identity design decision). What lands here is release machinery proven to work when the ids match; it stays inert until #892. **#891's retention measurement (#895) will still show retention after this merges — that is #892, not this fix failing.** A related point for #892's own acceptance: the scope this change keys on is the identity `SliceLoadingContext` registers, so two slices deployed from one artifact share one cache entry and one consumer identity, and the first of them to unload closes the shared resource while the other still holds it. Before this change nothing closed at all, so it is not a regression, but it is the same identity question #892 must settle.
- **Two factory-level `close` overrides remain silent no-ops:** `@Notify`'s `NotificationSenderFactory` (**#271**, leaks the SMTP event loop) and `ContentStoreFactory` (**#893**). Both bypass the default dispatch fixed here and are untouched.
- **`CacheInterceptorFactory` and `IdempotencyInterceptorFactory` retain registries on the FACTORY** that no release path prunes (**#894**, pull request #898 open) — the one leak that survives every fix above because the state is not on the resource.
- **Partial-provision cleanup** (R5, above) and **the plain overload's bounded leak** (R2, above) are recorded, not fixed.
- No other unreleased fragment touches `SpiResourceProvider`, `ResourceFactory`, `DatabaseConnector` or `releaseAll`; nothing to reconcile.
