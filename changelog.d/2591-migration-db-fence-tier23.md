### Changed (2026-11-11 — #2591 FDB-2b: the database-side migration fence, tiers 2 and 3, and H2)
- **SQL Server and Oracle (tier 2) run a migration on one dedicated session holding a session-owned lock for the whole run:** `sp_getapplock` with `@LockOwner = 'Session'`, and `DBMS_LOCK.REQUEST(.., X_MODE, 0, release_on_commit => FALSE)`. A second runner fails with `MigrationFencedInDatabase`. On Oracle the fence needs `EXECUTE ON SYS.DBMS_LOCK`; without it every migration is refused with `FenceUnavailable` naming `GRANT EXECUTE ON SYS.DBMS_LOCK TO <migration user>` (fails closed). Both engines are `[unverified engine: nightly heavy-db only]`; their statements are pinned against a scripted session [verified: `MigrationFenceTest$TierTwo`].
- **H2 is tier 1 through `SET EXCLUSIVE 1`** on the migration's session: a competing runner's connect is rejected by the engine (error 90135) and reported as `MigrationFencedInDatabase`, and the lock goes when the session closes [verified: `MigrationFenceInJvmTest.t12_*`]. H2's `CREATE TABLE` survives a `ROLLBACK`, so its migration dialect is now autocommit-with-checkpoint like MySQL (it claimed transactional DDL before: a latent defect closed here).
- **CockroachDB, DB2 and SQLite (tier 3) hold a per-script lock as the FIRST statement of each script's transaction and re-read the script's history row under it:** `SELECT 1 FROM aether_schema_owner FOR UPDATE` (also for a PostgreSQL-configured CockroachDB, found by the `version()` probe), `LOCK TABLE aether_schema_history IN EXCLUSIVE MODE`, and for SQLite a no-op `UPDATE` of the owner row that takes the write lock at the transaction's start. A serialized second runner finds the row and completes without running the script; any statement failure ends FAILED. The guarantee is per script, not per run: the script's statements and its history row commit at most once. The runner no longer runs CockroachDB unfenced, but the operator notice `schema-migration-unfenced` still says no whole-run fence holds there [verified: `MigrationFenceInJvmTest.t8_*` on SQLite and a CockroachDB-typed recording wrapper; CockroachDB and DB2 themselves `[design intent — unverified]`, fake-only in rc5].
- **A tier-3 script holding a statement that cannot run in a transaction is refused before its first statement** with `NonTransactionalScriptUnfenced` (`CREATE INDEX CONCURRENTLY` on CockroachDB; `VACUUM` on SQLite) [verified: `MigrationFenceInJvmTest.t6_*`]. To recover: move the statement to a migration of its own on an engine that fences it, or run it by hand and baseline.
- **A history insert that meets an existing `(version, type)` row ends FAILED with `HistoryRowCollision`** and is never converted to success; a changed repeatable still fails there as before (#2636) [verified: `MigrationFenceInJvmTest.t8b_*`].
- **Undo and the removal of its history row commit in one transaction** (on tier 3 under the lock, re-reading the row) [verified: `MigrationFenceInJvmTest.undo_*`].
- **Tier-3 bootstrap inserts** (meta version, owner) are `INSERT ... SELECT ... WHERE NOT EXISTS`, and the ownership claim re-reads and matches after its insert, so two bootstrapping runners cannot both insert.
- `MigrationFence.isTierOne` is renamed `isSessionFenced`; `Unfenced` is replaced by `ScriptLock`. Known, not changed: the applied count of a serialized tier-3 runner that skipped a script includes that script.
