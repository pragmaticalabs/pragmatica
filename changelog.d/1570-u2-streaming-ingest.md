### Added (2026-11-07 — #1570: upload ingest streams to content storage and forwards by reference, U2 part 1, off by default)
- **`[app-http.upload] streaming_ingest = true` writes an upload route's body to the node's `content` storage as it arrives, instead of reading it into memory, and dispatches the request with an empty body and a reference (`HttpRequestContext.upload`).** A body that is not multipart becomes one object; a `multipart/form-data` body becomes one object per file part, its text fields travel with the reference. A request forwarded to the hosting node carries the reference, not the body. [verified: `AppHttpServerForwardByReferenceTest`, a 1 GiB upload from node A to the slice on node B in a child JVM at `-Xmx256m`, under 64 KiB forwarded, digest equal on B] [verified: `AppHttpServerStreamingIngestGateTest`, every U1 ingest-gate test re-run over HTTP/1.1 and HTTP/3 with streaming on]
- **Off by default (know 74c6c0810a): nothing reclaims a stored upload until cluster GC (A4).** A stored upload records `expiresAt` = ingest time + `unclaimed_ttl` (default 24h), which nothing acts on yet; an object no slice deletes keeps its space. Operator action: leave `streaming_ingest` off where storage space matters; turning it off stops new stored uploads and removes none. [mechanism: `UploadConfig.DEFAULT_STREAMING_INGEST = false`; no reaper exists]
- **A request that reaches no slice deletes what it stored**: a malformed body (`400`), a part limit (`413`), a storage failure (`503`/`507`), a client that goes away, a security refusal, a route that no longer resolves, no forwarder, a forward that never left this node (nothing was applied), and a local refusal before the slice ran (rate limit, invocation admission) abort the open writer and delete the committed objects. **Kept, by design: a request that may have reached a slice** (a forward whose outcome is unknown, including a serving node that refused it as `upload-unavailable`, or a slice failure after it ran): the slice may have claimed the upload, so the object stays until `unclaimed_ttl` and nothing reclaims it before A4 (know 74c6c0810a). [verified: `IngestSinkTest`; `AppHttpServerStreamingIngestGateTest` (`storedUpload_*`, malformed multipart leaves no catalog entry); `AppHttpServerForwardByReferenceTest` (`upload_whoseForwardNeverLeftA_isDeleted_*`, `upload_whoseOutcomeIsUnknown_isKept`)]
- **Field values are bounded by a byte budget, refused `413` before they are buffered**: a multipart body's text fields are held in memory until the request is dispatched, so their total is capped at `max_field_size` times `max_fields` (or 1 MiB with no `max_field_size`) and never above `max_in_flight_size`; the upload reserves that budget with its write buffer. [verified: `IngestSinkFieldsAboveHeapTest`, 120 fields of 2 MiB at `-Xmx256m` are refused `413` with the heap intact; the control arm with no cap is not]
- **A storage stall is answered `503` with `Retry-After`, never `408`**: while the node itself holds reading off to wait for storage, the body's idle and minimum-rate clocks stop; a write outstanding longer than the route's `idle_timeout` (else `read_timeout`) is the node's fault and ends the request. `max_duration` keeps running. [verified: `RequestGateStreamTest`, `Http3StreamTest` storage-stall tests, red with the change reverted]
- **Forwarding by reference needs content storage both nodes read.** The ingress stores the object where the serving node's content storage must also read it (A2 provides no cross-node read path yet). A forwarded handle whose object the serving node's storage does not hold (deleted since, or stored elsewhere) fails the request `503` (`upload-unavailable` on the serving node, "outcome unknown" to the client) and never reaches the slice. [verified: `AppHttpServerForwardByReferenceTest` object deleted mid-forward, and a serving node with empty storage; both answer `503` with the slice never called, red with the check removed] [unverified: B reading A's object through the DHT]
- **Limits differ from the aggregated path:** the limit is the route's `max_size` under `max_size_ceiling` with no 2 GiB in-memory bound; an upload reserves the smaller of its length and its write buffer (five chunks, 20 MiB) from `max_in_flight_size`; part limits are enforced while the body streams. A body on an upload route that is not decodable multipart is answered `400` (the aggregated path hands it to the handler), a nested multipart part is refused `400` on every upload route, and an upload route without part limits is capped at 128 parts (`413`).
- Wire: `ObjectHandle`, `FileHandle`, `UploadHandle` pinned at 2890..2892 (ledger reservation 2890..2899); `HttpRequestContext` (tag 515) gains `Option<UploadHandle> upload`. Pre-GA shape change; mixed-version clusters are not supported across it.
