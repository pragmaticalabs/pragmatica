### Fixed (2026-09-05 — #654: cursor commits on consumer detach and checkpoint were discarded unobserved)

- **`ConsumerRuntimeState.flushCursorForKey` called `ConsumerCursorStore.commit(...)` — a consensus write — and dropped the returned `Promise<Unit>` unobserved**: no await, no failure log, no counter, no retry. This ran on every consumer detach and inside node stop's #488 ordering window, so a failed final commit before shutdown was invisible. `checkpointIfNeeded`'s periodic commit had the same defect and is fixed the same way.
- **`close()` now bound-awaits every final commit**: `awaitFinalCursorCommits()` collects one `Promise<Unit>` per attached consumer and calls `Promise.allOf(commits).await(CURSOR_COMMIT_SHUTDOWN_BOUND)` with a 5-second bound; node stop always continues past the bound, it never blocks on a wedged consensus write [mechanism: `Promise.allOf` derives its own aggregate promise and `.await(TimeSpan)` on timeout returns a manufactured `Timeout` result without cancelling or resolving the underlying commits — the late result still lands on whichever handlers are attached]. Every commit still unresolved the instant the bound expires is reported individually by `reportIfUnsettled`, not as one aggregate: it increments the node-wide `cursorCommitFailureCount` counter, records the per-partition detail (`unsettled at shutdown bound`), and logs once at ERROR naming that consumer group/stream/partition — the same per-commit surface a genuine failure uses, not a single WARNING naming the whole pending batch.
- **Both paths route through `observedCommit`**, which attaches `onSuccess`/`onFailure` to the commit promise: success clears the consumer's recorded failure, failure increments a new node-wide `cursorCommitFailureCount` counter, records the per-partition detail, and logs once at ERROR with group/stream/partition [verified: `StreamConsumerRuntimeTest.CursorCommitObservability`, 4 tests, plus two surgical single-hunk mutation probes — stripping the handler attachment and stripping the bound-await each failed exactly the predicted subset of tests].
- **Surfaced through the existing read surface, not a new one**: `StreamConsumerRuntime.cursorCommitFailureCount()` (new interface method, node-wide, survives detach) and `SubscriptionSnapshot.lastCursorCommitFailure` (new 7th field, per-consumer, cleared on detach). On the Management API, `DeclarativeConsumerPartition` gained a `lastCursorCommitFailure` field rather than overloading `DeclarativeConsumerDetail.diagnostic` — `diagnostic` is per-consumer and already multiplexes several unrelated health conditions (unassigned partitions, non-publishable event type), while a cursor commit failure is per-partition; folding it in would have lost both the partition granularity and the ability to tell which condition fired when more than one applies. The new field follows the same empty-string-for-absent convention.
- **Redelivery contract documented** in `management-api.md` beside the new fields: a commit that never lands past the shutdown bound is retried the same way any restart replays a partition — from the last durably committed cursor, so at-least-once delivery holds and the operator's recovery signal is the counter/detail staying non-zero, not a thrown error [design intent — unverified against a live multi-node failure injection; the bound and counter are exercised, the end-to-end redelivery-after-timeout path is not].
- **Round 2: the production `ClusterCursorStore` (#488) resolved `commit(...)` on the local disk write alone** — the consensus checkpoint publish that actually makes a cursor visible after failover was fire-and-forget, its failure swallowed at DEBUG, so round 1's entire observability surface above never observed the write the ticket named. `ClusterCursorStore.commit` now chains the publish onto the same `Promise` (`local.commit(...).flatMap(_ -> publishCheckpoint(...))`), keeping #488's rule that a consensus failure must never fail the local checkpoint by recovering the publish failure into a successful `Unit` rather than propagating it — but the failure is no longer discarded: it is recorded (keyed by consumer group/stream/partition) and logged once at WARN, and the 5-second shutdown bound at close now covers the publish leg too, not just the local write [mechanism: `flatMap` chains the publish onto `commit(...)`'s own Promise, so `Promise.await(TimeSpan)`'s existing timeout-without-cancel behavior bounds it the same way it already bounded the local write].
- **`ConsumerCursorStore` gained a default `lastRecoveredFailure(...)` method** (returns empty unless overridden) so a composed store can report an inner-stage failure it chose to recover rather than propagate, without adding a leaky push-callback into the consumer runtime or threading a new argument through `ClusterCursorStore`'s public factory (`AetherNode.java`'s construction call needed zero changes). `ConsumerRuntimeState.observedCommit` now clears the per-consumer failure OPTIMISTICALLY at the start of each attempt (rather than on the outer promise's success) and polls `lastRecoveredFailure(...)` from that same success handler — clearing on success would otherwise erase a recovered failure recorded moments earlier in the same resolution, since a promise's `.recover(...)` side effects are guaranteed to complete before externally-attached `.onSuccess` listeners run.
- **The two failure origins are now distinguishable on the same surface**: `lastCursorCommitFailure` (both the per-partition Management API field and the underlying `ConsumerState` detail) is prefixed `local commit:` when the local write itself failed, or `checkpoint publish:` when the local write succeeded but the consensus publish was the one recovered — an operator reading only the text can tell which write to investigate [verified: `StreamConsumerRuntimeClusterCursorTest` in `aether/node` (the only module where the real `ClusterCursorStore` and the real `StreamConsumerRuntime` are both on the classpath) — a failing consensus publisher leaves the local commit observably successful while the failure lands on the surface with the `checkpoint publish:` text, a never-settling publisher is bounded at the same 5-second close, and a subsequent clean publish clears the recorded detail; `ClusterCursorStoreTest.CommitFanout` pins the store's own recording/clearing/per-key-scoping contract in isolation].
- **Redelivery contract sharpened** in `management-api.md`: on failover to another node the consumer resumes from the last consensus-published checkpoint, not the outgoing node's local cursor — that local cursor is unreadable from any other node — so a lost publish means redelivery from that older, cluster-visible point, at least once.
- **Round 3: the shutdown-bound count no longer double-counts a commit that later also resolves.** A final commit already marked unsettled at the shutdown bound now records one incident, not two, when it goes on to resolve — whether with a genuine local-commit failure or a recovered checkpoint-publish failure: the marking is remembered per-consumer, and both failure paths skip their own counter increment once it is set. The ERROR log for the late resolution still fires — the exact failure cause is new information even when the count is not [verified: `StreamConsumerRuntimeTest.CursorCommitObservability#close_countsUnsettledCommit_whenFinalCommitNeverSettlesWithinBound` and `StreamConsumerRuntimeClusterCursorTest#close_countsUnsettledCommit_whenConsensusPublishNeverSettlesWithinBound` now assert the count stays at 1 after the late resolution, where it previously reached 2].
- **CLI: no change** — the Management API's existing `lastCursorCommitFailure` and `cursorCommitFailureCount` fields carry the round-2 detail without any new shape, so no CLI command needed updating.
