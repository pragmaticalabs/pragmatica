### Fixed (2026-09-05 — #654: cursor commits on consumer detach and checkpoint were discarded unobserved)

- **`ConsumerRuntimeState.flushCursorForKey` called `ConsumerCursorStore.commit(...)` — a consensus write — and dropped the returned `Promise<Unit>` unobserved**: no await, no failure log, no counter, no retry. This ran on every consumer detach and inside node stop's #488 ordering window, so a failed final commit before shutdown was invisible. `checkpointIfNeeded`'s periodic commit had the same defect and is fixed the same way.
- **`close()` now bound-awaits every final commit**: `awaitFinalCursorCommits()` collects one `Promise<Unit>` per attached consumer and calls `Promise.allOf(commits).await(CURSOR_COMMIT_SHUTDOWN_BOUND)` with a 5-second bound. A timeout or failure logs once at WARNING naming the pending count and cause; node stop always continues past the bound, it never blocks on a wedged consensus write [mechanism: `Promise.allOf` derives its own aggregate promise and `.await(TimeSpan)` on timeout returns a manufactured `Timeout` result without cancelling or resolving the underlying commits — the late result still lands on whichever handlers are attached].
- **Both paths route through `observedCommit`**, which attaches `onSuccess`/`onFailure` to the commit promise: success clears the consumer's recorded failure, failure increments a new node-wide `cursorCommitFailureCount` counter, records the per-partition detail, and logs once at ERROR with group/stream/partition [verified: `StreamConsumerRuntimeTest.CursorCommitObservability`, 4 tests, plus two surgical single-hunk mutation probes — stripping the handler attachment and stripping the bound-await each failed exactly the predicted subset of tests].
- **Surfaced through the existing read surface, not a new one**: `StreamConsumerRuntime.cursorCommitFailureCount()` (new interface method, node-wide, survives detach) and `SubscriptionSnapshot.lastCursorCommitFailure` (new 7th field, per-consumer, cleared on detach). On the Management API, `DeclarativeConsumerPartition` gained a `lastCursorCommitFailure` field rather than overloading `DeclarativeConsumerDetail.diagnostic` — `diagnostic` is per-consumer and already multiplexes several unrelated health conditions (unassigned partitions, non-publishable event type), while a cursor commit failure is per-partition; folding it in would have lost both the partition granularity and the ability to tell which condition fired when more than one applies. The new field follows the same empty-string-for-absent convention.
- **Redelivery contract documented** in `management-api.md` beside the new fields: a commit that never lands past the shutdown bound is retried the same way any restart replays a partition — from the last durably committed cursor, so at-least-once delivery holds and the operator's recovery signal is the counter/detail staying non-zero, not a thrown error [design intent — unverified against a live multi-node failure injection; the bound and counter are exercised, the end-to-end redelivery-after-timeout path is not].
