### Fixed (2026-09-15 — #1216: a co-deployed pub/sub topic delivered nothing while reporting success)
- **A bare topic name was namespaced by the SLICE that declared it, not by the blueprint that owns it, and both ends did it to themselves.** `BlueprintNamespace.deriveNamespace(Artifact)` namespaces by whatever artifact it is handed; the publisher (`PublisherFactory.resolveTopicAddress`, via the per-slice loading-context slice id) and the subscriber (`NodeDeploymentState.resolveSubscriptionAddress`, via `sliceKey.artifact()`) each handed it their own. `TopicSubscriptionRegistry` matches on exact string equality, so two distinct slices co-deployed in one blueprint could never agree on an address: `TopicPublisher` returned a SUCCESSFUL promise having delivered nothing, with no log line on either side. `TopicAddressResolver` documented the correct rule the whole time — the producer disagreed with its own docstring, which is why the docstring was never evidence. [verified: `aether/aether-invoke/src/test/java/org/pragmatica/aether/invoke/PublisherFactoryTest.java` `NamespaceAlignment`]
- Both ends now resolve through the owning blueprint, read from the same committed `SliceTargetValue.owningBlueprint` (#698). `OwningBlueprintResolver` supplies the one hop: the deployment FSM holds the KV store and calls it directly, while `PublisherFactory` holds only the slice-id string, so `AetherNode` registers the resolver as a provisioning extension — the same shape and the same reason as `StreamAddressResolver` (#1040), on the adjacent line. Agreement is structural rather than a convention two modules are each asked to remember. [verified: `aether/slice/src/test/java/org/pragmatica/aether/slice/blueprint/CoDeployedTopicAddressingTest.java`]
- **The topic path needs the blueprint IDENTITY, where the stream path needed a published address map.** `BlueprintStreamAddresses` states two reasons a stream alias cannot be re-derived locally; neither holds for topics. A stream's version is not derivable because `StreamConfig` drops the `version` key, whereas a topic carrying an explicit version is written fully namespaced and parsed verbatim, never reaching namespace derivation. An `External` stream deliberately points outside its blueprint; the topic equivalent is again the fully-namespaced spelling, handled by that same verbatim branch. So no second per-blueprint bindings map is published for topics. [verified: `CoDeployedTopicAddressingTest.FullyNamespacedDeclaration`]
- Exactly one fallback remains and it is a different state rather than a weaker one: a slice with **no owning blueprint** — unit tests, programmatic publishers, minimal runtimes — scopes to its own coordinates on BOTH ends, so they still agree. Unlike the stream path there is nothing to refuse, because no second spelling exists to disagree with. [verified: `CoDeployedTopicAddressingTest.NoOwningBlueprint`, `PublisherFactoryTest.NamespaceAlignment.provision_noResolver_bothEndsFallBackToSliceCoordinates`]
- **The old fixture specified the defect rather than missing it.** `publish_coDeployedBareTopic_reachesSubscriber` passed ONE artifact to both ends, which is not co-deployment at all; its sibling `publish_subscriberInDifferentBlueprint_isNotReached` passed two distinct SLICES, asserted non-delivery, and commented that they lived in different blueprints — while the derivation never saw a blueprint, so it asserted the production failure AS CORRECT BEHAVIOUR. Both now use the same two distinct slice artifacts and differ ONLY in owner, holding slice-distinctness constant so the blueprint is the isolated variable. Either test alone is satisfied by the defect; the pair is the instrument.
- **Nothing in the repo exercised a co-deployed topic, which is why this survived.** `examples/notification-hub` — the repo's only multi-slice blueprint — declares three distinct slice artifacts but published over `StreamPublisher`, dodging the bug. It now also publishes a co-deployed topic, from the **emailer** to the **analytics** slice. The direction is load-bearing: this blueprint's own artifact is `notification-hub-notification-service`, so a topic published by THAT slice derives an identical namespace whether scoped to the blueprint or to the slice, and could not tell correct addressing from broken. [mechanism: generated manifests carry `publish.topic.0.topicName=delivery-status` and `reactive.1.category=subscription`]
- The deployment FSM's half was unpinned by anything until now: reverting both of its call sites left all 1224 tests in `aether-deployment` green. A test drives the real LOAD → ACTIVE chain and asserts the `topic-sub/` key submitted to consensus carries the blueprint namespace and not the slice's. [verified: `aether/aether-deployment/src/test/java/org/pragmatica/aether/deployment/node/fsm/NodeDeploymentStateTopicSubscriptionNamespaceTest.java`]
- **TOPIC ADDRESSING IS WIRE-VISIBLE AND THIS RENAMES KEYS.** The address is embedded in the replicated KV key `topic-sub/<namespace>/<name>/<version>/<artifact>/<method>`. Co-deployed topics deliver nothing today and cannot regress. Same-artifact topics work today and, mid-rolling-upgrade, a publisher reaches only subscriber instances registered by nodes of its own addressing version; once the last old node drains, an old-code publisher delivers nothing — silently, still reporting success — self-healing when the upgrade completes. A node upgraded without a graceful drain leaves a `topic-sub/<oldNamespace>/…` entry that new code never removes, inert but persistent. **Durable topics are the sharpest case**: `provisionDurable` shares this resolver and `DurableTopicNames.topicStream` is `"topic:" + address`, so a durable topic's backing ring AND its `.dlq` are renamed, abandoning the old ring and stranding anything undelivered in it. No dual-read bridge is included: a fallback would permanently mask the very divergence this fix removes. [mechanism: `AetherKey.TopicSubscriptionKey.asString`, `PublisherFactory.provisionDurable`]
- The SCHEDULED half of #1216 is NOT addressed here and remains open; the ruling recorded it as an independent defect with no common ancestor past `readReactiveBindingsFromManifest`.
