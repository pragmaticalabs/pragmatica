### Fixed
- On HTTP/1.1, responses of pipelined requests are written in the order of their requests, whichever handler finishes first (#2484), and a response that ends the connection (`Connection: close`, or a refusal that closes it) is written only after every earlier response, so an earlier asynchronous response is no longer lost (#2485). All writes happen on the connection's event loop in request order, including the 101 of an accepted WebSocket upgrade. A finished response is held until every earlier one has been written; the held responses are bounded by the codec's pipeline depth of 128, so the memory held is at most 128 times the largest response body.

### Added
- `HttpServerConfig.responseTimeout` (`withResponseTimeout`, default 60 s, zero or negative disables): a dispatched HTTP/1.1 request whose response has not completed by then is answered 504 in its place and the connection is closed once the earlier responses are written. Without it one handler that never answers stalls every response pipelined behind it. Behind such a handler a 129th unanswered pipelined request still makes the codec close the connection, and the answers held for the earlier requests are discarded with it.
