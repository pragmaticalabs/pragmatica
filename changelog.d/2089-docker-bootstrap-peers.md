### Fixed (2026-10-10 — #2089: a docker-source `aether cluster bootstrap` never formed quorum)
- **Docker nodes were created with an empty `PEERS`.** `DockerComputeProvider` passes `PEERS=ctx.peers().or("")`, bootstrap supplied no peers for a docker source, and nothing pushes peers afterwards, so every node fell back to the peer list baked into the image, which never contained the node's freshly minted id; each aborted at boot with `Self node ... must be in coreNodes` and bootstrap failed at cluster formation with `0/N nodes healthy`. Bootstrap now mints every core node id before provisioning and creates every node of the docker source with the same full `id:host:port` list of the cores (a container's host is its name, which is its node id; port `6000`, the docker provider's default). Workers and spots get the same core list and let the provider mint their ids. The scale-wave docker path and `DockerComputeProvider` are unchanged. [verified: `DockerBootstrapPeersTest`]
- **A docker source that declares management TLS is now refused up front, instead of failing later.** `[operations.tls] auto_generate` defaults to true, and a docker node (created by `docker run` from the image's baked plain-HTTP configuration, with no channel for TLS material) cannot honour it. The VALIDATE phase now refuses such a config with `DockerSourceDeclaresTls`, naming the fix (`[operations.tls] auto_generate = false`), before any container exists. HTTP is used only when the config explicitly disables TLS, never inferred from the source type. `aether cluster init` for a docker target now writes `auto_generate = false` explicitly. Docker nodes serving TLS is a separate, later feature. [verified: `DockerTlsRefusalTest`, `ClusterConfigGeneratorTest`]
- **Several docker sources no longer form several clusters.** Every docker core now receives ONE list naming ALL cores of ALL docker sources (`DockerCores`), and a docker worker-only source gets the same core list. A docker source with cores beside a non-docker source with cores cannot share one reachable list (container names versus addresses), so bootstrap refuses that config with `DockerCoresMixedWithOtherCores` instead of splitting it. The cluster port in the list is handed to the provider explicitly (`cluster_port`), so the two cannot drift. [verified: `DockerBootstrapProvisionPhaseTest`, `DockerTlsRefusalTest`]
- **The CLI could not reach the docker nodes it had created.** A docker node's collected address was its container name (`name:8080`), which does not resolve outside the docker network, so the formation health probe timed out with `Quorum not established: 0/1 nodes healthy` on a cluster that had formed. The docker provider is now told to publish each node's management port (`expose_host_ports`, existing), bootstrap reads the mapped host port back with `docker port`, and the node's address is `127.0.0.1:<mapped port>`. Host ports work on Linux and Docker Desktop alike. `NodeAddress` and `ProvisionedNode` carry that per-node port (absent for cloud and ssh nodes, which keep the configured management port); the formation health and quorum probes, the stored management endpoint and the registered cluster endpoint use it, and a resumed run reads it back from the state file. Inter-node `PEERS` stay container names. [verified: `DockerHostReachabilityTest`]
