### Fixed (2026-10-10 — #2089: a docker-source `aether cluster bootstrap` never formed quorum)
- **Docker nodes were created with an empty `PEERS`.** `DockerComputeProvider` passes `PEERS=ctx.peers().or("")`, bootstrap supplied no peers for a docker source, and nothing pushes peers afterwards, so every node fell back to the peer list baked into the image, which never contained the node's freshly minted id; each aborted at boot with `Self node ... must be in coreNodes` and bootstrap failed at cluster formation with `0/N nodes healthy`. Bootstrap now mints every core node id before provisioning and creates every node of the docker source with the same full `id:host:port` list of the cores (a container's host is its name, which is its node id; port `6000`, the docker provider's default). Workers and spots get the same core list and let the provider mint their ids. The scale-wave docker path and `DockerComputeProvider` are unchanged. [verified: `DockerBootstrapPeersTest`]
- **A docker source that declares management TLS is now refused up front, instead of failing later.** `[operations.tls] auto_generate` defaults to true, and a docker node (created by `docker run` from the image's baked plain-HTTP configuration, with no channel for TLS material) cannot honour it. The VALIDATE phase now refuses such a config with `DockerSourceDeclaresTls`, naming the fix (`[operations.tls] auto_generate = false`), before any container exists. HTTP is used only when the config explicitly disables TLS, never inferred from the source type. `aether cluster init` for a docker target now writes `auto_generate = false` explicitly. Docker nodes serving TLS is a separate, later feature. [verified: `DockerTlsRefusalTest`, `ClusterConfigGeneratorTest`]
- **Several docker sources no longer form several clusters.** Every docker core now receives ONE list naming ALL cores of ALL docker sources (`DockerCores`), and a docker worker-only source gets the same core list. A cluster with ANY docker source must have ALL its sources docker: docker nodes reach each other by container name and the others by address, so no single peer list serves a mix (cores would split, and workers of either kind would boot with a core list they cannot reach), and bootstrap refuses any mix with `DockerCoresMixedWithOtherCores` instead of splitting it. The cluster port in the list is handed to the provider explicitly (`cluster_port`), so the two cannot drift. [verified: `DockerBootstrapProvisionPhaseTest`, `DockerTlsRefusalTest`]
- **The CLI could not reach the docker nodes it had created.** A docker node's collected address was its container name (`name:8080`), which does not resolve outside the docker network, so the formation health probe timed out with `Quorum not established: 0/1 nodes healthy` on a cluster that had formed. The docker provider is now told to publish each node's management port (`expose_host_ports`, existing), bootstrap reads the mapped host port back with `docker port`, and the node's address is `127.0.0.1:<mapped port>`. Host ports work on Linux and Docker Desktop alike. `NodeAddress` and `ProvisionedNode` carry that per-node port (absent for cloud and ssh nodes, which keep the configured management port); the formation health and quorum probes, the stored management endpoint and the registered cluster endpoint use it, and a resumed run reads it back from the state file. Inter-node `PEERS` stay container names. [verified: `DockerHostReachabilityTest`]
- **Docker nodes booted with a different cluster secret than the one the CLI authenticated with.** The CLI mints (or resumes) its own cluster secret and derives its bootstrap admin key from it; cloud nodes receive that secret in their user-data, but a docker node received only whatever `AETHER_CLUSTER_SECRET` the provider forwarded from the CLI's own environment (nothing, or an unrelated value). Every node then answered the CLI's quorum probe with "Invalid API key" and `--wait` ran to its timeout on a healthy cluster. Bootstrap now builds the docker provider with a host environment that answers `AETHER_CLUSTER_SECRET` from `ctx.clusterSecret()` and every other name from the process environment, so the secret the CLI holds is the only one a docker node receives. An `AETHER_CLUSTER_SECRET` in the operator's shell is ignored for bootstrap. No operator step is added. [verified: `DockerBootstrapSecretTest`]
- `aether cluster destroy` on a docker cluster now reaches the nodes through their published host ports (serving node identified by the endpoint's published port; sibling fallback uses each recorded `host:port` as is), and no longer reports success with exit 0 over failed drain/shutdown operations: it refuses before deleting anything and names `--force-undrained`, which proceeds and lists the nodes that were not drained.
- `docker port` is consulted at destroy only for a cluster whose bootstrap ledger records docker containers, never merely because the endpoint is on loopback. IPv6 hosts are bracketed in the persisted `host:port` form (`[::1]:38915`) and parsed back; a bare IPv6 address carries no port.
- The refusal over failed drain/shutdown operations applies to every provider, cloud included, and means REAL failures (unreachable node, timeout, 5xx, any refusal other than the budget): `--force-undrained` is the operator's explicit acknowledgement that VMs may be deleted undrained.
- A drain or shutdown refused by the cluster's disruption budget (HTTP 409 "Disruption budget exceeded") is no longer a failure: a destroy can never drain a majority of the cores, so those cores are reported as held for quorum, are not shut down, and are removed with their VMs. The summary prints `drained N, held for quorum M (names), failed K`; exit 0 when K is 0. The budget is recognised by status 409 plus its exact phrase, because the response carries no structured code.
- `aether cluster bootstrap --wait --timeout N` now caps node-health and quorum-formation waits at N seconds too (never raising them above the config), instead of bounding only the final status poll. The cap is a runtime setting and never enters the hashed config, so a timed-out bootstrap can be resumed with a longer `--timeout` or none; without `--timeout`, those waits use `[operations.timeouts]` as before. The refusal message no longer ends with a stray `; .`.
- `aether cluster destroy` reconciles the cluster's node list against the nodes recorded in the bootstrap ledger. A node the cluster did not list (the lifecycle list is the leader's view of its peers and can omit one) is named as "not listed by the cluster — removed without drain" (docker nodes by container name; otherwise counted with the ledger's labels), and the summary counts drained + held + failed + not listed against the ledger total. An unlisted node alone does not refuse the destroy.
