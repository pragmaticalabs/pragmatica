### Fixed (2026-11-18 — #3348: an operator drain of the current leader gets a typed refusal)
- **`POST /api/v1/nodes/drain/{id}` for the current leader answers `409 Conflict`: the node is the current leader or the node handling the request, such a node is not drained, and leadership must move first** (Refs #3348). Before, the answer was `404 Node lifecycle not found` on every node, because the route reads the receiving node's reported lifecycle states and the leader has no row for itself; that 404 was the only thing between the operator and a half-applied drain. The refusal covers the current leader and the node handling the request (a request for this route is forwarded to the believed leader, so a target equal to the handling node is a just-elected leader that has not yet applied its election), decided from state the receiving node holds, and it runs before the readiness lookup, the budget read and any dispatch. The product has no step-down command, so the text names what exists: stop the leader's process from outside the cluster (the service manager or the container runtime), the cluster elects another leader, then drain the node. Drain followed by a hand-over is not part of this change. With no leader known to the receiving node the answer is unchanged. `POST /api/v1/nodes/shutdown/{id}` of the current leader is refused the same way, with its own text (it half-applied exactly as a drain did); a shutdown of any other node is unchanged. `aether nodes drain` and `aether nodes shutdown` print the server's refusal text. `aether cluster destroy` recognises these two refusals by their shared wording and holds the leader (reported as `leader held`, no shutdown sent, not a failure); its instance is deleted by the cloud cleanup like a node held for quorum.
