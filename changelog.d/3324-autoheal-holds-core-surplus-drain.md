### Fixed (2026-11-17 — #3324: auto-heal disabled still drained a surplus CORE member)
- **With auto-heal disabled, a surplus core member was still drained** on the cluster's own initiative (the membership reconciler's surplus drain and the retirement of cores excluded from the voter set read no switch), while worker and community changes were held.
- Both core surplus drains now ask the same hold the worker and community paths ask (`ClusterTopologyManager.scalingHeld`, subject `core`, held on the committed core count recorded at disable). A held surplus is reported by the existing `auto-heal-scaling-held` warning and its resume by `auto-heal-scaling-resumed`; a core count committed while disabled is explicit intent and releases the hold. [mechanism: `LeaderReconciler.computePeersToDrain` and `TopologyAssembly.drainSurplusCores` return no victim while `scalingHeld("core")` holds; pinned by unit tests `LeaderReconcilerTest.AutoHealCoreSurplusHold`, `SurplusCoreRetirementHoldTest`, `ClusterTopologyManagerWorkerReconcileTest.scalingHeld_core_followsTheCommittedCoreCount`, not by a live multi-node run]
- An operator-directed drain (`POST /nodes/drain`, `POST /nodes/replace`, upgrade runs) does not pass through either site and is unaffected. [mechanism: neither path calls the gated methods]
- Upgrade note: an auto-heal disable recorded before this change carries no `core` value, so it does not hold the core surplus until auto-heal is disabled again. [mechanism: an absent recorded value differs from the committed one, which releases the subject]
