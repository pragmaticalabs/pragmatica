### Fixed (2026-11-09 - #2944: a transient fence conflict on a management write answered 500)
- **A management write refused by the leader's conditional-commit fence as a transient CONFLICT (`Hierarchy state changed before conditional commit`, nothing written) answered HTTP 500, and the CLI did not retry.** Typical trigger: `aether cluster topology auto-heal disable` right after cluster start, while the config seed is still settling.
- The leader-side toggle (`setAutoHealEnabled`, route `POST /cluster/topology/auto-heal/{enable,disable}`) now retries the CONFLICT itself, 5 attempts in all with a 50 ms x attempt pause, re-reading the record and the cluster configuration each attempt; `setDesiredCount` (no route calls it) keeps its 3 re-reading attempts and gains the same pause.
- Every other management write that commits through a fence, by route: slice scale, A/B test start/conclude/rollback and rolling-update deployment use `SliceTargetFence` (first submission plus 5 rebuilds); an exhausted or refused fence write used to reach the client raw (ab-test and rolling update: a 500) and now answers 409 (503 when no core leader is committed), with the retry hint on the exhausted case. Clear-unconfirmed-termination is not retried; a fence conflict on its delete is reported as such (409, `Conflicted`, no automatic retry because a retry could meet a later incarnation's mark) instead of as `Changed`. Parked-community-placement clear and cluster-config apply/scale/upgrade report a refused commit as 409 and are not retried.
- When the bound is exhausted the management API answers **409 Conflict** (`Refusal.CONFLICT` is listed in `ManagementStatus`) with the detail `...nothing was written, retry the request`; any other refusal (for example INACTIVE) is unchanged and is not retried. The CLI POST retries a 409 carrying that hint up to 4 requests in all (250 ms x attempt pause); other 409s (a slice-floor breach, an already-applied state) are returned at once.
