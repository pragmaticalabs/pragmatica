### Fixed (2026-10-09 — #1996: QUIC offline buffer delivers request frames after their caller gave up)
- **What was wrong:** a request frame sent to a peer with no live connection sat in that peer's offline buffer with no time limit and was delivered when the peer reattached, possibly minutes after its caller had timed out, failed or retried elsewhere, so the receiver executed work whose answer nobody collected. This covered slice invocation (including the failover attempts and fire-and-forget calls), HTTP forward, stream publish and read forward, stream replication and `ForwardApply`.
- Each of those request frames now carries the wait its caller just started, as a sender-side lifetime handed to the transport (`ClusterNetwork.send(peer, message, lifetime)`); no wire format changes. The buffer drops the frame at the reattach flush once that lifetime has passed, and it is never held longer than `timeouts.cluster.offline_buffer_cap` (new, default `30s`). Every frame without a caller deadline (consensus, DHT, responses, a fire-and-forget invocation) goes through plain `send`/`broadcast`, which the transport bounds by the cap alone, so nothing it buffers is held for ever. The lifetimes are: invocation, the correlation wait; HTTP forward, the hop timeout; stream forward, the publish or read timeout; replication, the 5s ack wait (replication does not retransmit, so that wait is its only deadline); `ForwardApply`, its 30s wait. [verified: `QuicClusterNetworkOfflineTtlTest`, `PeerStateTest`, `InvocationDeadlineCapTest`, `HttpForwarderDeadlineTest`, `StreamForwardOfflineTtlTest`, `ReplicationOfflineTtlTest`, `ForwardingClusterNodeOfflineTtlTest`]
- A dropped frame is operator-visible: the `quic_offline_expired_total` transport metric, a WARN, and an `offline-frames-expired` operator warning in the event stream per peer (throttled to one a minute per peer; it carries the number of frames and their message types). It is a point event with no recovery event. [verified: `ClusterEventAggregatorTest`]
- [unverified: that dropping a stale DHT or consensus frame after the cap is harmless rests on code reading (Rabia re-broadcasts and re-syncs: `RabiaEngine.java:1148`; DHT operations are version-fenced and anti-entropy repairs), not on a multi-node run. SWIM never reaches this buffer (UDP, own transport). A frame buffered for a peer that never reattaches is held until the buffer's 10,000-entry bound evicts it and is never delivered, but is not counted as expired.]
