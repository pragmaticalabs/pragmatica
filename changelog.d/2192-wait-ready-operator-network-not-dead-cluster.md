### Fixed (2026-10-18 — #2192: wait_for_cluster_ready fast-fail cannot tell operator-network loss from a dead cluster)
- **A ~30 s receive blackout on the operator host was reported as a dead cluster and turned the suite red against a healthy cluster.** When no core answered `/health/live`, `wait_for_cluster_ready` failed fast with "cluster appears down". Before failing fast it now probes a reference endpoint outside the cluster (cloud runs: `HCLOUD_API`, the Hetzner API; `OPERATOR_REFERENCE_URL` overrides, probe bounded by `OPERATOR_REFERENCE_TIMEOUT_S`, default 3 s): if that is unreachable too, it logs `operator network unavailable` and falls through to the normal bounded `wait_for`, which passes once the link is back and times out if it never is. Any HTTP answer from the reference counts as a working link, so a genuinely dead cluster with the operator's network up still fails fast with the old message. If the reference answers, one more core sweep runs before the cluster is called dead, so a link that recovered between the first sweep and the probe does not fast-fail a healthy cluster. **Still unfixed:** `--env remote` (ssh) and docker with a remote `TARGET_HOST` have no default reference, so there #2192 is fixed only when `OPERATOR_REFERENCE_URL` is set and otherwise fails fast as before (docker on the operator's own host or LAN is not affected by an operator link loss). The optional publish-ack check from the ticket is not part of this change. `[verified: aether/tests/integration/test/test-wait-ready-operator-network.sh]`
