### Added (2026-10-15 — #2204: deployment state machine rewrite, phase 3 tracer PR C: the wiring, the engine marker, T and E-01 on FSM2)
- **The FSM2 deployment engine can now run in a cluster, selected by a test-harness switch only.** `DeploymentWiring` is the one place every engine-dependent hook is bound. Under LEGACY (the default, and the only choice a deployment has: there is no TOML key in this PR) each hook keeps its legacy target and a checked-in baseline pins the table; under FSM2 each legacy hook is a counted drop (`aether_deployment_fsm2_dropped_total{point}`) and the KV routes, the leader and membership inputs, the self-ready signal and the stop sequence feed the two FSMs. A worker never receives an FSM2 system.
  [verified: `aether/node/src/test/java/org/pragmatica/aether/node/DeploymentWiringBootTest.java`, `aether/node/src/test/java/org/pragmatica/aether/node/deployment/Fsm2SystemTest.java`, `aether/node/src/test/java/org/pragmatica/aether/node/deployment/Fsm2RoutesTest.java`]
- **A committed engine marker keeps a node of one engine out of a cluster of the other.** `DeploymentEngineKey` (durable cluster state, wire pins 2160-2162) is minted with the cluster lineage in one leader transaction that expects both keys absent and is witnessed by the committed leader read on that pass. A node whose configured engine disagrees with the committed marker, or an FSM2 node that finds an incarnation with no marker, logs one `deployment-engine-mismatch` warning with the evidence and the recovery, runs no deployment activation, and exits when the window ends if the mismatch still stands. The restore arms (a pre-phase-3 backup removing the minted marker) and the worker arms are not built in this PR. The window (twice the leader-election timeout) is a guess pending the E-14 measurement.
  [verified: `aether/node/src/test/java/org/pragmatica/aether/node/EngineMarkerMintTest.java`, `aether/node/src/test/java/org/pragmatica/aether/node/deployment/EngineMarkerGuardTest.java`]
- **Under FSM2 a blueprint publish opens the apply record in the same batch** (`DeploymentApplyKey`, with `previous` captured as the same-id overwritten blueprint or else the blueprint of the committed target's prior version), and the publish is not confirmed until the record has landed, been closed by this attempt's terminal outcome, or been superseded. Under LEGACY the batch is unchanged.
  [verified: `aether/node/src/test/java/org/pragmatica/aether/deployment/cluster/BlueprintApplyRecordTest.java`]
- **The deployment FSMs' warning codes are catalogued** in `OperatorWarningCode` (subsystem `deployment`, level WARNING), so the translator publishes them as operator events; a code an FSM raises without an entry fails a source-scanning test, and a code outside the catalogue still takes the logged-and-counted unmapped path.
  [verified: `aether/node/src/test/java/org/pragmatica/aether/node/deployment/FsmWarningCatalogueTest.java`]
- **Fixed: a `close()` racing a `start()` could shut an FSM down on the caller's thread while its consumer was being created.** `FsmMailbox.retireIfConsumerless()` decides under the monitor `start()` holds, and a retired mailbox never starts a consumer.
  [verified: `aether/aether-deployment/src/test/java/org/pragmatica/aether/deployment/wiring/CloseAndOverrunProbeTest.java`]
- **Named limits.** The adapter does not execute `PREPARE_TEARDOWN`, `DEACTIVATE`, `UNLOAD`, `FORCED_CLEANUP` or `NOTIFY_CONFIG` (a step that would need one fails loudly), so the config hook (`ConfigChanged`) stays a counted drop until `NOTIFY_CONFIG` is wired. The tracer fault in `ActivationWriteFault` is inert unless a test arms it. Reader (c) of the #1117 tracer is not determinable under FSM2 because the stream-consumer reader is still fed by the legacy deployment map (phase 4a). The boot incarnation handed to the leader's admission is the SWIM high-water, not the peer's own boot value `[design intent — unverified]`.
