### Fixed (2026-09-04 — #841: ALL-mode scheduled-task counters shared one cluster-wide row instead of one per node)

- **An `execution_mode = "all"` task's `totalExecutions`/`consecutiveFailures`/etc. all accumulated into a single KV entry, even though every quorum member runs its own independent timer for the same task** — two nodes racing a read-modify-write against that one entry could lose one node's update, and the reported total no longer corresponded to any single node's real activity. `ScheduledTaskStateKey` now carries an optional node component: ALL-mode reads and writes are keyed by `ctx.self()`, so each node owns its own row; `execution_mode = "single"` is unchanged, since only the leader ever executes it
  [mechanism: `ScheduledTaskManager.TaskOps.stateKeyFor(ctx, task)` branches on `task.executionMode()`; pinned by `aether/aether-invoke/src/test/java/org/pragmatica/aether/invoke/ScheduledTaskManagerTest.java#MultiNodeStateIsolation` — two manager instances, distinct node ids, sharing one backing map in-process, asserting neither node's count is lost or overwritten by the other; component-level, not a live multi-node run].
- **`GET /api/v1/scheduled-tasks/executions-by-node/...` reported the task's `registeredBy` node as the sole executor for every mode** (an RC1 stub, count = `totalExecutions`). It now aggregates real per-node rows by scanning the live `KVStore` for node-scoped state entries, one row per node that has actually executed, sorted by `nodeId`
  [mechanism: `ScheduledTaskRoutes.buildExecutionsByNode`; pinned by `ScheduledTaskRoutesExecutionsByNodeTest.java#MultipleNodes` and `#WithState`].
- **Rolling-upgrade note:** a pre-#841 global (non-node-scoped) state entry is excluded from the new per-node scan rather than misread as belonging to some node, so an ALL-mode task's per-node counters restart at zero after upgrading instead of continuing from the old shared total
  [mechanism: the scan filters on `key.node().isPresent()` and task identity; pinned by `ScheduledTaskRoutesExecutionsByNodeTest.java#InvalidEntriesExcluded`, which seeds both a pre-#841 global entry for the target task and a node-scoped entry for a different task and asserts both are excluded].
- **`GET /api/v1/scheduled-tasks` (tasks-list summary) and `GET /api/v1/scheduled-tasks/state` (single-task state) also read the unscoped, single-row `ScheduledTaskStateRegistry` mirror regardless of execution mode**, reporting zero/stale totals for an ALL-mode task on the two surfaces `executions-by-node` did not cover. Both now aggregate the same per-node rows via the same `KVStore.forEach` idiom (`totalExecutions`/`skippedOverlaps` summed, `consecutiveFailures`/`lastExecutionAt` max, `nextFireAt` min, `lastFailureMessage`/`updatedAt` from whichever row is freshest by `updatedAt`) [design intent — unverified beyond the field-level reasoning; no review ruling pins these five combine choices specifically, only the two additive fields]
  [mechanism: `ScheduledTaskRoutes.toSummary`/`buildStateResponse` branch on `ExecutionMode.ALL` into `aggregateAllModeState`/`combineNodeStates`; pinned by `ScheduledTaskRoutesAllModeAggregationTest.java` (`ListSummary`, `SingleTaskState`), including a global-shaped-key-exclusion case per surface added after an adversarial mutation probe found the first pass of these tests didn't catch a dropped node-presence filter].
- Docs updated: `aether/docs/reference/management-api.md` (`/trigger` 409 response, per-node aggregation and rolling-upgrade note on all three read surfaces) and `aether/docs/slice-developers/resource-reference.md` (Execution State, Operational Controls).
- **Known caveat, not addressed by this change:** `POST /api/v1/scheduled-tasks/inject` (dev/test-only, `AETHER_INSECURE_DEV_MODE` gated) still writes the pre-#841 unscoped key for every execution mode. For `single`-mode tasks this is unchanged (still races the leader's automatic fire and `/trigger` on that same key). For `all`-mode tasks, the write no longer collides with automatic fires (which now use per-node keys) but is now excluded from all three read surfaces above by the same node-presence filter — an `/inject` call on an `all`-mode task returns its own advancing counters but they are permanently invisible on the Management API. Worth its own ticket to key `/inject` by `ctx.self()` for `all`-mode tasks, mirroring the automatic path; not folded into this change.
