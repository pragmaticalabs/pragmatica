### Added (2026-10-18 — #1469: a scheduled task that does not fire can now say why, and a Dormant scheduler is no longer silent)
- **`GET /api/v1/scheduled-tasks` tells apart the causes a bare `activeTimers: 0` conflated.** The response carries `schedulerState` (`DORMANT`, `FOLLOWING`, `LEADING`, `STOPPED`) and each task carries `eligibleHere` and `ineligibleReason`: `SCHEDULER_DORMANT`, `SCHEDULER_STOPPED`, `PAUSED`, `UNKNOWN_MODE`, `NOT_LEADER`, `NOT_HOSTING`, `DRAINING`, or `TIMER_ARM_FAILED` (eligible in every other respect, no timer armed). The filtered `/{section}` response carries `schedulerState` too. All of it describes the node that answers. The reasons mirror `TaskOps.eligible` term for term. `[verified: aether/aether-invoke/src/test/java/org/pragmatica/aether/invoke/ScheduledTaskManagerTest.java IneligibilityReasons, aether/node/src/test/java/org/pragmatica/aether/api/routes/ScheduledTaskRoutesOrderingTest.java Eligibility]`
- **A Dormant scheduler logs.** The `Dormant` state declared a logger and never used it, and the state machine does not run the initial state's `onEntry`, so a booting or quorum-less scheduler produced no line anywhere. It now logs a WARN when constructed and whenever it re-enters Dormant, and the quorum notification handler logs every notification (WARN when it is not `ACTIVE`, INFO otherwise, including stale ones it ignores).
- Not part of this change: the Dormant state is not independently reachable today (the issue's own bound), so no new transition is introduced.
