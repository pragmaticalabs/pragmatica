### Fixed (2026-09-14 — #279: the cache interceptor failed closed, `max_entries` capped nothing, and a shared section captured one method's `@Key` for every method)
- **(1) Fail-closed.** `CacheMethodInterceptor.cacheAside` chained `cache.get(key).flatMap(…)` and `writeThrough` chained `cache.put(…)`, so a backend failure — a DHT outage — failed the business call: a cache outage was a service outage. A backend `get` failure now reads as a **miss** (the method runs, its value is returned) and a `put` failure is absorbed (the completed write's result stands). Both are logged at DEBUG, deliberately: a per-call WARN during an outage would be an unbounded log on the hottest path (#718's measured lesson), and the outage is visible on the backend's own side. `WRITE_BACK`/`WRITE_AROUND` were already fire-and-forget. [verified: `CacheFailOpenTest` (`aether/resource/interceptors`) — `cacheAside`/`readThrough` with a backend whose `get` fails: method called once, value returned, backend consulted once; `writeThrough` with a failing `put`: value returned, put attempted; control: a failing METHOD still fails. Red at the base with `must be fail-open, got get: backend down`; reverting the interceptor reddens exactly these 3]
- **(4) Unbounded `InMemoryCache`.** `put` evicted only EXPIRED entries when full and then inserted regardless, so `max_entries` bounded nothing for a hot cache. The store is now an access-ordered `LinkedHashMap` evicting its least-recently-used entry on overflow (expired entries go first), guarded by the instance monitor. [verified: `InMemoryCacheTest$Bound` — 10 puts into a cap of 3 with nothing expired leave ≤ 3 present (was 10); the touched entry survives and the untouched one is the victim; an overwrite at the bound evicts nothing. Reverting `InMemoryCache` reddens the first two; the pre-existing 8-thread `ConcurrentAccess` test still passes]
- **(2) Shared-section `@Key` capture.** The generator deduplicated interceptor provisions by `(type, config)` and `findKeyInfoForInterceptor` returned the FIRST matching method's extractor, so two `@Key` methods under one config section shared one instance keyed by the first method's request type — a `ClassCastException` on the second method's first call, or a wrong key when the types coincided. A key-bearing method now gets its own provision (`provisionKey` = `(type, config)` + method name), carrying its own extractor; key-less methods keep sharing one instance per section, because sharing is the point for rate limits and circuit breakers. What is shared underneath — the named cache or idempotency store — is shared by the factory's `NamedResourceRegistry` (#898), not by the generated variable, so per-method instances do not duplicate caches. [verified: `SliceProcessorTest#should_provision_a_key_bearing_interceptor_per_method_when_the_config_section_is_shared` (`jbct/slice-processor`) — two `@Key` methods under `cache.shared` generate two `provide(MethodInterceptor.class, "cache.shared", …)` calls with `GetUserRequest::userId` AND `GetOrderRequest::orderId`; red at the base (second extractor absent); reverting the generator reddens it]. No envelope bump: `ENVELOPE_FORMAT_VERSION` is frozen at 1000 until GA (owner ruling on #386). [mechanism: root `mvn clean install -DskipTests` compiles every regenerated factory in the tree — see the report for the reactor result]
- **(3) DHT TTL and cross-node invalidation — NOT fixed here, stated.** `DHTClient` has no expiry primitive (`put(byte[], byte[])` only; repo grep for ttl/expire in `integrations/dht`: none), so honouring `ttl_seconds` on `DISTRIBUTED` is a DHT feature, not an interceptor fix; cross-node invalidation for `TIERED` is owner-deferred post-GA (ticket comment 2026-08-26). The doc's `TIERED` row already carried the gap; the `ttl_seconds` and `max_entries` rows now say which store each governs, and the `DISTRIBUTED` row states the fail-open behaviour.
