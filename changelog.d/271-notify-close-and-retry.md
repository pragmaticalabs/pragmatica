### Fixed (2026-09-13 — #271: `@Notify` leaked the SMTP event loop on release and retried permanent failures)
- **R8 — `NotificationSenderFactory.close` was a no-op override** (`return Promise.unitPromise()`), so the `SmtpClient` — which owns a Netty `EventLoopGroup` that only its own `close()` shuts down — was never closed on a slice unload. `SmtpNotificationSender` now implements `AsyncCloseable`, forwarding to `SmtpClient.close()`, and the factory override is **removed**: `ResourceFactory`'s default dispatch (#891) reaches the SMTP sender through `AsyncCloseable` and names the HTTP sender's lack of a close convention (DEBUG) rather than hiding both behind one silent success. [verified: `NotificationSenderFactoryCloseTest#close_smtpSender_closesTheSmtpClientExactlyOnce` (`aether/resource/notification`) — counts `SmtpClient.close()` calls through `factory.close`; 0 before, 1 after; restoring the override reddens it]
- **The HTTP sender still has nothing to close, and that is now visible rather than hidden.** `HttpEmailSender.httpEmailSender(config)` builds a `JdkHttpOperations` over `HttpClient.newHttpClient()` and exposes no close; `JdkHttpOperations` implements neither convention. Filed separately (ticket draft in the report) — it is an `integrations/http-client` defect, not this factory's. [unverified: retention of the JDK client's selector thread on the HTTP path — not measured here]
- **R9 — retry was indiscriminate.** Both senders carried their own copy of a retry loop (`sendWithRetry`/`nextDelay`/`delayThen`, a raw virtual thread per sleep) that consulted nothing about the cause. Both now retry through core `Retry` (`RetryConfig.retry()` builds the exponential strategy on the shared scheduler), which stops on a terminal cause, and **the backends' own error types now carry the classification**: SMTP `AuthFailed`, `TlsFailed`, `ProtocolError` are `Cause.Terminal`; `Rejected` gained the server's reply `code` and is terminal for 5yz (RFC 5321 §4.2.1 — permanent negative completion), transient for 4yz; HTTP `AuthError` and `VendorNotFound` are terminal; `RequestFailed` is terminal for 4xx except 408 and 429. 5xx, connection failures and timeouts keep the full schedule. [verified: `NotificationRetryClassificationTest` — 13 tests counting attempts at a stub backend with `maxAttempts = 3`: permanent causes → 1 attempt, transient → 3; the transient cases are the control and pass before and after. Red before the fix: `AuthFailed`, `TlsFailed`, `AuthError`, `RequestFailed(400)`, `VendorNotFound` all ran 3 attempts. Mutations: reverting the senders to the old loops reddens all six permanent pins plus the close pin; removing the SMTP classification reddens exactly the three SMTP permanent pins; removing the HTTP classification reddens exactly the three HTTP permanent pins]
- `SmtpError.Rejected` is now `Rejected(int code, String message)`. The only constructors are `SmtpSession`'s four refusal sites, which already had the code in hand; nothing outside `integrations/net/smtp` pattern-matched it. [mechanism: repo-wide grep, zero external references]
- The final error a caller sees is still `NotificationError.DeliveryFailed`; its message now carries the cause without an attempt count, because `Retry` logs the count itself (one WARN per exhausted or terminal call, per #718's logging contract). [verified: `NotificationRetryClassificationTest$Smtp#exhaustedTransientFailure_surfacesAsDeliveryFailed`]
- **R10 — the example bound nothing.** `examples/notification-hub/notification-emailer/src/main/resources/resources.toml` declared `[notification.smtp]`, which the binder never derives (`Option<SmtpConfig> smtpConfig` reads `smtp_config`, #671) and which binds silently to no config; its NOTE still said the section was gated on #671, which landed. Renamed to `[notification.smtp_config]`, the auth example to `[notification.smtp_config.auth]`, the stale note removed. [verified: `NotificationConfigBindingTest#config_smtpBackend_staleDocSectionName_silentlyBindsEmptyNotAnError` is the pre-existing pin that the old spelling binds nothing; `#config_smtpBackend_bindsNestedSmtpAndRetryFromDocumentedToml` pins the new one]. The `username`/`password`/`pool_size`/`helo_hostname` keys the ticket cites were already gone from the example at the base.
- `resource-reference.md`'s `@Notify` retry section now states which failures are not retried, and `DeliveryFailed`'s row no longer claims every failure exhausted the schedule.
- **What is NOT verified.** [unverified: a real Netty `EventLoopGroup` observed terminated after a deployed slice's unload — `SmtpClientImpl.close()` (`shutdownGracefully`, unchanged) is reached, which the counting pin shows; the production measurement of the release path is #895.]
