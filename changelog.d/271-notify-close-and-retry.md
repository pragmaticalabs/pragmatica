### Fixed (2026-09-13 — #271: `@Notify` leaked the SMTP event loop on release and retried permanent failures)
- **R8 — `NotificationSenderFactory.close` was a no-op override** (`return Promise.unitPromise()`), so the `SmtpClient` — which owns a Netty `EventLoopGroup` that only its own `close()` shuts down — was never closed on a slice unload. `SmtpNotificationSender` now implements `AsyncCloseable`, forwarding to `SmtpClient.close()`, and the factory override is **removed**: `ResourceFactory`'s default dispatch (#891) reaches the SMTP sender through `AsyncCloseable` and names the HTTP sender's lack of a close convention (DEBUG) rather than hiding both behind one silent success. [verified: `NotificationSenderFactoryCloseTest#close_smtpSender_closesTheSmtpClientExactlyOnce` (`aether/resource/notification`) — counts `SmtpClient.close()` calls through `factory.close`; 0 before, 1 after; restoring the override reddens it]
- **The HTTP sender still has nothing to close, and that is now visible rather than hidden.** `HttpEmailSender.httpEmailSender(config)` builds a `JdkHttpOperations` over `HttpClient.newHttpClient()` and exposes no close; `JdkHttpOperations` implements neither convention. Filed separately (ticket draft in the report) — it is an `integrations/http-client` defect, not this factory's. [unverified: retention of the JDK client's selector thread on the HTTP path — not measured here]
- **R9 — retry was indiscriminate.** Both senders carried their own copy of a retry loop (`sendWithRetry`/`nextDelay`/`delayThen`, a raw virtual thread per sleep) that consulted nothing about the cause. Both now retry through core `Retry` (`RetryConfig.retry()` builds the exponential strategy on the shared scheduler), which stops on a terminal cause, and **the backends' own error types carry the classification, derived from the reply code on every command**: every SMTP refusal record — `Rejected` (greeting, MAIL FROM, RCPT TO, DATA, message), `ProtocolError` (EHLO), `TlsFailed` (STARTTLS), `AuthFailed` (AUTH) — carries the server's reply `code` through one `SmtpError.ReplyRefused` rule: **a 4yz reply is transient; everything else refused is terminal** — 5yz (RFC 5321 §4.2.1), and a 3yz where a completion was expected (a `334` challenge this client cannot answer, a `354` outside DATA), which the session no longer mistakes for success (`isSuccess` is 2yz only). RFC 4954 `454 Temporary authentication failure` and RFC 3207 `454 TLS not available` are 4yz and retried. `ConnectionFailed` (transport, no reply) and `Timeout` are `Cause.Transient`. HTTP: `AuthError` and `VendorNotFound` are terminal; `RequestFailed` is terminal for 4xx except 408 and 429 and transient otherwise. `NotificationError.DeliveryFailed` now carries the backend's last cause (`Cause.Wrapped`) and answers `isTerminal()`/`isTransient()` from it, so a caller's own retry policy can tell a terminal `550` from an exhausted `4yz` schedule. [verified: `NotificationRetryClassificationTest` — 19 tests counting attempts at a stub backend with `maxAttempts = 3`: 5yz/terminal → 1, 4yz/transient → 3, at every SMTP site; `DeliveryFailed` after a `550` is terminal and after an exhausted `451` transient. `SmtpReplyCodeClassificationTest` — the REAL `SmtpClient`+`SmtpSession` against a scripted loopback server counting accepted connections: `454`@AUTH → 3, `421`@EHLO → 3, `454`@STARTTLS → 3, `421`@greeting → 3, `451`@MAIL FROM → 3; `535`@AUTH → 1, `554`@STARTTLS → 1, `554`@greeting → 1, `550`@MAIL FROM → 1. `TransientClassificationTest` in `integrations/net/smtp` and `integrations/email-http` asserts `isTransient()`/`isTerminal()` directly on every record, including the 3yz rows — the sender-level pins read `isTerminal()` only, so the transient half of the rule is pinned there and nowhere else. Mutations: making `ReplyRefused` unconditionally terminal reddens exactly the nine 4yz pins; returning `isSuccess` to `< 400` reddens the 3yz pin]
- **A TLS setup failure fails CLOSED.** `SmtpClientImpl.buildInsecureSslContext` used to log a failed `SslContextBuilder` and carry on WITHOUT a context; in STARTTLS mode the session then skipped STARTTLS and sent AUTH PLAIN in cleartext, and the delivery SUCCEEDED (review of #1075, BLOCKING-1 — probed with the real client; round 2 had documented the opposite and pinned it with a stub, the fixture-tell). `send()` now builds the context first when the mode requires one, and a failure fails the promise with terminal `TlsSetupFailed` before any connection is opened. [verified: `SmtpClientFailClosedTest#startTlsMode_tlsContextCannotBeBuilt_failsTerminal_beforeAnyConnection` (`integrations/net/smtp`) — the real client with a TLS-context supplier that fails, against a scripted server that records every command: the send fails with terminal `TlsSetupFailed`, the server accepts zero connections, no `AUTH` reaches the wire; control `#startTlsMode_withAContext_sendsStartTlsAfterEhlo` shows `STARTTLS`, not `AUTH`, after EHLO. Mutation (context failure swallowed, round-2 shape): the server answers an `AUTH PLAIN` sent in cleartext — `AuthFailed[code=220, message=… 220 go ahead]` — which is the reviewer's probe reproduced]
- **A malformed reply or a command timeout closes the channel** with the promise; before, only a reply-code refusal did, and under retry the open sockets stacked three per send (review of #1075, SF-2). `SmtpSession.onException` and the new `onTimeout` go through `failSession`, which closes. [verified: `SmtpClientFailClosedTest#malformedReply_failsThePromise_andClosesTheChannel`, `#commandTimeout_failsThePromise_andClosesTheChannel` — the scripted server holds the socket and reports whether the client closed it; both red under mutation (promise failed without `failSession`)]
