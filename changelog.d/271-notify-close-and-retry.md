### Fixed (2026-09-13 — #271: `@Notify` leaked the SMTP event loop on release and retried permanent failures)
- **R8 — `NotificationSenderFactory.close` was a no-op override** (`return Promise.unitPromise()`), so the `SmtpClient` — which owns a Netty `EventLoopGroup` that only its own `close()` shuts down — was never closed on a slice unload. `SmtpNotificationSender` now implements `AsyncCloseable`, forwarding to `SmtpClient.close()`, and the factory override is **removed**: `ResourceFactory`'s default dispatch (#891) reaches the SMTP sender through `AsyncCloseable` and names the HTTP sender's lack of a close convention (DEBUG) rather than hiding both behind one silent success. [verified: `NotificationSenderFactoryCloseTest#close_smtpSender_closesTheSmtpClientExactlyOnce` (`aether/resource/notification`) — counts `SmtpClient.close()` calls through `factory.close`; 0 before, 1 after; restoring the override reddens it]
- **The HTTP sender still has nothing to close, and that is now visible rather than hidden.** `HttpEmailSender.httpEmailSender(config)` builds a `JdkHttpOperations` over `HttpClient.newHttpClient()` and exposes no close; `JdkHttpOperations` implements neither convention. Filed separately (ticket draft in the report) — it is an `integrations/http-client` defect, not this factory's. [unverified: retention of the JDK client's selector thread on the HTTP path — not measured here]
- **R9 — retry was indiscriminate.** Both senders carried their own copy of a retry loop (`sendWithRetry`/`nextDelay`/`delayThen`, a raw virtual thread per sleep) that consulted nothing about the cause. Both now retry through core `Retry` (`RetryConfig.retry()` builds the exponential strategy on the shared scheduler), which stops on a terminal cause, and **the backends' own error types carry the classification, derived from the reply code on every command**: every SMTP refusal record — `Rejected` (greeting, MAIL FROM, RCPT TO, DATA, message), `ProtocolError` (EHLO), `TlsFailed` (STARTTLS), `AuthFailed` (AUTH) — carries the server's reply `code` through one `SmtpError.ReplyRefused` rule: `isTerminal = code >= 500`, `isTransient = code < 500` (RFC 5321 §4.2.1; RFC 4954 `454 Temporary authentication failure` and RFC 3207 `454 TLS not available` are 4yz and retried). A local TLS-context failure is the new `TlsSetupFailed`, terminal. `ConnectionFailed` (transport, no reply) and `Timeout` are `Cause.Transient`. HTTP: `AuthError` and `VendorNotFound` are terminal; `RequestFailed` is terminal for 4xx except 408 and 429 and transient otherwise. [verified: `NotificationRetryClassificationTest` — 18 tests counting attempts at a stub backend with `maxAttempts = 3`: 5yz/terminal → 1, 4yz/transient → 3, at every SMTP site; `SmtpReplyCodeClassificationTest` — the REAL `SmtpClient`+`SmtpSession` against a scripted loopback server counting accepted connections: `454`@AUTH → 3, `421`@EHLO → 3, `454`@STARTTLS → 3, `421`@greeting → 3, `451`@MAIL FROM → 3; `535`@AUTH → 1, `554`@STARTTLS → 1, `554`@greeting → 1, `550`@MAIL FROM → 1. Mutation: making `ReplyRefused` unconditionally terminal (the site-classified shape the first round shipped and review of #1075 refuted) reddens exactly the nine 4yz pins]
- **Round-1 defect, recorded:** the first round made `AuthFailed`/`TlsFailed`/`ProtocolError` unconditionally terminal — classified by command SITE — so a 4yz at EHLO/STARTTLS/AUTH got one attempt where the base retried, and a 5yz greeting (`554 No SMTP service here`) was `ConnectionFailed` and retried on the full schedule; the round's pins hand-fed `AuthFailed("535 …")` and never read the number (the fixture stated the rule instead of probing the producer). Both directions are now decided by the code, and the producer-level pin above is what would have caught it.
- `SmtpError`'s refusal records now all carry `int code` (`Rejected`, `AuthFailed`, `TlsFailed`, `ProtocolError`); the greeting refusal is a `Rejected` rather than a `ConnectionFailed`. The only constructors are `SmtpSession`'s eight reply sites, which already had the code in hand, and `SmtpClient`'s local TLS-context site (now `TlsSetupFailed`); nothing outside `integrations/net/smtp` pattern-matched any of them.
