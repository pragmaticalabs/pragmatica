### Fixed (2026-11-24 — #3026: terra:assemble --check required deployment secrets at build time)
- **`terra:assemble` ran the launcher's `--check` through the launch path, so a distribution whose deployment secrets come from the environment failed the build unless the build environment carried them: an HS256 `[jwt]` without `TERRA_JWT__SECRET`, and an `[api_keys.<name>]` entry without `TERRA_API_KEYS__<NAME>__KEY`.** `--check` now loads the plan with deployment secrets deferred: everything known at build time (keys, modes, `auth_schemes`, slice selection, a secret that is supplied but too short or blank, a blank api key, an invalid api-key role, a duplicate supplied api key) is still checked, and an absent `jwt.secret` or `api_keys.<name>.key` is reported in the check log as `Runtime input not supplied (required at launch): <input>` instead of failing; two absent api keys are not a duplicate. A launch still refuses a missing secret (`JWT HS256 mode requires jwt.secret`, `Invalid API-key configuration for entry <name>`), and a plan loaded for checking refuses `start()` with `Runtime inputs not supplied: ...`. Limits: an api-key entry the settings do not declare at all (no `[api_keys.<name>]` section and no environment variable) cannot be seen by the check; a secret read inside a custom `HttpAuthenticatorFactory` is the provider's, and the check cannot defer it. `[verified: terra/launcher DeferredRuntimeInputsTest]`
