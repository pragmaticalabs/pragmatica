### Changed (2026-11-09 — #2973: SQL datasource pools are shared per node — **Breaking**)
- **SQL datasource pools are now shared per node.** Slices on one node whose datasource section resolves to the same connection settings now share one connection pool, where previously each slice had its own. [mechanism: one pool per share key in the node's provider; pinned against a real PostgreSQL by `PgSharedPoolLiveTest` (3 slices, one pool's sessions in `pg_stat_activity`), a single provider, not a cluster run]
- `pool_config.min_connections`/`max_connections` now size **the node's pool for that datasource**: 19 slices at `max_connections = 32` previously opened up to 608 sessions per node, and now open up to 32. **Operator action:** size `max_connections` for the node's peak concurrent database work on that datasource. Multiplying the old value by the slice count is the conservative fallback, but it restores the over-provisioning that this change removes.
- To keep per-slice pools, set `pool_scope = "slice"` in the **datasource section** (not in `pool_config`). The spellings `pool-scope`, `poolScope` and `pool_config.pool_scope` fail the slice load with an error naming `pool_scope`; other unknown keys in a datasource section are still ignored (forge.toml's `[database]` carries Ember's own keys). Overlays can set `pool_scope` per slice. [mechanism: `MisplacedPoolScope` checks the file-backed layers when the slice composite loads a datasource section, and `@StrictKeys` on `PoolConfig` refuses unknown `pool_config` keys; `pool_scope` binds as an enum, unknown values refuse] [verified: `PoolScopeRefusalTest` for the three `pool_scope` spellings; `DbShareKeyTest` for the `PoolConfig` unknown-key refusal and the unknown-value refusal] Environment and system-property layers are not checked.
- Sharing is per connector type: `SqlConnector`, `PgSqlConnector` and jOOQ on one datasource are separate pools. Slices whose settings differ (URL, user, resolved secret, database type, any pool setting, `properties`, application name) also get separate pools. [verified: `DbShareKeyTest` (every input, async host, port and database, and type, changes the key; a distinctive password and user never appear in `toString`)]
- **Isolation changes:** pooled connections are shared across slices. A slice that changes session state (`SET`, temp tables, session advisory locks outside `pinned`) must restore it or use `pool_scope = "slice"`. One slice's long transactions or leaked connections can now starve the others on that datasource.
- `stop()`/`close()` on a provisioned shared connector releases only your slice's handle (later async calls on it fail with `HandleReleased`; on the jOOQ view the synchronous accessor `dsl()` is not guarded and keeps returning the pool's `DSLContext`, which for JDBC is bound to the shared `DataSource`: do not use a `DSLContext` you kept after `stop()`); the pool closes when the last slice using it releases it. Casting a provisioned connector to a concrete class no longer works. [mechanism: per-holder views; holders and pool change in one `ConcurrentHashMap.compute` per key, and only the release that removes the last holder closes the pool] [verified: `SqlConnectorViewTest`, `JooqConnectorViewTest` (every async method of the SQL, PostgreSQL and jOOQ views fails with `HandleReleased` after release on a pool whose calls succeed), and each factory's `*SharedPoolTest` (the view is not the pool, `stop()` releases and never stops the pool)]
- A slice that bundles its own DB connector module or driver keeps a private pool. Drivers for shared pools come from the node classpath.
- The server sees N nodes × each node's pool.
- Verify sharing in the node log: `opened/joined/left/closed shared pool`.
- New: a WARN and an operator warning when a node's pool demand exceeds what the PostgreSQL server allows (`datasource-demand-exceeds-server-limit`), or when the server refuses a connection as full (`datasource-server-refused-connection`, SQLSTATE 53300 on the postgres-async transport). Each has an INFO recovery for the same server: `datasource-demand-within-server-limit` when a later probe answer or a pool close finds the node's sums back within the server's limit, and `datasource-server-accepting-connections` when a later probe of that server is answered [verified: `PoolDemandGuardTest`]. A warning for a server that is never probed or closed against again stays open until the node restarts. It never refuses a pool. [mechanism: a probe after each pool open; the 53300 arm is pinned against a real PostgreSQL by `PgSharedPoolLiveTest`, a single provider, not a cluster run] **Operator action:** size `max_connections` per node per datasource, keep pools shared, or raise the server limit.
- **Failure and shutdown containment (round 1 of #2978):** a factory that throws, or whose provision fails, never wedges its share key or a slice's own pool: the entry is evicted and the next acquire provisions afresh (a throw is contained on both the shared and the `pool_scope = "slice"` paths); node stop leaves no pool open even when it races an acquire; a view's `stop()` releases only the holding it was issued for, so a stale view cannot close the pool a slice re-acquired. [verified: `SharedPoolContainmentTest`, including a 300000-round race of `closeAll` against `acquire`] Pools are created under the factory's class loader on all seven connectors, so a node-shared pool's threads never pin the first slice's class loader [verified: each factory's `*SharedPoolTest`].
