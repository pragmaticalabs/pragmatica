### Changed (2026-11-11 — #686 part A1: server route check for `POST /api/v1/cluster/config`)
- **An apply request may claim who fills its pools, and the server checks the claim** (#686). `ApplyConfigRequest` gains an optional `route` (`LEADER` or `APPLY`). With it, the server recomputes the diff, decides each pool-changing action's route from the committed auto-heal value (worker and spot pools, and core pools with auto-heal on, are the leader's; core pools with auto-heal off are apply's), and refuses a claim that differs with a typed `RouteMismatch` (409). Structural changes are admitted only on this path; without `route` they stay refused as before. The wildcard `expectedVersion` 0 is refused with a route. [verified: `ClusterConfigRoutesApplyTest$RouteCheck`]
- **Unsafe structural changes are refused with a next step** (#686): a source field change outside a core-only source with auto-heal off (`SourceReplaceRefused`), a worker or spot removal with a committed count above 0 (`LivePoolRemovalRefused`; a zero-count removal is admitted), a core role added with nodes while auto-heal is on (`CoreFillRefused`), and a core scale-up with auto-heal on and several core sources (`MultiSourceCoreScaleRefused`). The explicit-community guard also covers a worker role added on the route path.
- **Config refusals carry a machine-readable `code`** in the problem body (#686), so a client tells the definitive 409s from the transient "current core leader required" 409, which stays untyped. [verified: `ClusterConfigRoutesApplyTest$RouteCheck.everyRoutePathRefusal_carriesCode`]
