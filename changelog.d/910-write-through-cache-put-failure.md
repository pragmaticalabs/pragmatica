### Fixed (2026-09-14 — #910: a cache-tier put failure failed a write-through put that was already durable)
- **`StorageInstance.promoteToNextCacheTier` logged a cache-tier failure as "skipped" and then `flatMap`ped the failure through**, so the caller's `put` failed after the durable tier had already accepted the bytes: the caller was told its durably stored data was lost, the claim was released and the bytes orphaned (two-tier) or a stale record survived (three-tier), exactly as the ticket traces. The chain now absorbs a cache-tier failure — the durable write has succeeded by the time any cache tier is asked, so a cache failure is an accelerator failure, not a data failure — and continues with the next cache tier. [verified: `StorageIntegrationTest$TierWaterfallTests#memoryTierGenuinelyFull_putSucceeds_andReadsFromDisk` (`integrations/storage`) — a 64-byte block into a 32-byte memory tier over a disk tier: the put succeeds, memory holds zero bytes, disk holds the block, `get` returns it. Red at the base with `MEMORY tier full: 0/32 bytes`; reverting `StorageInstance` reddens exactly this test]
- **A cache tier that fails MID-WRITE has its partial copy discarded.** A tier that fails part-way — a real `LocalDiskTier` under ENOSPC, reproduced by the review of #1095: 901,120 of 2,097,152 bytes on disk — leaves a truncated file, and the read waterfall stops at the first tier that returns bytes, so every later `get` failed its integrity check while the durable copy sat unreachable behind it. Round 1 had turned that loud put failure into a silent-until-read one and written "served from the durable tier" into the log. Now a failed promotion is followed by a best-effort `delete` on that tier (itself absorbed and WARNed if it fails) — but only for a failure that could have written something: a tier that refused BEFORE writing (`TierFull`) left nothing to discard, and the id may already hold a valid copy there, which the round-2 unconditional delete evicted on every re-promotion against a full tier (review of #1095 r2). The read-path rule itself (stop at the first tier with bytes, never fall through on an integrity failure) is unchanged and is a separate ticket. [verified: `CacheTierPartialWriteTest#cacheTierFailsMidWrite_putSucceeds_partialCopyIsDiscarded_readServesDurableBytes` — a tier double that stores half the block and fails: the put succeeds, the truncated copy is gone, `get` returns the durable bytes (red with the delete removed: the half copy survives); `#fullCacheTier_rePromotion_keepsTheValidCopy` — a memory tier holding exactly the block, a fresh instance re-puts it: `TierFull`, and the copy is still there (red at the round-2 head: `exists` false; red with the `TierFull` guard removed)]
- **`LocalDiskTier` never has a partial copy at the block path, and its accounting cannot go negative.** `Files.write` is TRUNCATE_EXISTING, so the round-2 in-place write destroyed the previous copy at open and, on failure, deleted whatever was left — an open-time failure therefore discarded an intact previous copy, and the instance-level `delete` that followed the tier's own discard subtracted a second time (`-64` with a directory squatting on the path, `-1024` after a 1,024-byte partial). The block is now written to a sibling `<hex>.<n>.partial` file and renamed over the block path once complete (`FileOps.moveReplace`, a same-directory `rename(2)`), so the block path only ever holds a whole copy — the previous one until the rename, the new one after it. A failed write discards only what it created (the partial file), the reservation is released exactly once in `put`, `delete` subtracts only the regular file it removes (a squatting directory is neither a block nor a size), and a partial left by a crash is removed — not counted — at the next startup. Behaviour change to note: an EMPTY directory squatting on a block path is now replaced by the block (the JDK removes it before the rename) where round 2 failed the write; a non-empty one still fails it. [verified: `CacheTierPartialWriteTest#localDiskTier_midWriteFailure_discardsThePartial_usedBytesEndsAtZero` — a write seam that writes 1,024 of 4,096 bytes then fails, through a real `StorageInstance`: the fixture proves 1,024 bytes were on disk, the partial is gone, the block is absent, `usedBytes` is 0, the read serves the durable copy (red with the discard removed: the partial survives; red with the release removed: 4,096; red with the in-place write restored: `-1024`); `#localDiskTier_failedOverwrite_keepsThePreviousCopy` — the same seam failing after 1,024 bytes and after 0 bytes over an existing copy: the previous bytes are intact, `usedBytes` stays 4,096 (red at the round-2 head: `Option is empty`, the previous copy deleted); `#localDiskTier_deleteOfADirectorySquattingTheBlockPath_subtractsNothing` (red at the round-2 head: `-64L`); `#localDiskTier_emptyDirectorySquattingTheBlockPath_isReplacedByTheBlock` (red with a directory counted as a previous copy: 1,984); `#localDiskTier_startup_removesLeftoverPartials_andCountsOnlyBlocks` (red with the sweep removed); `#localDiskTier_failedWrite_releasesTheReservation` — the real writer against a non-empty squatting directory: `usedBytes` back to 0, no partial left]
- **Logging policy, stated.** `TierFull` is steady state on a hot tier and logs at DEBUG — a per-put WARN there is the #718 flood. Any other cause means the tier is not working, and that was invisible at INFO with no circuit and no metric (1,000 writes → 1,000 attempts at a dead tier, all DEBUG — review of #1095, SF-1): now the FIRST non-capacity failure per tier logs at WARN, then every 1,000th with the running count, the rest at DEBUG. [verified: `CacheTierPartialWriteTest#brokenCacheTier_warnsOnce_thenDebug_andTierFullNeverWarns` — 5 puts through a broken tier: 1 WARN, 4 DEBUG; a full tier: 0 WARN (red with the WARN branch disabled)]
- `MemoryTier.put` names its own `level()` in `TierFull` instead of hard-coding `MEMORY` (N-1); `StorageMaintenanceWiringTest`'s comment says "absorbs … true since #910" rather than presenting the new behaviour as always-true (N-2).
- The pre-existing `memoryTierFull_writesToDisk_readsFromDisk` writes 25 bytes into a 32-byte tier and never fills it; it is left as-is (it still pins the waterfall read) and the new test sits beside it with a name that says the tier is actually full.
