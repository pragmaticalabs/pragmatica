### Fixed (2026-11-02 — #2045: Rabia empty-slot livelock from voters' committed-batch ledgers disagreeing)
- **A late `NewBatch` of an already-decided batch could stop consensus from applying anything.** Each voter recorded the correlation ids it had merged locally as committed, so the voters' ledgers depended on message arrival order: some voters re-queued the late batch and proposed it forever while the others refused it, no value reached 3 identical proposals, and every slot decided empty (644,712 slots in 601 s in an N=100 run). A slot now satisfies only the correlation ids its Decision carries: the ledger records those alone, so it is the same on every replica that applied the same slots, and an id merged locally but not decided stays pending as a request of its own. `[verified: integrations/consensus/src/test/java/org/pragmatica/consensus/rabia/RabiaReorderedDeliveryTest.java pendingHead_requeuedOnTwoOfFourLiveVoters_laterRequestStillCommits]` (single-JVM scheduled cluster, not a multi-node run)
- **Changed behaviour:** two genuine identical submissions that one voter merged now apply once each, each completing its own caller; before, the second was coalesced into the first (#958 coalescing after proposal). One submission still applies once. `[verified: RabiaReorderedDeliveryTest mergedIdenticalSubmission_lateNewBatch_appliesOncePerSubmission, singleSubmission_lateNewBatchAndReplayedProposal_isAppliedOnce]`
- **A voter that skipped a slot through a snapshot restore no longer re-proposes a batch committed in it.** A voter whose ledger holds a proposal's correlation ids as committed now answers the proposer with the new `BatchCommitted` message (wire tag 2201); the proposer records the ids and drops them from its queue, and a local caller waiting on one of them fails with `CommittedOutcomeUnknown`. `[verified: RabiaReorderedDeliveryTest snapshotSkippedSlot_lateNewBatchOfCoveredBatch_isNotRequeued]`
- **The livelock is visible.** `consensus_consecutive_empty_slots_with_pending` (Prometheus, a level) and `consecutiveEmptySlotsWithPending` plus `firstChoiceBatchId` in the comprehensive metrics response's `consensus` block. No new route. Recovery if the counter keeps climbing: compare `firstChoiceBatchId` across cores, and restart the core whose first choice differs from the rest. `[design intent — unverified]` for the recovery step.
