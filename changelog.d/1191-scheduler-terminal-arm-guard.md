### Fixed (2026-09-15 — #1191: a certificate retry timer could outlive `stop()`, leaving a live tick on a stopped scheduler)
- **Hooks run after and outside the CAS, so two transition WINNERS can overtake each other.** `Fsm.tryAdvance` returns early when the compare-and-swap fails — `onExit`, the transition action and `onEntry` all sit behind that early return — so a LOSING transition runs no hooks at all, and the class documentation says exactly that. The real interleaving is between winners: a thread that has won `Renewing → RetryBackoff` can still sit between the CAS and its `onEntry` while a second thread wins `RetryBackoff → Stopped` and completes the drain; the first then arms a retry timer onto a stopped scheduler, uncancelled and still firing its `Tick`. [mechanism: `Fsm.tryAdvance` returns before `onExit`/action/`onEntry` when the CAS fails; hooks execute outside the atomic]
- **An earlier revision of this change recorded the OPPOSITE mechanism and was wrong**, claiming a losing transition "has already begun running its side effects". An adversarial reviewer read `tryAdvance` and refuted it. The error mattered beyond wording: a wrong mechanism aims the FSM-wide follow-up at making losers skip side effects, which they already do.
- **Arming, draining and marking terminal take ONE lock, and every arm carries an EPOCH.** `terminated` and `scheduledTask` are separate references, so no arrangement of atomics makes "is this terminal" and "what is armed" a single observation. Each hook that arms calls `openArmingEpoch()` **before scheduling**, captures the value, and passes it back. Under the lock, an arm that is terminal **or** whose epoch is no longer current cancels **itself** and returns. [mechanism: one critical section over the pair, plus a monotonic epoch that identifies which hook an arm belongs to]
- **WHY THE EPOCH, AND THIS IS THE PART A LATER READER MUST NOT LOSE.** An intermediate revision of this fix cancelled the *displaced* task on every arm. That is **strictly worse than the bug it replaced**, and it was caught in review rather than by any test. `Healthy.onEntry` SCHEDULES before it arms, and on the immediate branch the delay is zero — so the tick can complete the whole `Healthy → Renewing → RetryBackoff` round trip, arming the real 5-minute retry, while the original hook still sits between its `schedule` and its arm. That late arm then displaced and **cancelled the live retry**. Renewal stops permanently and `renewalStatus()` still reports FAILED. The lock cannot fix it: it makes two arms atomic with respect to each other but cannot say which is NEWER. A stale entry hook arriving late is indistinguishable, at the seam, from a legitimate re-arm — only an epoch distinguishes them. [mechanism: zero-delay tick completes the round trip inside the window between `schedule` and `armScheduledTask`, asserted by this class's own documentation]
- **All three arming sites carry it** — `Healthy.onEntry`, `RetryBackoff.onEntry`, and the dev-mode-only `configureShortValidity`. The epoch is what covers the third: it arms with no state identity at all, so a state check could not have guarded it.
- **Four mutations produce four DIFFERENT single-test red sets, none a superset of another.** Measured over the whole test class, never a selected method:

  | mutation | red set |
  |---|---|
  | terminal check removed | `armScheduledTask_afterStop_refusesAndCancelsTheTask` |
  | epoch check removed | `armScheduledTask_whenTheArmIsStale_cancelsItselfAndLeavesTheResidentTimer` |
  | displace-and-cancel replaced by a bare `set` | `armScheduledTask_whenAnotherArmDisplacesIt_cancelsTheDisplacedFuture` |
  | mark/drain order swapped | `stopEntry_raisesTerminatedBeforeDraining_soNoArmCanSlipBetweenThem` |

  Unmutated: the class is 7 tests, 0 failures; module `integrations/net/tcp` is **71 `<testcase>` elements across its surefire reports in one run, 0 failures**, against 67 before this change. [mechanism: per-mutation red sets measured over the whole class; counts are `<testcase>` elements in that module's surefire reports, stated with their space because a count without one is not checkable]
- **The scope is one scheduler, and #1191 stays OPEN — the survey says the exposure is WIDER, not narrower.** Of **ten** production state hierarchies built on `FsmState` (fourteen files match the type; four are the framework itself or use it only as a generic bound — a count an earlier revision of this fragment stated wrongly as "fourteen implementations", without its space), at least `LeaderElectionState` is exposed to the **same winner-overtaking race**: `AwaitingKvSync.onEntry` schedules a grace timeout and stores it, and `Pending` and `Led` share the shape. **Its `onCasLost` override does NOT mitigate this** — `tryAdvance` calls that hook only on the CAS-LOSS path, and this race is between two winners, so it never fires. What that hook genuinely protects is the different hazard `FsmState` documents for it: futures constructed eagerly in a factory on a state that never became current. `ClusterDeploymentState` arms in one entry hook whose body makes two scheduling calls, and **one never stores its future at all**, so nothing can cancel it. Neither is changed here. [design intent — unverified]
- **Pinning the ordering needed the right entry path, and the first attempt measured the wrong drain.** `transitionTo` runs the FROM state's `onExit` before the target's `onEntry`, and `Healthy.onExit` already drains the holder, so a probe installed after `start()` is cancelled by the EXIT hook while `terminated` is still false — that version failed against correct code. Entering from `Idle`, which declares no exit hook, leaves the terminal drain as the only one that can reach the probe. The test records what `terminated` held at the instant the drain cancelled a stub future, turning an ordering into a value observable with no concurrency and no timing.
- **What this does NOT establish, recorded beside the claims rather than left to be noticed.** #1191 reports roughly 6% (3 in 50) **"on an idle box" — it never says CI**, which is the same condition as the 200 isolated and 50 whole-class local runs here that reproduced it zero times. Those two figures are unreconciled, not reconciled in this change's favour. Worse for checkability: **the test #1191 names does not exist** — `stopAfterImmediateRenewalotherwise_clearsScheduledTask`, zero occurrences against a positive control of 2 for the real method — so the rate is attached to a symbol nobody can resolve. This change is justified by reading the FSM and by pinned invariants, and **no claim is made here that the reported flake is now impossible**. [design intent — unverified]
