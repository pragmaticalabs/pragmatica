### Fixed (2026-09-15 — #1191: a certificate retry timer could outlive `stop()`, leaving a live tick on a stopped scheduler)
- **The FSM's CAS serialises which transition WINS, not the side effects of the one that loses.** `Fsm.dispatch` reads the current state and only then calls `handle`, with the compare-and-swap inside `TransitionRequest.transitionTo`, which swaps first and runs `onExit` / action / `onEntry` afterwards. A transition that loses the swap has therefore already begun its side effects. In `CertificateRenewalScheduler` that let `RetryBackoff.onEntry` store a retry future AFTER a concurrent `stop()` had run `Stopped.onEntry` and drained the holder — an uncancelled timer that still fires its `Tick` on a scheduler the operator has stopped. [mechanism: `Fsm.dispatch` reads `currentState` before dispatching to `handle`; `transitionTo` CASes before invoking the entry hook]
- Arming now goes through `Context.armScheduledTask`, which cancels the task instead of storing it once the scheduler is terminal. `Stopped.onEntry` raises `terminated` BEFORE it drains, and the guard checks that flag both before and after the store. Either the store precedes the drain, and the drain removes the task; or the drain precedes the store, in which case the flag was already raised and the post-store check cancels. No interleaving leaves a task armed past the terminal state. [mechanism: double check against a flag raised before the drain, giving each order a disqualifying observation]
- **All three arming sites are routed through the guard, not just the one the failure was seen on** — `Healthy.onEntry`, `RetryBackoff.onEntry`, and the dev-mode-only `configureShortValidity`. Guarding one of three would have read as a complete fix while leaving two paths open.
- **The scope is one scheduler on purpose, and #1191 stays open.** The general fix is an FSM-wide design decision affecting every state machine whose entry hook arms a timer or opens a resource, and that ticket asks for a survey rather than a point fix. The survey now exists: of fourteen `FsmState` implementations, `LeaderElectionState` arms inside `onEntry` at three sites and `ClusterDeploymentState` at one. Neither is changed here and neither is claimed to be broken; they have the same shape and want the same examination. [design intent — unverified]
- **The test that exposed this was right and was not touched.** `stopAfterImmediateRenewal_clearsScheduledTask` asserts that the terminal drain leaves the holder empty, which is a real property, so it was fixed rather than relaxed. Its sibling in the same class had previously been disabled for a different, genuinely unpinnable transient; that one stays as it was rewritten in #1194. A new deterministic test drives the arming seam directly after `stop()` rather than waiting on the race, because the natural interleaving reproduced zero times in 200 isolated local runs while CI hit it once — a rate that makes a timing-based regression pin a lottery.
- **What the new test does NOT pin, recorded next to the claim rather than left for a reader to notice.** Mutating the guard away — leaving a plain store — turns `armScheduledTask_afterStop_refusesAndCancelsTheTask` red, so the refusal itself is pinned by measurement. Swapping the two lines inside `Stopped.onEntry`, so the drain runs BEFORE `terminated` is raised, leaves that test GREEN: it calls the arming seam after `stop()` has already returned, by which point the flag is set under either order. So the ordering that the correctness argument rests on is load-bearing by argument and undefended by test, and an edit that reversed those two lines would reopen the race silently. The comment at `Stopped.onEntry` says so at the point where someone would make that edit. [design intent — unverified]
