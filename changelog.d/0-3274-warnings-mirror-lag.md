### Fixed (2026-11-16 — #3274: an FSM2 warning close could be published against a lagging mirror)
- **The operator's warning open set is a read of the committed `FsmWarningKey` rows, and a warning close is no longer published against a stale mirror** (#3274). A WARNINGS write that settled as failed (`ApplyTimeout`) or expired can still commit, and a `Rebuild` snapshot cannot see a batch of the previous incarnation still in consensus. The open set is now the set of committed rows with `open` true; events are notifications and no reader derives the set from them. Each family site calls `Warnings.raise` unconditionally; the leader's family state is its intent, and one WARNINGS transaction at a time writes the difference between intent and the mirrored committed rows. A row carries the key's next `revision` and the writer's stamp (node, process, incarnation), so a stale CAS cannot commit after a newer write; the FSM never removes a row (every close writes a kept `open` false row with the recovery text); a row of this incarnation's stamp is only compared with intent, an earlier self's row is ignored and another node's row is joined open-biased after the family's hold test (rule O). Notifications are a function of one accepted committed pair `expected -> replacement` (rule E): the opener when the replacement holds a (member, value) the expected does not, the recovery when an open row is replaced by a closed one. `FsmWarningValue` gains `revision` and the writer stamp (wire encoding change under tag 2903, no mixed-version rolling upgrade across it); the transaction is a `LeaderTransaction` and the value `LeaderAuthorized`, so a deposed leader's write is refused. Compaction of closed rows of departed subjects is a follow-up. [mechanism: every own write, closes included, CAS-moves the key to a value with a higher revision and no row is removed, so a stale batch whose CAS expects the earlier value cannot commit; pinned by in-JVM FSM harness tests (`WarnAfterCommitTest`, `WarningsCommittedRowsTest`, `WarningsFamilyStateWritersTest` which fails on any family-state assignment outside `Warnings`), no multi-node failure injection]
- **`join-unmatched` is announced once per episode** (#3274): the 30 s tick no longer repeats the WARN for a join that stays unmatched; the open warning stays readable at `GET /api/v1/warnings` until the join matches or the node departs.
