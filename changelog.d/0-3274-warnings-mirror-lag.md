### Fixed (2026-11-15 — #3274: an FSM2 warning close could be published against a lagging mirror)
- **A warning close is no longer published while the committed row may still be open** (#3274). A WARNINGS write that settled as failed (`ApplyTimeout`) or expired can still commit, and a `Rebuild` snapshot cannot see a batch of the previous incarnation still in consensus. The keys of such a write, and every mirrored key at `Rebuild`, are now unsure: held warnings are published only through the write that carries them until a write of this node touching each key is accepted or the stale write is seen committed. `FsmWarningValue` gains a `revision` (wire encoding change under tag 2903, no mixed-version rolling upgrade across it), so every write leaves a value no stale CAS expects; an unsure key with nothing to write gets a confirming write, and the FSM never removes a WARNINGS row: every close writes a kept "no warning" row under the next revision, so a key never returns to an earlier value ("no row" included). Compaction of the closed rows of departed subjects is a follow-up. Known transient: a stale write of a key absent from the successor's mirror is shown until the next flush closes it. [mechanism: every own write, closes included, CAS-moves the key to a value carrying a higher revision and no row is ever removed, so a stale batch whose CAS expects the earlier value cannot commit after it; in-JVM FSM harness tests in `WarningsMirrorLagTest`, no multi-node failure injection]
