### Fixed (2026-09-13 — #1067: config-section preflight rejected deploys the runtime would accept)
- **A blueprint whose slice declares a resource's config section only in its own jar's `META-INF/resources.toml` was refused at deploy with HTTP 500 (`MissingConfigSection`), although the slice loader resolves that section.** `ConfigSectionPreflightValidator` checked only the leader's node composite (KV overlay ⊕ `node.toml`), while `SliceStore` has layered the jar's `resources.toml` beneath that composite at load since the same commit that added the check (`265748fbd`). `DurableEntityForgeTest` and `DurableEntityTimerDurabilityTest` failed in setUp on exactly this: `test-entity` ships `[entities.orders]` only in its jar. [verified: `BlueprintPublishOwnershipTest.ConfigPreflight.publish_succeeds_whenDeclaredSectionShipsOnlyInTheSliceJar` and `publishFromArtifact_succeeds_whenDeclaredSectionShipsOnlyInTheSliceJar` red at the rc4 tip, green after]
- The preflight now checks each slice over the loader's own layering, calling the loader's functions rather than a copy of them: `SliceStore.readSliceResourcesToml`, `SliceStore.sliceIntrinsicLayer` and `SliceStore.layerSliceComposite`, which `SliceStore` itself now uses at load. **Guarantee:** a deploy is refused iff some declared section is absent from every layer the loader would consult for that slice, as seen from the leader. The view is per slice, so one slice's jar never satisfies another. A jar `resources.toml` that does not parse contributes no layer, matching the runtime's fallback to the node composite. [verified: `ConfigSectionPreflightValidatorTest.SliceJarLayer`]
- **Still refused, with the same `MissingConfigSection`, when a section is in no layer**; a section present only in `node.toml`, or only in the KV overlay, is still accepted. [verified: `publish_failsWithMissingConfigSection_whenSectionIsAbsentFromEveryLayer`, `publish_succeeds_whenSectionIsConfiguredOnlyInNodeToml`, `publish_succeeds_whenSectionIsConfiguredOnlyInKvOverlay`]
- Limits, stated rather than closed: the node composite is still the leader's alone; `${secrets:...}` placeholders in a jar's `resources.toml` are not resolved by the check, so a section present only in a jar whose secrets fail to resolve at load passes it and fails at provisioning `[unverified: no test drives that path]`; with no configuration provider the check still fails open. `MissingConfigSection`'s message now names the jar layer among the layers checked.
