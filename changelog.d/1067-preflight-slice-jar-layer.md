### Fixed (2026-09-13 — #1067: config-section preflight rejected deploys the runtime would accept)
- **A blueprint whose slice declares a resource's config section only in its own jar's `META-INF/resources.toml` was refused at deploy with HTTP 500 (`MissingConfigSection`), although the slice loader resolves that section.** `ConfigSectionPreflightValidator` checked only the leader's node composite (KV overlay ⊕ `node.toml`), while `SliceStore` has layered the jar's `resources.toml` beneath that composite at load since the same commit that added the check (`265748fbd`). `DurableEntityForgeTest` and `DurableEntityTimerDurabilityTest` failed in setUp on exactly this: `test-entity` ships `[entities.orders]` only in its jar. [verified: `BlueprintPublishOwnershipTest.ConfigPreflight.publish_succeeds_whenDeclaredSectionShipsOnlyInTheSliceJar` and `publishFromArtifact_succeeds_whenDeclaredSectionShipsOnlyInTheSliceJar` red at the rc4 tip, green after]
- The preflight now checks each slice over the loader's own layering, calling the loader's functions rather than a copy of them: `SliceStore.readSliceResourcesToml(URL)`, `SliceStore.sliceIntrinsicLayer` and `SliceStore.layerSliceComposite`, which `SliceStore` itself now uses at load. **Guarantee:** a deploy is refused iff some declared section is absent from every layer the loader would consult for that slice, as seen from the leader. The view is per slice, so one slice's jar never satisfies another. A jar `resources.toml` that does not parse contributes no layer, matching the runtime's fallback to the node composite. [verified: `ConfigSectionPreflightValidatorTest.SliceJarLayer`]
- **The loader itself read the intrinsic layer through the composed slice classloader, which also holds every `[slices]` dependency jar — so a slice shipping no `resources.toml` of its own silently took the first dependency jar's file as its intrinsic layer, and provisioned a section the preflight (reading the own jar alone) refused.** Fixed on the runtime side: `SliceClassLoader.sliceJarUrl()` names the slice's own jar (the first url, by construction at every production site) and `SliceStore.readSliceResourcesToml(URL)` reads `META-INF/resources.toml` from that jar alone, closing the throwaway classloader afterwards — the one function both the loader and the preflight now call. A dependency slice's file is never this slice's layer; a loader built without a jar has an empty layer. [verified: `SliceStoreTest.buildSliceCompositeFromClassLoader_ignoresDependencyJarToml_whenOwnJarShipsNone` red at `284547461`, green after; reading through the composed loader again reddens exactly it; `SliceStoreTest.buildSliceCompositeFromClassLoader_readsOwnJarToml_ignoringDependencyJar` and `SliceClassLoaderTest.sliceJarUrl_isTheFirstUrl_andDependencyUrlsAppendAfterIt` pin the own-jar-first convention]
- A slice jar located at expansion but not at the preflight's second locate is still left unchecked rather than failing the publish (the pre-#1067 behaviour); `BlueprintService.loadSliceJar` now logs that skip as such, and the comment states that `BlueprintExpander.expand` has already refused an unlocatable jar, so the branch is only reachable by an eviction between the two locates `[unverified: not inducible in the unit fixture]`.
- Acceptance: `DurableEntityForgeTest` and `DurableEntityTimerDurabilityTest` (and the `02w-entity-crash` suite) posted to `/api/v1/entity/*`, while the `test-entity` fixture's `routes.toml` declares `prefix = "/api/entity"` and the generated routes register exactly that — the app HTTP surface carries no server-added version segment, as every sibling fixture (`/api/stream`, `/api/kv`, …) shows. The callers now use the registered prefix. [verified: both classes green in-JVM at the PR head — 15 failsafe `<testcase>`, 0 failures/errors/skips, 0 `requires config section` lines; no Heavy run had passed their `setUp` before]
- **Still refused, with the same `MissingConfigSection`, when a section is in no layer**; a section present only in `node.toml`, or only in the KV overlay, is still accepted. [verified: `publish_failsWithMissingConfigSection_whenSectionIsAbsentFromEveryLayer`, `publish_succeeds_whenSectionIsConfiguredOnlyInNodeToml`, `publish_succeeds_whenSectionIsConfiguredOnlyInKvOverlay`]
- Limits, stated rather than closed: the node composite is still the leader's alone; `${secrets:...}` placeholders in a jar's `resources.toml` are not resolved by the check, so a section present only in a jar whose secrets fail to resolve at load passes it and fails at provisioning `[unverified: no test drives that path]`; with no configuration provider the check still fails open. `MissingConfigSection`'s message now names the jar layer among the layers checked.
