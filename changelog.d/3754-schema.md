### Fixed (2026-11-26 — #3754: the schema orchestrator's lease renewal and retry re-dispatch outlived the node)
- **A stopped node kept renewing its schema-migration lease and re-dispatching migrations** (#3754). `SchemaOrchestratorService` had no stop: its self-re-arming lease renewal (every TTL/3, a durable `SchemaMigrationLockKey` Put) and its transient-failure re-dispatch (a lock claim, then migration scripts on the database) ran on the shared scheduler after `AetherNode.stop()`. Both now go through one `OwnerLifetime` that `SchemaOrchestratorService.stop()` ends, called from `AetherNode`'s component stops. Stop ends renewal and releases nothing: it writes no tombstone, so a lock held under a running script is no longer renewed and lapses by its TTL (at most `LOCK_TTL_MS`, 5 minutes), as after a crash; releasing at stop would free the lock while the script may still run on the database and let another node start the same migration. A script that completes after the stop still releases its own lock by tombstone. A lease still does not end at leader deactivation, where it keeps renewing for the running script. Recovery: none needed; the lock lapses by itself, and a PENDING record is re-dispatched when a leader rebuilds. [mechanism: `OwnerLifetime.end()` cancels every armed task and turns an already-armed wrapper into a no-op] [verified: `SchemaOrchestratorLeaseTest$NodeStop`, `StopSequencePinTest`]
- **Narrowing, not a fence, for a body already past its scheduler read at stop.** The renewal Put re-checks the lifetime immediately before `cluster.apply`, and `acquireLock` refuses at entry, before claiming the single-flight fence or the lock. The lock key is already `VersionFenced` against another node's write; nothing at the receiver refuses "this node is stopping", so a dispatch that passed `acquireLock` before the stop still runs its scripts.
