### Added (2026-11-03 — #2591: `SqlConnector.pinned`, one physical connection held for a whole session)
- **`SqlConnector.pinned(statementTimeout, body, release)` runs `body` on ONE physical connection borrowed in autocommit mode**, so a session-scoped database lock (the groundwork for the DB-side migration fence, which needs it) can live and die with the connection it was taken on. Every call the body makes, and every `transactional(...)` it opens, runs on that same backend; the connection is not lent to any other borrower while pinned [verified: `JdbcSqlConnectorPinnedTest`, `R2dbcSqlConnectorPinnedTest`, `PgAsyncSqlConnectorPinnedTest`: the same `pg_backend_pid()` across calls and a nested transaction, a different one for a competing borrow, and with a pool of one the competing borrow stays unresolved until the release; mutating each transport so its session goes through the pool turns these red].
- **A pinned connection returns to the pool only after `release` succeeded; if `release` fails it is destroyed.** JDBC aborts it (`Connection.abort`, which Hikari evicts), R2DBC closes the physical connection under the pooled wrapper so r2dbc-pool invalidates the slot, and postgres-async gains `Connection.abort()` that closes the socket and frees the pool slot (a waiting borrower is served by a fresh connection). A session lock a failed unlock left behind therefore dies with its backend instead of riding a pooled connection to the next borrower [verified: the three `*PinnedTest`s take `pg_advisory_lock` in the body, fail the release, and find a different backend on the next borrow, no advisory lock left and the old pid gone from `pg_stat_activity`; `ConnectionAbortTest` for the pool slot; mutating each transport so a failed release returns the connection to the pool turns the lock test red]. On HikariCP `Connection.abort` alone does NOT free the pool entry (it stays checked out), so the JDBC connector evicts through `HikariDataSource.evictConnection`.
- **Default behaviour changes for custom `SqlConnector` implementations:** the interface default refuses with the new `DatabaseConnectorError.PinnedSessionUnsupported` and never falls back to an unpinned run. `InMemorySqlConnector` and `InMemoryPgSqlConnector` (slice-testkit) implement it on the fake itself; any other fake or wrapper must forward or implement `pinned` before something starts calling it [verified: `SqlConnectorPinnedDefaultTest`, `InMemoryPinnedTest`].
- Not enforced: R2DBC and postgres-async have no per-statement timeout, so `statementTimeout` binds JDBC statements only (the caller's own promise timeout bounds the others). postgres-async in `TRANSACTION` pool mode refuses `pinned` (it lends a physical connection per query). Nothing in the runtime calls `pinned` yet.
- **CI:** `-Daether.requireDocker=true` is passed to the test-group job, so a live-database test that finds no Docker daemon FAILS there instead of self-skipping (`DockerRequirement` in db-jdbc, db-r2dbc, db-async and aether-deployment; the three aether-deployment schema tests now use it) [verified: `JdbcSqlConnectorPinnedTest` run with `-Daether.hideDocker=true` (the helper's switch that pretends no daemon is reachable) fails with `-Daether.requireDocker=true` and skips without it].
