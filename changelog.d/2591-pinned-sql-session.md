### Added (2026-11-03 — #2591: `SqlConnector.pinned`, one physical connection held for a whole session)
- **`SqlConnector.pinned(statementTimeout, body, release)` runs `body` on ONE dedicated physical connection, opened for the call outside any pool, in autocommit mode**, so a session-scoped database lock (the groundwork for the DB-side migration fence, which needs it) can live and die with the connection it was taken on. Every call the body makes, and every `transactional(...)` it opens, runs on that same backend; the connection is never borrowed from the pool, so a competing pool borrow is served at once [verified: `JdbcSqlConnectorPinnedTest.pinned_runsEveryCallOnOneBackend_theSingleSlotPoolIsServedAtOnceByAnother`, and the same-named test in `R2dbcSqlConnectorPinnedTest` and `PgAsyncSqlConnectorPinnedTest`: the same `pg_backend_pid()` across calls and a nested transaction, and with a pool of one the competing borrow is answered at once by the pool's own, different backend; mutating each transport so its session goes through the pool turns these red].
- **`pinned` opens its own connection and never takes one from a pool; closing it is the release.** JDBC uses `DriverManager` from the datasource config, R2DBC the raw `ConnectionFactory` the pool wraps, postgres-async `ConnectibleBuilder.plain()` (a `PgDatabase`, whatever the pool mode). After `body` and a courtesy `release` step the physical connection is closed, which ends the server session, so a session lock dies with its backend whether or not the explicit unlock worked and can never leak into a pool. The two-argument `R2dbcSqlConnector.r2dbcSqlConnector(config, factory)` is removed (it let a pooled factory serve as the unpooled one); the three-argument form takes both explicitly. Cost: one extra server connection per running pinned scope [verified: the three `*PinnedTest`s: the pinned backend differs from a single-slot pool's own connection, which keeps answering at once and is the same connection after; a lock taken in the body with a failing release is gone, with its backend, once `pinned` returns; mutating each transport so `pinned` borrows from the pool turns them red].
- **Default behaviour changes for custom `SqlConnector` implementations:** the interface default refuses with the new `DatabaseConnectorError.PinnedSessionUnsupported` and never falls back to an unpinned run. `InMemorySqlConnector` and `InMemoryPgSqlConnector` (slice-testkit) implement it on the fake itself; any other fake or wrapper must forward or implement `pinned` before something starts calling it [verified: `SqlConnectorPinnedDefaultTest`, `InMemoryPinnedTest`].
- Not enforced: R2DBC and postgres-async have no per-statement timeout, so `statementTimeout` binds JDBC statements only (the caller's own promise timeout bounds the others). postgres-async in `TRANSACTION` pool mode refuses `pinned` (it lends a physical connection per query). Nothing in the runtime calls `pinned` yet.
- **CI:** `-Daether.requireDocker=true` is passed to the test-group job, so a live-database test that finds no Docker daemon FAILS there instead of self-skipping (`DockerRequirement` in db-jdbc, db-r2dbc, db-async and aether-deployment; the three aether-deployment schema tests now use it) [verified: `JdbcSqlConnectorPinnedTest` run with `-Daether.hideDocker=true` (the helper's switch that pretends no daemon is reachable) fails with `-Daether.requireDocker=true` and skips without it].
