### Changed (2026-11-05 — rc6 §3.1: slice capacity requirements and the leader's combiner)
- **BREAKING (pre-GA): `aether scale -n` / `POST /api/v1/scale` `instances` set a floor, not a count.** The value is the operator's requirement; the slice runs at least that many, and more while the autoscaler's requirement is higher. An operator can no longer scale a slice down: a release (`aether scale --release`, API `"release": true`) or a lower `-n` releases the operator's claim and the slice keeps its count until the autoscaler's requirement falls, under its cooldown. `-n` is no longer required (it and `--release` are alternatives).
- **BREAKING (pre-GA): `aether scale --auto` is gone from the docs.** It was documented and never shipped by the CLI (a `known-doc-drift.txt` entry); the autoscaler's requirement now composes with the operator's floor instead of being switched off per slice.
- **BREAKING (pre-GA): `aether deploy -n` / `POST /api/v1/deploy` `instances` is refused with `400`.** A deployment runs over the slice's committed target, whose count the combiner owns, so the requested count used to be silently ignored over an existing target. Set a count with `aether scale -n`. Omitted, a slice of the blueprint with no target yet is created at 3, as before. The CLI sends `instances` only when `-n` is given.
- **BREAKING (pre-GA flag day): three new KV wire types, tags 2210-2212** (`SliceRequirementKey`, `SliceRequirementValue`, `RequirementKind`; `wire-assignment-baseline.txt`). A node of an earlier build cannot decode them (the codec refuses an unknown tag), and a leader of this build writes `REACTIVE` on its first scaling decision, so a mixed-version cluster must not run [mechanism: unknown-tag refusal, `SliceCodecTest.sliceCodec_unknownTag_throwsException`; what the older node does after the refused decode: design intent — unverified]. Upgrade by coordinated replacement.
- **`aether scale` sets a floor, not a raw count.** Each source of capacity demand now commits its own requirement record (`SliceRequirementKey`, one per slice and source): the autoscaler writes `REACTIVE`, `aether scale -n <n>` writes `OPERATOR`, and `aether scale --release` (API: `"release": true`) removes it. `SCHEDULED`, `CAMPAIGN`, `PREDICTIVE` and `RECOVERY` are defined with no writer yet. The autoscaler and the operator no longer overwrite each other's count ("last write wins").
- **The leader's combiner is the only writer of a target's instance count after its creation**: `target = clamp(max(minAvailable, every unexpired requirement), 3, maxInstances)`, evaluated with the evaluation time as an input and requirements read in a fixed order. Placeable capacity does not bound it yet: the core node count is not a stand-in (allocation is per placement audience, and worker placements land on workers). A target above what the slice's audience can place leaves the excess unplaced, one instance per eligible node, and the leader raises the new `slice-target-exceeds-placement` warning (recovery `slice-target-placement-restored`). It runs on every requirement put or remove, on every target put (a republish arrives this way), on every topology change, on every A/B test put, at the earliest requirement expiry and on leader takeover, and writes through the #2662 fence plus a witness on every requirement of the slice [mechanism: compare-and-set on the target value read; only the leader runs the combiner]. With no unexpired requirement the current count stands.
- **Version writers carry the committed count.** A deployment start over an existing target changes its version only. The blueprint's declared count still seeds a new target.
- **The A/B canary still runs at 3 instances** (#1721, owner ruling 2026-11-06). While a test deploys its variants or is active, the combiner and the autoscaler leave the slice alone, so the variant never runs at the full target. Concluding or rolling back sets the slice to its floor (at least 3), and the combiner then restores the count the committed requirements ask for.
- **Scale-down only through the autoscaler's requirement.** A release, a lowered floor or an expiring requirement re-bases the autoscaler's `REACTIVE` requirement to the current count in the same transaction (the combiner also removes the expired record in it), so the target holds until `REACTIVE` falls.
- **The autoscaler announces only real scaling.** `ScaledUp`/`ScaledDown` events and `SCALED_*` decision records are emitted only when the decision changes `REACTIVE` and that moves the combined target; a decision an operator floor holds the target above writes `REACTIVE` silently.
- **Scale route:** a requirement above the slice's `maxInstances` is refused with `400`; the response adds `target`, the count the committed requirements combine to. Expiry in it is judged on the handling node's clock, not the leader's.
- Requirement records of a slice are removed in the same transaction as its target when a blueprint is deleted or a deployment rolled back (default deployment engine), so re-applying the blueprint never inherits the deleted deployment's operator floor. A record that outlives its target for any other reason is removed by the leader while the target is absent, retried with a backoff until it applies.
