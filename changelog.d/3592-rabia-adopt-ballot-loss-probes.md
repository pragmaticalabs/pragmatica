### Fixed (2026-11-23 — #3592: RabiaAdopt ballot-loss probes name the event that loses the ballot)
- **One constant per code event that could lose ballot memory**: the RabiaAdopt model's `KeepBallots` controlled ballot loss on both pause and adoption, so every ballot-loss probe went red on the same pause-only double vote whatever its description said. It is split into `KeepBallotsOnPause` and `KeepBallotsOnAdopt`, both `TRUE` in every config that models the code (`RabiaEngine.phases` is held in memory; `phases.clear()` runs only on stop and the GC `doCleanupOldPhases` drops only expired past slots, so ballots survive pause, resume and a same-epoch Install; a newer-epoch adoption replaces the PhaseData of every slot at or after the frontier, which drops those ballots, harmlessly because self votes only at `currentPhase`), and each probe sets exactly one of them `FALSE`.
- `ballotlossD5` (pause) is now an expected `Agreement` failure; `ballotloss` and `resync_ballotloss` fail through an adoption (after a pause into a sync round, and after a resync); the new `adoptlossD5` shows adoption loss alone is harmless on the newer-epoch path.
- `adoptlossD5_nooneconfig` and `adoptlossD5_noselfvouch` cannot isolate the fix they drop: they find exactly the state count of their base with the fix on, so they are `pass` rows that say so, not known-bad configs.
