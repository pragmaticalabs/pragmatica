### Fixed (2026-11-23 — #3592: RabiaAdopt ballot-loss probes name the event that loses the ballot)
- **One constant per code event that could lose ballot memory**: the RabiaAdopt model's `KeepBallots` controlled ballot loss on both pause and adoption, so every ballot-loss probe went red on the same pause-only double vote whatever its description said. It is split into `KeepBallotsOnPause` and `KeepBallotsOnAdopt`, both `TRUE` in every config that models the code (`RabiaEngine.phases` is held in memory and cleared only on stop; neither pause, resume nor `applyRestoredState` touches it), and each probe sets exactly one of them `FALSE`.
- `ballotlossD5` (pause) is now an expected `Agreement` failure; `ballotloss` and `resync_ballotloss` fail through an adoption (after a pause into a sync round, and after a resync); the new `adoptlossD5` shows adoption loss alone is harmless on the newer-epoch path.
- `ballotlossD5_nooneconfig` and `ballotlossD5_noselfvouch` cannot isolate the fix they drop: they find exactly the state count of their base with the fix on, so they are `pass` rows that say so, not known-bad configs.
