### Fixed (2026-10-05 — #1937: stream max-event-size had no bound, and two stream catch-up alarms hid each other)

- **`max-event-size` above what one transport frame can carry is now refused at config validation.** A single event travels alone in one replication or catch-up message, so a stream declaring more than the frame less its envelope could be created and then fail at its first oversized event. The ceiling is `OutboundMessageLimit.MAX_TRANSFER_BYTES` (the 32 MiB frame less its reserve) minus a 4 KiB envelope reserve, and the reserve is pinned against the real messages: `StreamEventFrameBoundTest` encodes `ReplicateEvents` and `CatchupResponse` through the node's codec registry (worst-case names, a catch-up history) with a payload of exactly the ceiling and requires them to fit; measured envelopes are 324 bytes (replicate) and 306 plus 72 per history entry (catch-up). Refusal is the typed `StreamDeclarationError.ValueAboveMaximum`.
  [verified: `StreamConfigParserTest` (ceiling accepted, one byte over and 40 MB refused), `StreamEventFrameBoundTest`; reserve = 0 reddens all three frame pins]
- **A promoted owner's backfill now raises `STREAM_EVENT_EXCEEDS_READ_CAP` once per transition**, like the activation gate, instead of a WARN on every redrive. The report is forgotten on EVERY way the condition ends (no peer cut before its first event, a catch-up from another peer, an all-clear, the partition quarantined, this node no longer the owner), so the same peer and offset recurring later raises again. Each end also raises the new recovery `STREAM_EVENT_EXCEEDS_READ_CAP_RESOLVED` (INFO, same subject), as does the gate when its block clears.
  [verified: `PartitionBackfillTest...oversizedEndedByACatchup_raisesAgainWhenItRecurs_andReportsEachEnd`, `...raisesTheBlockOncePerTransition`, `ByteCappedPeerGateTest.oversizedPeerCleared_whenTheGateActivates_reportsTheEnd`, `OwnerPromotionAlarmTest`; clearing only on the all-clear path reddens the first: one raise where two are expected]
- **While one peer is refused for an oversized event, another peer's unreachable alarm is no longer masked.** The two are independent conditions: the unreachable timer and its block have their own slot, and the oversized refusal no longer returns before the timer is evaluated. A recovered silent peer ends its own block and leaves the oversized one standing, never re-raising either.
  [verified: `ByteCappedPeerGateTest.oversizedPeer_doesNotMaskAnotherPeersUnreachableAlarm`, `...unreachablePeerRecovers_...`; reverting to the early return reddens both]
  [limit: the status read (`ownerActivationBlock`) shows one block per partition, the oversized one when both stand]
- **The members-unreachable wait is now an operator event, with a recovery.** It was a `LOG.warn("CRITICAL: ...")` with a TODO(#1574). It raises `STREAM_OWNER_PROMOTION_HOLDERS_UNREACHABLE` (CRITICAL) once per distinct block and `STREAM_OWNER_PROMOTION_HOLDERS_ANSWERING` (INFO) when every member answers or the node stops being the owner, both flood-guarded by the operator-warning sink. The other activation blocks stay a WARN and the partition status read.
  [verified: `OwnerPromotionAlarmTest`, `ByteCappedPeerGateTest.unreachablePeerRecovers_reportsItsEnd_andNotTheOversizedBlocks`; dropping the end report in `clearUnreachable` reddens the second]
- **`CLUSTER_EVENTS_MAX_EVENT_SIZE_BYTES` is held to the same one-frame ceiling.** `system:cluster-events:1.0.0` is built directly, not through the blueprint parser, so its maximum was `Long.MAX_VALUE` and bypassed the ceiling. A value above `StreamEventLimits.MAX_EVENT_SIZE_BYTES` now refuses the boot (marked choice: refuse, like every other out-of-range value of this variable, rather than clamp silently).
  [verified: `ClusterEventsLimitsTest...eventSizeAboveTheOneFrameCeiling_refusesTheBoot`, `...AtTheOneFrameCeiling_isAccepted`; restoring `Long.MAX_VALUE` reddens the first]
