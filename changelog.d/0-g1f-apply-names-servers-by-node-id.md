### Changed
- **`aether cluster apply` now lets the provider's server-name uniqueness decide a repeated create** (G1-f). A cloud server is named by its minted node id (lower case) with the `aether.op` label beside the existing `aether-node-id`, `aether-apply` and `aether-cluster` labels, so Hetzner refuses a second server for the same node. A `--resume` whose lookup finds no server for an INTENDED row (ABSENT) now creates it ONCE MORE under the SAME id instead of minting a new one; a create that landed after the lookup window answers `AlreadyExists` and is adopted, so two concurrent resumes make one server. `[verified: aether/cli/src/test/java/org/pragmatica/aether/cli/cluster/ApplyNameDedupTest.java]`
- A server is adopted (by the resume lookup, or after a refused name) only if it carries this cluster's AND this apply's labels. A name held by anything else is refused, typed (`NameHeld`), and never adopted; the row stays INTENDED.
- A CREATED row whose VM has vanished is still never created again: the audit marks it GONE and the next create takes a new id (a name is free again once its server is deleted).
