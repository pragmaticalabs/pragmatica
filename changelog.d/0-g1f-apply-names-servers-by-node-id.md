### Changed
- **`aether cluster apply` now lets the provider's server-name uniqueness decide a repeated create, where the provider has it** (G1-f). A cloud server is named `<cluster>-<nodeId>` (lower case) with the `aether.op` label beside the existing `aether-node-id`, `aether-apply` and `aether-cluster` labels. On **Hetzner** (the only provider that honours an operation id today), a `--resume` whose lookup finds no server for an INTENDED row (ABSENT) creates it ONCE MORE under the SAME id instead of minting a new one; a create that landed after the lookup window answers `AlreadyExists` and is adopted, so two concurrent resumes make one server. On **every other provider** nothing changes: an ABSENT id is not re-issued, the remainder mints a fresh id as before, because a late-landing original plus a re-issue would be two live servers for one node id. `[verified: aether/cli/src/test/java/org/pragmatica/aether/cli/cluster/ApplyNameDedupTest.java, ApplyReissueGateTest.java]`
- A server is adopted (by the resume lookup, or after a refused name) only if it carries this cluster's AND this apply's labels. A name held by anything else is refused, typed (`NameHeld`), and never adopted; the row stays INTENDED.
- A vanished server is never created again under its name: a CREATED row whose VM is gone is marked GONE by the audit (which runs after the executor, so the FIRST resume creates nothing for it). A SECOND resume of the same still-unfinished action counts GONE rows as not recorded and creates a replacement under a NEW id, never the vanished name. A TERMINATED or GONE row is never re-issued.
- Known residual, Hetzner: a create whose reply was lost and whose server is then deleted by anyone before the resume's first listing that would have shown it is re-created once by that resume (a name is free again once its server is deleted). Characterised by `ApplyReissueGateTest`, not closed.
