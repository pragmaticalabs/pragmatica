### Fixed (2026-11-24 — #3672: pg-parser rejected DOUBLE PRECISION, CHARACTER VARYING and BIT VARYING column types)
- **Multi-word SQL types parse in whole statements** (#3672). `NumericType`, `CharType` and `BitType` put `[ \t\r\n]+` between the words; those are parser rules over lexemes, so the class was tested against the next token's first character and never matched. The type fell through to a plain type name and the second word was left unconsumed (`expected end of input at 1:1`). The words are now consecutive keywords (any case, any whitespace including a newline), and `CstNavigator.tokenText` joins every leaf of a multi-word rule with one space, so the type resolves as `double precision` / `character varying` / `bit varying` instead of its first word. The error position reporting `1:1` for a later token is NOT changed here. [verified: `DdlTest$MultiWordTypes`, `CstExtractorTest$DataTypeExtraction`, `MigrationProcessorTest` (DOUBLE PRECISION column equals FLOAT8 column)]
