### Fixed (2026-11-20 — #3334: a redeploy could change an immutable key of a committed stream)
- **A redeploy that changed the partition count, lowered the replication or confirmation factor, changed the truncation policy, or changed `max_event_size` / `encryption_key_id` of an already committed stream was accepted at deploy validation** and only dropped later on the node by `StreamConfigChangeNotApplied`. It is now refused before any command is built, by the named rules `partition-count-immutable`, `durability-only-increases`, `truncation-policy-immutable` and `storage-key-immutable`; the message names the key, and the committed row is unchanged. Raising a factor, an unchanged redeploy, a first deploy and a `latest` version (no concrete address at deploy time) are not refused. `StreamConfigChangeNotApplied` stays the backstop for a local KV that lags a commit.
- A key that is still inert keeps its inert refusal: the inert gate wins and the committed row is not compared for that alias. `encryption_key_id` is inert today, so its `storage-key-immutable` arm is pinned on model objects, and the deploy-path test for it is `@Disabled` until the key is wired (#253).
