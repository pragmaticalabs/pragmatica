### Changed (2026-11-15 — #2767: FSM2 is the default deployment engine)
- **New clusters run the FSM2 deployment engine by default** (#2767, FSM replacement plan F6). `AetherNodeConfig` and the Ember/Forge harness selector default to FSM2; the `legacy` value of the harness engine property still selects LEGACY until LEGACY is deleted (F7). A cluster's committed engine marker still decides: a node whose configured engine disagrees refuses itself (`deployment-engine-mismatch`). [mechanism: one default at `AetherNodeConfig` and one at `EngineSelector`; unit tests `EngineSelectorTest`, `EmberClusterDefaultEngineTest`, `AetherNodeConfigRedactionTest`]
- **A backup without an engine marker (rc4 and earlier) restores into the running engine** (plan 3.2 delta (a)). The restore's finish keeps a marker minted locally during the restore, or mints the restoring node's own engine marker; it no longer removes the marker, which left an FSM2 cluster reading LEGACY and refusing every node. [mechanism: the marker arm of the restore finish targets the backup's marker, else the local one, else the running engine's; `BackupRestoreCoordinatorTest`, no multi-node failure injection]
- **An IN_PROGRESS deployment outcome with no apply record is closed at an FSM2 leader's activation** (plan 3.2 delta (b)): FAILED for the same attempt, cause `restored-without-apply`, announced once as `outcome-closed-unapplied` (INFO). A backup taken mid-deployment no longer restores an outcome nothing would ever complete. Recovery: republish the blueprint. [mechanism: `Rebuild` drafts the close for every such outcome in blueprint-id order; in-JVM FSM harness test `UnappliedOutcomeRebuildTest`]
