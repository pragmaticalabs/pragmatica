### Fixed (2026-09-29 — #1100: `jbct lint --format json|sarif` reported a coverage-gap run as a clean document)
- **`jbct lint --format json` and `--format sarif` now state the run's coverage inside the document.** A run that could not parse a collected file (exit 2) used to emit `[]` / `results: []` with no in-document signal, so a SARIF uploader that ignores the exit status recorded a clean scan for files nobody analysed. A run that found no Java files emitted the same empty document and exited 0. [verified: jbct/jbct-cli/src/test/java/org/pragmatica/jbct/cli/LintCommandMachineFormatTest.java — both gap shapes fail the documented clean-scan predicate, a complete clean run passes it]
- **Breaking (pre-GA): `jbct lint` exits `2` when it found no Java files**, in every output format, instead of `0`. Examining nothing is a coverage gap, never a pass. `check`, `score` and `format --check` are unchanged. No workflow or script in this repository runs the `jbct` CLI's `lint` (searched `.github/`, every `*.sh`, `*.yml` and `Makefile`). [verified: jbct/jbct-cli/src/test/java/org/pragmatica/jbct/cli/LintCommandMachineFormatTest.java]
- **Breaking (pre-GA, no shim): `--format json` is now one object, not a bare array:** `{ "collected", "examined", "skipped": [{file, reason}], "diagnostics": [...] }`. SARIF gains `runs[0].invocations[0]` with `executionSuccessful` (false when a file was skipped) and `toolExecutionNotifications` (an `error` per skipped file, or one saying nothing was examined; `executionSuccessful` is false in both cases). The clean-scan `jq` predicates are in `jbct/README.md`.
