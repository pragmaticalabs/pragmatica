### Fixed (2026-09-13 — #893: `ContentStoreFactory.close` was a silent no-op override)
- **`ContentStoreFactory` overrode `ResourceFactory.close(T)` with `return Promise.unitPromise()`** — a close that reports success while releasing nothing, indistinguishable from a working one, and the same shape as #271 on a different resource. Found by the #891 audit of all 23 non-test `ResourceFactory` implementations; it was one of two no-op overrides (the other is `NotificationSenderFactory`, #271).
- **The override is removed rather than "made real", because there is nothing for it to release.** `DefaultContentStore` holds a `StorageInstance`, a `ContentStoreConfig` record and a `CompressionCodec`. The storage instance is the NODE's: `AetherNode.registerRuntimeExtensions` registers the node's content tier as the `StorageInstance` extension every `ContentStore` is provisioned over, and the node shuts it down. Closing it from one slice's `releaseAll` would shut the node's content storage under every other slice — the #268 R2 use-after-close, arriving through a "properly implemented" close. The codec and the config own no handles. So the resource now falls through to `ResourceFactory`'s default dispatch, which names the "no close convention" outcome (`noCloseConvention`, DEBUG) instead of succeeding silently. A comment on the factory records the reason so the override is not re-added as a tidy-up. [verified: `ContentStoreFactoryCloseTest#factory_declaresNoCloseOverride_soReleaseTakesTheDefaultDispatch` (`aether/aether-storage`) — a reflection pin on the declared methods, because a no-op override and the default dispatch return identical promises and no behavioural probe can tell them apart; reddens with `["close", "close"]` (the override plus its bridge) when the override is restored]
- The reason is pinned as behaviour, not only as prose: releasing a provisioned content store must not shut down the node-owned storage instance it was provisioned over. [verified: `ContentStoreFactoryCloseTest#close_doesNotShutDown_theNodeOwnedStorageInstance` — a `StorageInstance` proxy counting `shutdown()` calls reads zero after `provision` then `close`. This guards the overcorrection ("close it properly"); it passes against the old no-op too and is not the pin for the removal.]
- **The release path this sits on is real and reachable from an unload**: `SliceStore.unloadSlice` → generated `stop()` → `SliceAwareResourceProvider.releaseAll` → `SpiResourceProvider.releaseAll` → `closeThroughOwningFactory` → `factory.close` → default dispatch, pinned end to end by `ReleaseIdentityTest#unloadSlice_closesTheResourceTheSliceProvisioned` (#892). No new close path is added here.
- Audit of the other `close` overrides at this tip, per the ticket's acceptance 3: `NotificationListenerFactory` (real — `NotificationListenerHandle.close()`), `DurableEntityFactory` (real — `fenced.unload()`, logged on throw), `CacheInterceptorFactory` / `IdempotencyInterceptorFactory` (real since #898 — registry holder release), `NotificationSenderFactory` (**still a no-op — #271**).
