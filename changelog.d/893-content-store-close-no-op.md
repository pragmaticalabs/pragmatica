### Fixed (2026-09-13 — #893: `ContentStoreFactory.close` was a silent no-op override)
- **`ContentStoreFactory` overrode `ResourceFactory.close(T)` with `return Promise.unitPromise()`** — a close that reports success while releasing nothing, indistinguishable from a working one, and the same shape as #271 on a different resource. Found by the #891 audit of all 23 non-test `ResourceFactory` implementations; it was one of two no-op overrides (the other is `NotificationSenderFactory`, #271).
- **The override is removed rather than "made real", because there is nothing for it to release.** `DefaultContentStore` holds a `StorageInstance`, a `ContentStoreConfig` record and a `CompressionCodec`. The storage instance is the NODE's: `AetherNode.registerRuntimeExtensions` registers the node's content tier as the `StorageInstance` extension every `ContentStore` is provisioned over — never a slice's to close. Closing it from one slice's `releaseAll` would shut the node's content storage under every other slice — the #268 R2 use-after-close, arriving through a "properly implemented" close. (The node does not shut that instance down at stop either — `AetherNode.stop()` calls no `StorageInstance.shutdown()`; that gap is #1078 and is not touched here.) The codec and the config own no handles. So the resource now falls through to `ResourceFactory`'s default dispatch, which names the outcome in code (`noCloseConvention`) and emits it to `java.util.logging` at FINE — **which a deployed node does not show**: `System.Logger` binds to JUL, the node's classpath carries no `log4j-jpl`, and JUL's default handler drops FINE, so on a node this is as silent as before (#1077). A comment on the factory records the reason so the override is not re-added as a tidy-up. [verified: `ContentStoreFactoryCloseTest#factory_declaresNoCloseOverride_soReleaseTakesTheDefaultDispatch` (`aether/aether-storage`) — a reflection pin on the declared methods; reddens with `["close", "close"]` (the override plus its bridge) when the override is restored] [verified: `#close_emitsTheNoCloseConventionRecord_throughTheDefaultDispatch` — a JUL handler at `ALL` on the `ResourceFactory` logger captures exactly one "No close convention … DefaultContentStore" record through the default dispatch and zero with the no-op override restored (`Expected size: 1 but was: 0` under mutation); this is the behavioural discriminator beside the reflection pin]
- The reason is pinned as behaviour, not only as prose: releasing a provisioned content store must not shut down the node-owned storage instance it was provisioned over. [verified: `ContentStoreFactoryCloseTest#close_doesNotShutDown_theNodeOwnedStorageInstance` — a `StorageInstance` proxy counting `shutdown()` calls reads zero after `provision` then `close`. This guards the overcorrection ("close it properly"); it passes against the old no-op too and is not the pin for the removal.]
- **The release path this sits on is real and reachable from an unload**: `SliceStore.unloadSlice` → generated `stop()` → `SliceAwareResourceProvider.releaseAll` → `SpiResourceProvider.releaseAll` → `closeThroughOwningFactory` → `factory.close` → default dispatch, pinned end to end by `ReleaseIdentityTest#unloadSlice_closesTheResourceTheSliceProvisioned` (#892). No new close path is added here.
