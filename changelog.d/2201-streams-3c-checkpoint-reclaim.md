### Changed (2026-10-31 — #2201 PR-3c: entity checkpoint blocks are reclaimed)
- **BREAKING (pre-GA flag day): the entity checkpoint block layout changes.** Every checkpoint block now opens with an identity header (`CKPTID01`, the keyspace, the partition and the claim), so two partitions, or two claims, with byte-identical folds no longer share one content-addressed block. A build without the header reads a new block as "no usable checkpoint" (its first byte is neither snapshot version) and rebuilds the partition from its log: safe, but slow, and the rebuild refuses where the log below the claim is gone. Upgrade by coordinated replacement. Blocks written before this change are still read. Such a block has no identity, so pointers of several partitions, or of several keyspaces, with byte-identical folds may name one block; the delete-time check (below) keeps it while any pointer names it.
- **Fixed: a checkpoint block the pointer stopped naming was never reclaimed, so every advancing checkpoint (one full copy of the fold per 30 s tick) stayed in stream storage, its DHT copies included, and counted against `dht_segment_max_bytes`.** After a confirmed pointer swap the writer deletes the block the replaced pointer named once 60 s have passed (a loader that read the old pointer just before the swap and loses the race folds from the log); after a swap the fenced applier refused, it deletes its own new block at once. The delete goes through `StorageInstance.delete`, which removes the block from every tier: on the DHT a write-quorum remove that leaves tombstones, carried by anti-entropy to a replica that missed it (not under `FULL` replication). A delete the store refuses is retried five times with backoff, then logged at WARN and left. A block is deleted only when its claim is below the committed claim, which never falls back while the fenced applier is the only writer of the pointer; a block displaced at an equal claim waits for the next swap that passes it. The applier is not the only writer (a snapshot restore bypasses the fence; a pointer removed and rewritten at the same claim names its old block again), so the pointers are read again when the delete runs, on every attempt, and a block a pointer names in that node's view is not deleted. The check only withholds deletes: a pointer that node has not applied yet, or one committed between the read and the quorum remove, is not seen. [verified: `aether/node/src/test/java/org/pragmatica/aether/resource/entity/EntityCheckpointReclaimTest.java`, `aether/ember/src/test/java/org/pragmatica/aether/ember/EmberCheckpointReclaimTest.java`]
- Not reclaimed (stated, L-12): the blocks written since the last confirmed swap when a node crashes between the block put and the swap or between the swap and the delete; a block displaced at an equal claim when the node restarts first; the node-private memory and disk copy on a node other than the deleting writer (after a handover, the previous owner's own copy); a block whose delete the check withheld because another pointer named it, when that pointer is later removed rather than swapped (a swap deletes it in turn). No sweep exists.
- Known limit (DHT, not this change's own): a replica that returns as a member with its store intact after `tombstone_retention` (default 1 h), when the tombstone has been collected, can bring a deleted block back. No pointer names it, so it is a leak.
