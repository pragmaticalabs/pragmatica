### Fixed (2026-10-08 — #1727, M2 mitigation: stranded lost data on a QUIC connection)

- **A lane data write now starts an "activity kick" on its connection.** netty-quic can run an elapsed retransmission timer inline from inside `connectionSend()`; quiche then declares the last in-flight packet lost, nothing re-sends it, and the data waits for an unrelated event (`fin-199`). The only public lever that reaches `connectionSend()` is a non-empty stream write, so each `QuicPeerConnection` now writes its existing CONTROL-lane `KeepAlive` every 100 ms after a data write, until 5 s pass with no data write (about 10 small frames/s for 5 s after each data write; the transport's own CONTROL-lane keepalive does not count as a data write, and an idle link measured 0 kick frames over 4 s on two real networks; no wire change). The kick belongs to the connection and stops when it closes (a superseded connection is closed at once, so it gets no extra time); it is silenced while blackholed. Bare `QuicClusterClient`/`QuicClusterServer` users without `QuicClusterNetwork` are not covered. The real fix is upstream netty (defer the elapsed timer); an enabled tripwire test fails when the pinned netty has it, as the cue to remove the kick.
