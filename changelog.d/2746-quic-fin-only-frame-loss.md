### Fixed (2026-11-07 — #2746: HTTP/3 exchanges stalled ~5 s when a FIN-only QUIC frame was lost)
- **An HTTP/3 response or request could stall until the idle timeout (~5 s, the client then reads `closed`).** The stream was ended by `shutdownOutput()` after the last write, a FIN-only STREAM frame; quiche (netty-codec-native-quic 4.2.18, unchanged in 4.2.20) never retransmits that frame when its loss is detected in the same batch as earlier data loss on the stream, so the peer held every byte but never saw the stream end. The HTTP/3 response writer (`Http3Server`) and the HTTP/3 request writer (`NettyHttpOperations`) now end the stream with the last bytes themselves: a `QuicStreamFinisher` ahead of the frame codec turns the final frame's bytes into one STREAM frame with `FIN` set, and no FIN-only frame is sent. Workaround for an upstream quiche defect, not yet reported upstream. [verified: `Http3ResponseFinLossTest`, `NettyHttpOperationsFinLossTest`, each dropping the tail datagrams deterministically, red on the release-1.0.0-rc5 writers; `Http3FinLossTest` pins the quiche defect on the wire, with a tripwire that fails once quiche retransmits a lost FIN-only frame]
- **An HTTP/3 response with an empty body was reset instead of answered.** The writer ended it with an empty buffer that the HTTP/3 frame codec refuses ("Frame of type EmptyByteBuf unexpected"), so the stream was reset with `H3_INTERNAL_ERROR`. The `FIN` now rides on the HEADERS frame. [verified: `Http3ResponseFinLossTest.emptyBodyWithHeadersTailLost_responseStillEnds`]
