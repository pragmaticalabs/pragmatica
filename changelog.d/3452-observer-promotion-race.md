### Fixed (2026-11-20 — #3452: an observer promotion or a quorum return decided on the caller thread could overwrite or drop a queued quorum-loss pause)
- **`RabiaEngine` decides an observer's promotion on its apply executor, in the same step as the write.** `authorizeActivation` tested `isObserving()` on the caller thread and queued a promotion that wrote `Idle` unconditionally, so a quorum-loss pause queued ahead of it was overwritten and the engine left a pause it should hold. The promotion now applies only from `Observing`; from any other state it is a no-op, and the authorization is kept (`observerMode` is cleared), so a paused observer resumes as a voter.
- **A quorum `ACTIVE` is dispatched on the apply executor too.** The same caller-thread read in `handleClusterActive` saw an engine whose pause was still queued as active, dropped the `ACTIVE` as an echo, and left the engine `Paused` with quorum present until the next notification.
- Pinned by `RabiaObserverPromotionRaceTest` (the executor is parked, the pause and then the promotion or the quorum return are queued behind it; both arms red before the fix).
- **A restore is announced before the Decisions buffered during synchronisation are applied.** `activate`, `activateAsObserver` and `doResumeFromPause` drained the buffer first, so live Decisions applied, and notified, ahead of the restore's replay burst, against its "world-as-of-N, then N+1 onward" contract; on an observer the announce fired from inside the drain. Pinned by `RabiaAnnounceBeforeDrainTest` (voter and observer activation; both red before the fix). The resume path takes the same order and is not separately probed.
