### Fixed (2026-11-02 — #2579: a failed ACTIVATE write leaves a slice LOADED until a leader change)
- **A slice whose one ACTIVATE write failed served nothing until the leader changed.** The leader wrote ACTIVATE once, when the slice reached LOADED, and only logged a failure. LOADED is neither in progress nor transitional, so neither reconcile nor the stuck-slice remediator acted on it. Under consensus-lane backpressure this stranded a slice for minutes (flake #2567).
- **A failed ACTIVATE write is now retried.** After 5, 10, 20 and 40 s, each jittered by ±20%, the leader re-reads the committed state. If the state is still LOADED, it re-issues ACTIVATE through the same schema-hold and dependency checks as the first ACTIVATE. A write that timed out but applied is not issued again. [verified: `aether/aether-deployment` `ActivateWriteRecoveryTest` (failed write retried; applied-after-all write not re-issued)]
- **Reconcile re-issues ACTIVATE for any slice stranded in LOADED.** This covers a lost write, not only a failed one. The slice must have been LOADED for longer than the activation timeout (ACTIVATING's 90 s), and the committed state must still be LOADED. It fires once per window, and a slice held by its schema or a dependency stays held. [verified: `ActivateWriteRecoveryTest` (lost write re-issued only after the timeout; a held slice stays held)]
- **A re-issued ACTIVATE is a compare-and-set on the committed LOADED value**, not a plain write. A plain write of a node-artifact value is not merged. So an earlier ACTIVATE that applied late, followed by the node's ACTIVATING, would otherwise be overwritten back to ACTIVATE. [verified: `ActivateWriteRecoveryTest`] [mechanism: `KVStore.handleLeaderTransaction` applies a mutation only when its expected value equals the committed one]
- Operator recovery is unchanged and no longer needed for this case: a slice still LOADED after a reconcile window has its ACTIVATE re-issued automatically. A leader change also still re-issues it.
