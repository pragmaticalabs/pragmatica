### Changed (2026-09-08 — #887: security overrides now take effect on the node hosting the route)
- **Operator-visible behaviour change — read before upgrading a running cluster.** Requests that a node previously served will now be refused. Under the shipped `security_mode = "api-key"`, any route covered by a blueprint `[security.overrides]` entry was, until this release, enforced only when the request arrived at a node that did **not** host it; a request arriving at the hosting node was authorized against the route's own declared policy instead. Those requests are now authorized against the override.
- **What an existing deployment must do.** Before upgrading, review every `[security.overrides]` entry in your active blueprints against the callers that use those routes. A caller that has been reaching an overridden route without satisfying the override — most visibly an API key lacking a role an override requires — has been relying on the gap and will start receiving `403`. Grant the caller the required role, or withdraw the override, before rolling the upgrade out. Overrides can be changed at runtime by republishing the blueprint and take effect on the next request, so a lockdown that proves too broad can be relaxed without a redeploy.
- **The reported state was also wrong, in the direction that hides this.** `GET /api/v1/routes` read the replicated KV entry, which carried the override, while the hosting node enforced the raw policy — so an operator verifying a lockdown through the management API was told it was in force when it was not. Any lockdown verified that way before this release should be re-verified against the live path, not the report.
