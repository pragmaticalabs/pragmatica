### Changed (2026-09-08 — #887: security overrides now take effect on every node, not just the one that received them)
- **Operator-visible behaviour change — read before upgrading a running cluster.** Requests that were previously served will now be refused. Under the shipped `security_mode = "api-key"`, a route covered by a blueprint `[security.overrides]` entry was, until this release, enforced on at most one node: the one that happened to serve `POST /api/v1/blueprints`. Every other node held no overrides at all, and the node hosting the route authorized against the route's own declared policy instead of the override. Both gaps are closed, so overrides now govern requests arriving at any node.
- **What an existing deployment must do.** Before upgrading, review every `[security.overrides]` entry in your active blueprints against the callers that use those routes. A caller that has been reaching an overridden route without satisfying the override — most visibly an API key lacking a role an override requires — has been relying on the gap and will start receiving `403`. Grant the caller the required role, or withdraw the override, before rolling the upgrade out. Overrides can be changed at runtime by republishing the blueprint and take effect on the next request, so a lockdown that proves too broad can be relaxed without a redeploy.
- **The reported state was also wrong, in the direction that hides this.** `GET /api/v1/routes` read the replicated KV entry, which carried the override, while the hosting node enforced the raw policy — so an operator verifying a lockdown through the management API was told it was in force when it was not. Any lockdown verified that way before this release should be re-verified against the live path, not the report.
- **Overrides now survive a restart.** They were held only in memory on one node, so a restart or a DEPLOYMENT task-group migration silently dropped them. If you have been restarting nodes and re-applying blueprints to "make overrides stick", that workaround is no longer needed.
- **Several active blueprints declaring different `override_policy` values now log a warning and fall back to `strengthen_only`** instead of the last one applied winning per node. If you rely on more than one blueprint carrying overrides, give them a single policy.
