### Fixed (2026-10-28 — #2235: release SHA256SUMS covered 4 of 23 assets and recorded build paths)
- **`SHA256SUMS` listed 4 jars under `target/` paths**, so no platform archive could be verified and `sha256sum -c` failed on a downloaded release. It is now generated by a final `release-checksums` job that runs after the linux-amd64, macOS and linux-arm64 jobs, over every published asset, by bare file name, in `sha256sum -c` format.
- The job fails the release if an asset published by the release is missing from `SHA256SUMS`, if it names anything that is not an asset, or if `sha256sum -c` fails on a fresh download of the published release. `SHA256SUMS` itself is not listed in itself. [verified: tools/test_release_checksums.py, which runs scripts/release-checksums.sh on a 22-asset directory and goes red when one asset is dropped]
- The release workflow gains a `workflow_dispatch` dry run that builds every asset and runs the same generate and verify over them, publishing nothing: no release, no upload, no image push (each guarded by the tag trigger, not by an input). [verified: tools/test_release_checksums.py pins the push-only guard on every publishing step; the real job on the PR-triggered dry run is not yet exercised]
- `aether/install.sh` and `aether/upgrade.sh` look each archive up by name in `SHA256SUMS` and skip verification when nothing matches, so with bare asset names archive verification now actually happens. [mechanism: read from the installers, not covered by a test]
- On a pull request that touches `scripts/release-checksums.sh` or `release.yml` the same dry run executes, so the real job runs in that PR's own CI.
