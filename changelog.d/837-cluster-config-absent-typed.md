### Fixed (2026-09-04 — #837: cluster config/status/upgrade against a cluster with no stored config answered 500)

- **`GET /api/v1/cluster/config`, `GET /api/v1/cluster/status`, and `POST /api/v1/cluster/upgrade` against a fresh, unconfigured cluster (e.g. right after a `docker compose down -v` volume wipe) all answered HTTP 500.** The two GETs shared `ClusterConfigRoutes`'s `ConfigNotFoundError` — the same bare, statusless `Cause` #335/#835 traced for `POST /api/v1/cluster/scale` — defaulting to 500 through `ProblemResponses.resolveStatus`. Upgrade routed through the same promise-failing lookup instead of branching on absence.
- **The two reads now answer HTTP 404** (`ConfigNotFoundError` implements `HttpStatusAware`, mapping to `HttpStatus.NOT_FOUND`) — absence of a resource on a GET, not server failure. `GET /api/v1/cluster/status` was considered for a 200 with an explicit "config absent" field instead, and rejected: `ClusterStatusResponse` mixes config-derived fields (`clusterName`, `desiredVersion`, `desiredCoreCount`) with live node/membership data, and fabricating the former or adding a new flag would misrepresent a shape this route has never returned before.
- **Upgrade now refuses with a typed `ClusterConfigError.NoConfigToUpgrade`, HTTP 409**, mirroring #335/#835's `NoConfigToScale`: an `UpgradeRequest` carries only `targetVersion`, not the cluster name, topology, or deployment settings a config requires, so there is no honest way to synthesize one. The response names the actual recovery (`aether cluster bootstrap <aether-cluster.toml>`, then retry the upgrade) [verified: aether/node/src/test/java/org/pragmatica/aether/api/routes/ClusterConfigRoutesNoConfigTest.java].
- **`aether/tests/integration/lib/cluster.sh`'s `scale_cluster` chaos helper** previously logged every non-2xx scale response identically, body truncated and unparsed. It now extracts and prints the RFC 9457 `detail` field via a new `_extract_problem_detail` helper (jq with a grep/sed fallback) and labels 404/409 as an expected typed refusal versus a genuine failure for any other status [mechanism: cluster.sh non-2xx branch, no change to the function's return code].
- Docs updated: `management-api.md` gains a "Not Found (404)" note under `GET /api/v1/cluster/config` and `GET /api/v1/cluster/status`, and a "Conflicts (HTTP 409)" note under `POST /api/v1/cluster/upgrade`, each naming the recovery command [mechanism: docs cross-checked against the message text the route emits].
