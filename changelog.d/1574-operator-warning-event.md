### Added (2026-09-27 — #1574: operator warnings reach the cluster event log, step 1)
- **New `OPERATOR_WARNING` cluster event (wire tag 292).** Its `details` carry `code`, `subsystem`, `subject`, `nodeId` and `suppressedSince`. Operators can now identify, by a stable `code`, conditions that were previously only in one node's log. `GET /api/events` and `aether events` cannot filter on it yet: fetch the feed and match `details.code`. [verified: aether/node/src/test/java/org/pragmatica/aether/api/ClusterEventAggregatorTest.java] (unit-level, through the real cluster-events stream partition and codec)
- **`OperatorWarnings.raise` (`integrations/utility`) logs and emits from one call site.** The log line is always written first, prefixed with `[code]`. It never waits for the event log: the node's sink hands each warning to a bounded queue (256) drained by one virtual thread, and a burst beyond that drops the event (never the log line) and is counted and reported by the next accepted warning. A publisher that throws is logged and dropped; `raise` never throws a non-fatal exception (a `VirtualMachineError` is rethrown by design). Components reach their own node's event log through a per-instance `OperatorWarningSink` bound by `AetherNode`, so Ember's in-JVM nodes never cross-attribute. Codes come from the single `OperatorWarningCode` catalogue, which is tested for uniqueness. [verified: integrations/utility/src/test/java/org/pragmatica/utility/warning/OperatorWarningsTest.java — a 2 s publisher leaves `raise` under 50 ms; a synchronous hand-off turns it red]
- **Emits are throttled to one per `(code, subject)` per 60 s window. Log lines are not throttled.** The next emitted event reports how many were held back as `suppressedSince`. A window is consumed only by an event that is published: when the publish fails (replay, bootstrap), the next occurrence is admitted and counts the lost one. Keys idle for 120 s are evicted once a minute, so the throttle does not grow without bound; held-back counts on evicted keys are reported in one aggregate WARN line. [verified: `ClusterEventAggregatorTest` — the flood, eviction (100k keys) and failed-first-publish tests]
- **Three proof sites converted:**
  - SWIM co-confirmation kill-gate hold (`swim-kill-gate-held`, WARNING).
  - Worker core-absence fence (`core-absence-fence`, CRITICAL). Its log line moves from WARN to ERROR.
  - Replica fsync failure that withholds an ack (`replica-fsync-failed`, WARNING).
  - Each site has a test that its warning reaches the sink. [verified: the site tests in `SwimDeathPathCoConfirmationTest`, `CoreAbsenceDetectorTest`, `ReplicationReceiveHandlerTest`]
  - The core-absence binding in `AetherNode` is pinned end to end: `CoreAbsenceFenceOrderingTest` isolates a real worker in Ember and reads the warning from that worker's own aggregator. [verified: aether/forge/forge-tests/src/test/java/org/pragmatica/aether/forge/CoreAbsenceFenceOrderingTest.java — unbinding it turns the test red] An isolated worker cannot reach the cluster event log, so that event is not published there; its log line is the record.
  - [unverified: wiring not pinned] The SWIM and replication bindings in `AetherNode` have no test that constructs them.
- About 230 remaining WARN/ERROR sites (per the audit) are still log-only and will be converted by their owners.
