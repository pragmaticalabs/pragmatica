### Added (2026-09-27 — #1574: operator warnings reach the cluster event log, step 1)
- **New `OPERATOR_WARNING` cluster event (wire tag 292).** Its `details` carry `code`, `subsystem`, `subject`, `nodeId` and `suppressedSince`. Operators can now identify, by a stable `code`, conditions that were previously only in one node's log. `GET /api/events` and `aether events` cannot filter on it yet: fetch the feed and match `details.code`. [verified: aether/node/src/test/java/org/pragmatica/aether/api/ClusterEventAggregatorTest.java] (unit-level, through the real cluster-events stream partition and codec)
- **`OperatorWarnings.raise` (`integrations/utility`) logs and emits from one call site.** The log line is always written first, prefixed with `[code]`. It never waits for the event log: the node's sink hands each warning to a bounded queue (256) drained by one virtual thread, and a burst beyond that drops the event (never the log line) and is counted and reported by the next accepted warning. A publisher that throws is logged and dropped; `raise` never throws a non-fatal exception (a `VirtualMachineError` is rethrown by design). Components reach their own node's event log through a per-instance `OperatorWarningSink` bound by `AetherNode`, so Ember's in-JVM nodes never cross-attribute. Codes come from the single `OperatorWarningCode` catalogue, which is tested for uniqueness. [verified: `OperatorWarningsTest.raise_slowPublisher_returnsWithoutWaitingForIt` — with a 2 s publisher, `raise` returns within the pinned 1 s bound; a synchronous hand-off turns it red (measured 2,024 ms)]
- **Emits are throttled to one per `(code, subject)` per 60 s window. Log lines are not throttled.** The next emitted event reports how many were held back as `suppressedSince`. Operator-warning events go through cluster-event redelivery (#1640/#1653), like every other cluster event: a publish that fails transiently is held and re-sent, and it keeps its window, so no second event is admitted while the first is still being delivered. Only an event that is LOST (suppressed during replay, or dropped by redelivery: permanent failure, expiry past its 5-minute horizon, overflow) reopens the key after a short 5 s retry window; the next occurrence after it is admitted and counts the lost one. A key whose events keep being lost therefore makes at most one attempt per 5 s, not one per occurrence, and the first success restores the 60 s window. [verified: `ClusterEventAggregatorTest.onOperatorWarning_transientPublishFailure_isRedelivered_andDoesNotReopenTheWindow`, `onOperatorWarning_eventRedeliveryGivesUpOn_reopensTheShortWindow` — unit-level] Keys idle for 120 s are evicted by a once-a-minute task, so the throttle does not grow without bound (the schedule is pinned in the node assembly by `OperatorWarningWiringTest`); held-back counts on evicted keys are reported in one aggregate WARN line. [verified: `ClusterEventAggregatorTest` — the flood, eviction (100k keys), failed-first-publish and always-failing-publish tests]

  - Worker core-absence fence (`core-absence-fence`, CRITICAL). Its log line moves from WARN to ERROR.
  - Replica fsync failure that withholds an ack (`replica-fsync-failed`, WARNING).
  - Each site has a test that its warning reaches the sink. [verified: the site tests in `SwimDeathPathCoConfirmationTest`, `CoreAbsenceDetectorTest`, `ReplicationReceiveHandlerTest`]
  - The core-absence binding in `AetherNode` is pinned end to end: `CoreAbsenceFenceOrderingTest` isolates a real worker in Ember and reads the warning from that worker's own aggregator. [verified: aether/forge/forge-tests/src/test/java/org/pragmatica/aether/forge/CoreAbsenceFenceOrderingTest.java — unbinding it turns the test red; the test is `@Tag("Heavy")`, so default CI does not run it] An isolated worker cannot reach the cluster event log, so that event is not published there; its log line is the record.
