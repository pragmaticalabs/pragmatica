### Changed (2026-11-04 — #2591: the database-side migration fence, tier 1: PostgreSQL and MySQL/MariaDB)
- **A schema migration on PostgreSQL or MySQL/MariaDB now runs on ONE dedicated database session that holds a session-scoped database lock for the whole run** (`pg_try_advisory_lock(0x41455448, 1)` per database; `GET_LOCK` on `aether_mig:` + 40 hex of SHA-256 of the lower-cased schema, 51 characters). The lock is taken first; bootstrap, the ownership claim, the applied-history read and every statement, checkpoint and history write follow on that session, and each write re-checks that the session still holds the lock. Leaving the run closes the session, which releases the lock. A second runner while the first still executes runs nothing, reads nothing and fails with `MigrationFencedInDatabase` naming the holding session (PostgreSQL `pid`/`application_name aether-mig:<node>`; MySQL connection `id`), which the orchestrator retries with its bounded backoff [verified: `MigrationFencePgTest` (through the production JDBC and pg-async connectors) and `MigrationFenceMysqlTest` (JDBC), T1, T4, T7, T9].
- **Holder death:** a transactional script of a dead holder rolls back and the next holder acquires only once its session is gone; on the autocommit path (a `CREATE INDEX CONCURRENTLY`, every MySQL/Oracle file) a statement the dialect can run in a transaction now commits in the same transaction as its checkpoint, so it is applied exactly once across holder deaths; a statement that cannot is re-attempted at most once, sequentially [verified: `MigrationFencePgTest` T4, T5, T5b; `MigrationFenceMysqlTest` T5b].
- **`CREATE INDEX CONCURRENTLY` that leaves an INVALID index** (cancelled by the statement timeout, or its session died) now fails the run with `InvalidIndexLeftBehind` naming the index and `DROP INDEX CONCURRENTLY` as the repair, instead of a resumed `IF NOT EXISTS` passing over it silently. Name every index in a migration: an unnamed concurrent build cannot be checked [verified: `MigrationFencePgTest` T11].
- **Refused, never run unfenced:** Galera (`wsrep_on=ON`) and multi-primary group replication (`GET_LOCK` is node-local there), a MySQL connection without a default schema, and a session that does not hold the lock it took (a transaction-mode pooler such as PgBouncer swapped it): `FenceUnavailable`, permanent. Migrations need a direct connection or session pooling, and one extra server connection per running migration. A PostgreSQL-configured datasource whose `version()` names CockroachDB gets no advisory lock (CockroachDB's acquire nothing); its fence comes in FDB-2b, as do SQL Server, Oracle, DB2, SQLite and H2, which run as before.
- **R2DBC and postgres-async pinned sessions set `statement_timeout` and `lock_timeout` first**, both to the statement bound (the migration timeout, 15 minutes by default), so a hung statement no longer holds the dedicated connection and its lock forever. `lock_timeout` is not shorter on purpose: a concurrent index build's lock waits share the statement's budget [verified: `R2dbcSqlConnectorPinnedTest`, `PgAsyncSqlConnectorPinnedTest`].
- **Fixed:** an R2DBC pinned session's `update` of a statement with no row count (`SET`) failed with `NoResult`; it now returns 0 [verified: `R2dbcSqlConnectorPinnedTest.update_onAPinnedSession_setWithNoRowCount_returnsZero`].
- **Known, not changed here:** schema migrations do not run through the R2DBC transport at all, fence or not: the history repository binds `?` placeholders, which r2dbc-postgresql rejects (and DDL through it also fails, `Expected single result but got 2`). Pinned by the enabled tripwire `MigrationFencePgTest.tripwire_r2dbcCannotRunAMigration_enableTheR2dbcRowsWhenThisGoesRed`.
- `SchemaMigrations.schemaMigrations()` is replaced by `schemaMigrations(TimeSpan statementTimeout)`.
