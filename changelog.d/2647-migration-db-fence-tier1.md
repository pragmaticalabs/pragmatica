### Changed (2026-11-04 — #2591: the database-side migration fence, tier 1: PostgreSQL and MySQL/MariaDB)
- **A schema migration on PostgreSQL or MySQL/MariaDB now runs on ONE dedicated database session that holds a session-scoped database lock for the whole run** (`pg_try_advisory_lock(0x41455448, 1)` per database; `GET_LOCK` on `aether_mig:` + 40 hex of SHA-256 of the lower-cased schema, 51 characters). The lock is taken first; bootstrap, the ownership claim, the applied-history read and every statement, checkpoint and history write follow on that session, and each write re-checks that the session still holds the lock. Leaving the run closes the session, which releases the lock. A second runner while the first still executes runs nothing, reads nothing and fails with `MigrationFencedInDatabase` naming the holding session (PostgreSQL `pid`/`application_name aether-mig:<node>`; MySQL connection `id`), which does NOT consume a migration attempt: the schema stays `PENDING` and is re-dispatched with the retry backoff capped at 45 s, and from the 3rd consecutive fenced attempt on each one raises the operator warning `schema-migration-fence-held` naming the holder (until FDB-3 adds a FENCED state) [verified: `SchemaOrchestratorLeaseTest.HeldInTheDatabase`]. A runner refused at acquire never runs the courtesy unlock (`pg_advisory_unlock_all()` / `RELEASE_ALL_LOCKS()`), nor does one that lost the lock mid-run, so a refused runner cannot drop another client's lock on a shared server session [verified: `MigrationFencePgTest` (through the production JDBC and pg-async connectors) and `MigrationFenceMysqlTest` (JDBC), T1, T4, T7, T9].
- **Holder death:** a transactional script of a dead holder rolls back and the next holder acquires only once its session is gone; on the autocommit path (a `CREATE INDEX CONCURRENTLY`, every MySQL/Oracle file) a statement the dialect can run in a transaction now commits in the same transaction as its checkpoint, so it is applied exactly once across holder deaths; a statement that cannot is re-attempted at most once, sequentially [verified: `MigrationFencePgTest` T4, T5, T5b; `MigrationFenceMysqlTest` T5b].
- **`CREATE INDEX CONCURRENTLY` that leaves an INVALID index** (cancelled by the statement timeout, or its session died) now fails the run with `InvalidIndexLeftBehind` naming the index and `DROP INDEX CONCURRENTLY` as the repair, instead of a resumed `IF NOT EXISTS` passing over it silently. The same holds when the build itself FAILS (cancelled by a bound, or a resumed build without `IF NOT EXISTS` meeting the INVALID leftover as "already exists"): the raw error is replaced by `InvalidIndexLeftBehind` when the named index is INVALID. The check looks only at the build's own table (`to_regclass` of the `ON` target), so a same-named INVALID index in another schema no longer fails a valid build. Name every index in a migration: an unnamed concurrent build cannot be checked [verified: `MigrationFencePgTest` T11, `cicWithoutIfNotExists…`, `sameNameInvalidIndexInAnotherSchema…`].
- **Refused, never run unfenced:** Galera (`wsrep_on=ON`) and multi-primary group replication (`GET_LOCK` is node-local there), a MySQL connection without a default schema, and a transaction-mode pooler: `FenceUnavailable`, permanent (the schema goes `FAILED` with the reason). **Transaction-mode poolers (PgBouncer `pool_mode = transaction`, or any pooler that shares one server session between clients) are unsupported.** Because both locks are re-entrant, a runner handed a server session that already holds the fence is refused at acquire ("this server session already held the fence before taking it"), and a runner moved to another server session is refused at its next write ("this session does not hold the fence it took"); a pooler that does neither in a given run is not detected. Migrations need a direct connection or session pooling, and one extra server connection per running migration [verified: `MigrationFencePoolerTest` (PgBouncer 1.x, transaction mode)]. A PostgreSQL-configured datasource whose `version()` names CockroachDB gets no advisory lock (CockroachDB's acquire nothing) and runs UNFENCED, never silently: the runner logs a warning and the orchestrator raises the operator warning `schema-migration-unfenced` on every schema operation [verified: `SchemaOrchestratorLeaseTest.UnfencedCockroach`]; its fence comes in FDB-2b, as do SQL Server, Oracle, DB2, SQLite and H2, which run as before.
- **Pinned PostgreSQL sessions (JDBC, R2DBC and postgres-async) set `statement_timeout` and `lock_timeout` first**, both to the statement bound, and set them explicitly even for a zero bound (`0` = unbounded), so a role or database default never governs a migration session (the migration timeout, 15 minutes by default), so a hung statement no longer holds the dedicated connection and its lock forever. `lock_timeout` is not shorter on purpose: a concurrent index build's lock waits share the statement's budget [verified: `R2dbcSqlConnectorPinnedTest`, `PgAsyncSqlConnectorPinnedTest`].
- **Fixed:** an R2DBC pinned session's `update` of a statement with no row count (`SET`) failed with `NoResult`; it now returns 0 [verified: `R2dbcSqlConnectorPinnedTest.update_onAPinnedSession_setWithNoRowCount_returnsZero`].
- **Known, not changed here:** schema migrations do not run through the R2DBC transport at all, fence or not: the history repository binds `?` placeholders, which r2dbc-postgresql rejects (and DDL through it also fails, `Expected single result but got 2`). Pinned by the enabled tripwire `MigrationFencePgTest.tripwire_r2dbcCannotRunAMigration_enableTheR2dbcRowsWhenThisGoesRed`.
- `SchemaMigrations.schemaMigrations()` is replaced by `schemaMigrations(TimeSpan statementTimeout)`.
- **Operator warnings of the fence now close:** `schema-migration-fence-held` is closed by the new INFO `schema-migration-fence-released` (a later attempt on the datasource acquired the fence and completed) and `schema-migration-unfenced` by the new INFO `schema-migration-fenced` (a later schema operation on the datasource ran fenced). Each is raised only after its warning was raised for that datasource, once per warning; the open state lives in the raising node's memory, so a leadership change leaves the warning open [verified: `SchemaOrchestratorLeaseTest$HeldInTheDatabase`, `$UnfencedCockroach`].
