### Security (2026-10-18 — #2263: an AHSE upload could pose as a chunk manifest)
- **A `ContentStore` upload beginning with `AHSE-MANIFEST:` was read as a manifest.** Reading it returned the blocks it named (a confused-deputy read), and deleting it released them, which could let another file's chunks be collected. Whether a value is a manifest is now decided out of band. The store writes every value under a trusted ref (`|` + name) and believes its typed envelope (`D` content, `M` manifest) only there. No value written before the upgrade can sit under such a ref: legacy snapshots split ref lines at the first `|`, so a name containing `|` never survived a restart. A legacy value is never read as an envelope, so a legacy upload that begins with the new marker, whatever the kind byte, reads back verbatim. [verified: integrations/storage/src/test/java/org/pragmatica/storage/ContentStoreManifestFramingTest.java]
- Manifest fields are length-prefixed. A name containing `|` or `=` round-trips through the manifest, and across a restart through the `format=2` snapshot encoding (#2257). [verified: ContentStoreManifestFramingTest, ContentStoreReclamationTest]
- Legacy text manifests stay readable under their bare names, and their delete releases their chunks. Writing a legacy name moves it to the trusted ref and retires the legacy ref. A pre-upgrade upload that begins with `AHSE-MANIFEST:` still reads as a manifest until its name is rewritten or deleted, because such a legacy value is ambiguous by construction. [verified: ContentStoreManifestFramingTest]
- **Upgrade note: rolling a node back to a binary from before this change is unsupported.** After the upgrade every name lives under a trusted ref (`|` + name), and the bare ref of a rewritten or deleted name is retired. A build with the `format=2` snapshot encoding (#2257) but without this change restores the snapshot, but it looks names up under their bare refs: every name written since the upgrade answers "not found" there, and a later roll-forward brings the trusted refs back, shadowing anything written under those names in between. A build from before #2257 cannot read the snapshot at all (see #2257). This applies to a node that boots the older binary over the same content snapshot directory: an in-place restart, or a replacement node whose storage resolves there. Pre-GA, a downgrade is unsupported by decision. See `aether/docs/reference/versioning-and-compatibility.md`. [mechanism: the pre-change DefaultContentStore.get resolves the bare name only; DefaultSnapshotManager dispatches on `format`]
- **Known exception, accepted pre-GA:** a `format=2` snapshot (#2257) round-trips any ref name, so an unreleased 1.0.0-rc5 development build from 2026-10-19 on that has #2257 but not this change could store an upload named `|victim` under a bare ref that this change then reads as the trusted ref of `victim`, the forgery above. Only nodes that ran such a build and accepted an upload whose name begins with `|` are exposed. The window closes once this change is in rc5; no released build is affected. [mechanism: ContentEnvelope.trustedRef; SnapshotNameCodec decodes every name]
