### Security (2026-10-18 — #2263: an AHSE upload could pose as a chunk manifest)
- **A `ContentStore` upload beginning with `AHSE-MANIFEST:` was read as a manifest.** Reading it returned the blocks it named (a confused-deputy read), and deleting it released them, which could let another file's chunks be collected. Whether a value is a manifest is now decided out of band. The store writes every value under a trusted ref (`|` + name) and believes its typed envelope (`D` content, `M` manifest) only there. No value written before the upgrade can sit under such a ref: legacy snapshots split ref lines at the first `|`, so a name containing `|` never survived a restart. A legacy value is never read as an envelope, so a legacy upload that begins with the new marker, whatever the kind byte, reads back verbatim. [verified: integrations/storage/src/test/java/org/pragmatica/storage/ContentStoreManifestFramingTest.java]
- Manifest fields are length-prefixed, and snapshot ref names are now percent-escaped (`%`, `|`, `=`, CR, LF; legacy snapshots are read as before). A name containing `|` or `=` round-trips both through the manifest and across a restart. [verified: ContentStoreManifestFramingTest, ContentStoreReclamationTest]
- Legacy text manifests stay readable under their bare names, and their delete releases their chunks. Writing a legacy name moves it to the trusted ref and retires the legacy ref. A pre-upgrade upload that begins with `AHSE-MANIFEST:` still reads as a manifest until its name is rewritten or deleted, because such a legacy value is ambiguous by construction. [verified: ContentStoreManifestFramingTest]
- **Upgrade note: rolling a node back to a binary from before this change is unsupported, and loses every content-store name written since the upgrade.** After the upgrade every name lives under a trusted ref (`|` + name), and snapshots write ref names percent-escaped. An older binary reads an escaped name verbatim (`%7Cname`, never `|name`) and skips every ref line that contains `=`, so the content hash it recomputes no longer matches the one stored and it rejects every snapshot that holds a name written since the upgrade. It falls back to the newest older retained snapshot that validates; if none does, the node refuses to boot. If it boots, names written since the upgrade are gone, and the blocks they named become unreferenced and may be collected. A name rewritten since the upgrade reverts to its pre-upgrade value only if a pre-upgrade snapshot is still retained, and that value's chunks may already have been released. Pre-GA, a downgrade is unsupported by decision. This applies to a node that boots the older binary over the same content snapshot directory: an in-place restart, or a replacement node whose storage resolves there. See `aether/docs/reference/versioning-and-compatibility.md`. [mechanism: DefaultSnapshotManager.parseRefLine, readAndValidateSnapshot and nothingRestored at the merge base; MetadataSnapshot.isValid hashes the ref names]
