### Fixed (2026-09-13 — #1039: STREAM_REPLICAS was structurally incapable of returning an authoritative answer)
- **`GET /api/v1/streams/{ns}/{stream}/{version}/replicas/{partition}` reported a non-owner's empty replica ring as if it were the partition's state.** The route was `taskGroup(STREAMING)`-dispatched, which lands a request on an arbitrary STREAMING-capable node and discards whether that node is the partition's HRW owner — and the `ReplicaRegistry` is authoritative only ON the owner, since only the owner receives every replica's ack. Measured on a live 5-node cluster, same node and instant: `replicas-local` returned `servedByOwner:true, ownerHeadOffset:20` with a `CAUGHT_UP` replica at 19, while the delegate-routed variant returned `servedByOwner:false, ownerHeadOffset:0, confirmedOffset:-1` — indistinguishable from a genuinely empty partition, and `false` from 5 of 5 ports including the owner's own. The silent-divergence state #333 named this endpoint to expose was therefore unobservable through it.
- New `RouteTarget.PartitionOwner(partitionParamIndex)` forwards to the deterministic HRW owner, executed at both dispatch points (`ManagementServerImpl.tryForwardToRouteOwner` and `HttpForwarder.dispatchByTarget`). `STREAM_REPLICAS` now uses it; `STREAM_REPLICAS_LOCAL` is unchanged, because "what does THIS node see" and "what is authoritative" are different questions. [mechanism: both dispatch points switch on the sealed `RouteTarget`, so the compiler forces every site to handle the new variant; the forwarding decision is pinned by unit tests at both sites — `HttpForwarderPartitionOwnerTest`, `ManagementServerPartitionOwnerTest` — which is NOT the live-path bar]
- **One derivation of stream identity, not two.** The owner is `hrw(engineKey, partition)`, and `StreamManager.engineKey` lives in module `node` while `HttpForwarder` lives in `aether-invoke`. Rather than re-implement the reduction — one declaration resolving to two engine keys is the defect tracked by #1040 — the node injects a `PartitionOwnerResolver`, which reuses `ManagementServerImpl.resolveEngineKey` and the very `StreamReadRouter` owner resolver that `replicaSnapshot` reads to compute `servedByOwner`. Forwarder and handler therefore agree by construction; a separately wired resolution could forward to a node that then answers `servedByOwner:false`, which is this defect one hop further away. [mechanism: `ManagementServerPartitionOwnerTest` pins the dispatch-path engine key against `StreamManager.engineKey` as an identity, so a change to the reduction that moves only one of them fails the build]
- **Two conditions are named rather than faked.** An unresolvable owner (empty member view, or the bootstrap window before the first reconcile) fails with `PartitionOwnerUnresolved` instead of answering locally with an empty ring; a receiver that resolves a different owner fails with `OwnerForwardLoop`, so membership skew terminates on a named cause rather than decaying into a request-budget deadline. Neither depends on anything the client sends. [mechanism: the client-facing entry in `ManagementServerImpl.forwardViaForwarder` carries no hop state by construction, and the previous hop the refusal names is `HttpForwardRequest.sender`, the peer identity the cluster transport already carries as a typed field. Unit-level, not a live multi-node run]
- **The skew refusal is raised where it can actually fire: on the RECEIVING node.** A forwarded management request is dispatched by `router.handle` directly and never re-enters `dispatchManagementRequest`, so none of the `RouteTarget` dispatch switch runs on the node that receives it. Without a receive-side check, a `PartitionOwner` route reaching a node that disagreed with the sender about ownership was answered anyway — `200` with `servedByOwner: false` and a partial ring, the exact ambiguity this issue exists to remove, behind documentation promising a named `503`. `ManagementServerImpl.checkForwardedPartitionOwner` now re-resolves the owner from the receiver's own view before dispatch, through the SAME `resolvePartitionOwner` the sending side uses, and refuses when it does not resolve itself. It does not re-forward: a second hop is what could cycle, and the sender has already made an owner decision, so the receiver's disagreement is the answer. Only `PartitionOwner` routes are judged; leader-, core-, task-group- and node-targeted forwards dispatch untouched. [mechanism: `ForwardedOwnerGuardTest` pins the decision and `ManagementForwardOwnerGuardWiringTest` drives a real `ManagementServerImpl.onHttpForwardRequest` end to end, asserting the emitted `HttpForwardResponse` carries the named refusal. Mutation-checked: deleting the call site alone leaves the decision tests green and reddens exactly the two wiring tests, out of 1372 `aether/node` tests]
- **No `[verified:]` tag on this change, deliberately.** Per the claim-discipline rule a unit test does not meet that bar. Not yet demonstrated on the live path: no multi-node run has confirmed `servedByOwner:true` from every port since the change, and no run has observed a real membership-skew `503` — the skew case is driven only by a stubbed owner resolver. The `02-chaos` harness's retry-until-owner loop still tolerates the old behaviour and was not tightened. [design intent — unverified]
- **Residual, disclosed rather than removed:** `HttpForwarder.forwardManagement`'s `previousHop` parameter and the `forwardToPartitionOwner` guard behind it still have no production caller that supplies a present value, and are therefore unreachable in production. The receive-side check above supersedes them and is strictly stronger — it fires on disagreement regardless of hop count. Retiring the parameter is a follow-up, not done here, because it changes a shared interface.
- **A defect found in this change's own first round, recorded because the shape recurs.** The loop marker was first read with an exact-case key lookup. `Headers.asMap()` normalizes every key to lowercase and `ForwardedRequestContext` routes deserialized headers through it, so the guard would have passed its unit test — which hands the context over unnormalized — and missed silently on a real second hop. Fixed to match case-insensitively, and the regression test now runs node A's stamped headers through the real `Headers` normalizer instead of lowercasing them by hand. [mechanism: the test asserts, as its own control, that the normalizer actually changed the key before asserting the guard still fires]
- **The loop guard was client-settable in the first round of this change, and that is now fixed rather than documented.** The hop was originally recorded in an `X-Aether-Owner-Forwarded-By` header on the forwarded request. Nothing in this repo strips inbound headers (`headers().remove` / `removeHeader`: zero sites), so any caller could set it and change a receiving node's dispatch decision on a first hop — a guard the thing it guards against could switch off. Hop state moved off-header onto the `forwardManagement` parameter; the header no longer exists. [mechanism: `forwardManagement_stillForwardsToTheOwner_whenAClientSuppliesTheFormerMarkerHeader` asserts both casings of the former header name still forward to the owner, and goes RED against the header-based implementation]
