### Fixed (2026-09-13 — #1039: STREAM_REPLICAS was structurally incapable of returning an authoritative answer)
- **`GET /api/v1/streams/{ns}/{stream}/{version}/replicas/{partition}` reported a non-owner's empty replica ring as if it were the partition's state.** The route was `taskGroup(STREAMING)`-dispatched, which lands a request on an arbitrary STREAMING-capable node and discards whether that node is the partition's HRW owner — and the `ReplicaRegistry` is authoritative only ON the owner, since only the owner receives every replica's ack. Measured on a live 5-node cluster, same node and instant: `replicas-local` returned `servedByOwner:true, ownerHeadOffset:20` with a `CAUGHT_UP` replica at 19, while the delegate-routed variant returned `servedByOwner:false, ownerHeadOffset:0, confirmedOffset:-1` — indistinguishable from a genuinely empty partition, and `false` from 5 of 5 ports including the owner's own. The silent-divergence state #333 named this endpoint to expose was therefore unobservable through it.
- New `RouteTarget.PartitionOwner(partitionParamIndex)` forwards to the deterministic HRW owner, executed at both dispatch points (`ManagementServerImpl.tryForwardToRouteOwner` and `HttpForwarder.dispatchByTarget`). `STREAM_REPLICAS` now uses it; `STREAM_REPLICAS_LOCAL` is unchanged, because "what does THIS node see" and "what is authoritative" are different questions. [verified: aether/aether-invoke/src/test/java/org/pragmatica/aether/http/forward/HttpForwarderPartitionOwnerTest.java]
- **One derivation of stream identity, not two.** The owner is `hrw(engineKey, partition)`, and `StreamManager.engineKey` lives in module `node` while `HttpForwarder` lives in `aether-invoke`. Rather than re-implement the reduction — one declaration resolving to two engine keys is the defect tracked by #1040 — the node injects a `PartitionOwnerResolver`, which reuses `ManagementServerImpl.resolveEngineKey` and the very `StreamReadRouter` owner resolver that `replicaSnapshot` reads to compute `servedByOwner`. Forwarder and handler therefore agree by construction; a separately wired resolution could forward to a node that then answers `servedByOwner:false`, which is this defect one hop further away. [verified: aether/node/src/test/java/org/pragmatica/aether/api/ManagementServerPartitionOwnerTest.java]
- **Two conditions are named rather than faked.** An unresolvable owner (empty member view, or the bootstrap window before the first reconcile) fails with `PartitionOwnerUnresolved` instead of answering locally with an empty ring; a request already owner-forwarded carries an `X-Aether-Owner-Forwarded-By` marker and a second owner-forward fails with `OwnerForwardLoop`, so membership skew terminates on a named cause rather than decaying into a request-budget deadline. [verified: HttpForwarderPartitionOwnerTest — the loop case is driven end to end, replaying node A's own stamped request into node B's forwarder under disagreeing views]
- **Not yet demonstrated on the live path:** no multi-node run has confirmed `servedByOwner:true` from every port since the change; the evidence above is unit-level at both dispatch points. The `02-chaos` harness's retry-until-owner loop still tolerates the old behaviour and was not tightened. [design intent — unverified]
