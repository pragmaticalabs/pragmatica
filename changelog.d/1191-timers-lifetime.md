### Fixed (2026-11-26 — #1191: Fsm.dispatch: the CAS serialises which transition wins, not the side effects of the losing path — live timer survives stop())
- **A state's `onEntry` that was overtaken by the next transition could arm a timer that nothing cancelled** (#1191). The CAS orders which transition wins; the winner's `onEntry` and the next winner's `onExit` are not ordered against each other, so an entry overtaken by an exit stored its timer after the exit had drained the holder. `Fsm` now gives every entered state an `OwnerLifetime` (`FsmState#onEntry(OwnerLifetime)`, `Fsm#entered()`), ended on the CAS winner before `onExit` runs; a timer registered on an ended lifetime is never enqueued. A CAS loser ends nothing. The `Fsm` class documentation no longer claims the CAS serialises the hooks. [verified: `StateLifetimeOvertakeTest`]
- **Every timer armed by an entry hook or by an event/callback path of the states below goes through the lifetime**: `CertificateRenewalScheduler` (timerLock, arming epoch and terminated flag removed; reconfigure is a `Reconfigure` transition), `ScheduledTaskManager` (Following/Leading entry, registry arm, interval and cron arms and the three cron re-arms; `cancelAllTimers` removed), and `ClusterDeploymentState.Active` (the reconcile timer, the deferred topology recheck and the twelve event/callback schedules; the `reconcileTimer` field removed). The node-deployment state already registered through a context lifetime that `Stopped.onEntry` ends; a guard test pins that a registration after the stop is refused. [verified: `CertificateRenewalSchedulerStaleTimerTest`, `ScheduledTaskStateLifetimeOvertakeTest`, `ScheduledTaskCronRearmLifetimeTest`, `ClusterDeploymentActiveLifetimeTest`, `NodeDeploymentStopLifetimeTest`]
- **Not covered:** a timer body whose wrapper read the lifetime before `end()` may still run once after it (a running task is never interrupted), so bodies that must not act after exit keep their own state check. The leader-election state machine arms raw timers in `QuorumWaiting`, `AwaitingKvSync` and `Led` entry hooks; it stays safe through its single serial drainer (`dispatchConfined`), not through the lifetime. [mechanism: `OwnerLifetime` javadoc, `LeaderElectionContext#dispatchConfined`]
