### Fixed (2026-10-18 — #1473: an unmounted volume is no longer read as a first boot at the snapshot layer)
- **A node whose disk tier is armed no longer boots on empty metadata when its volume is missing.** An unmounted but existing mount point presents an empty, listable snapshot directory, which the snapshot manager read as a first boot.
- **Mechanism.** The first successful snapshot write gives the volume an id: a random UUID in `.volume-id` inside the snapshot directory and the same id in a sentinel file OUTSIDE the volume. When nothing restores, a present sentinel whose matching `.volume-id` is absent or different refuses the boot (`VolumeNotPreviouslyWritten`, naming the snapshot path and the sentinel). No sentinel is a first boot; a remount of the right volume boots. An armed but empty snapshot directory alone never refuses. A volume written before this change is adopted at its next snapshot (marker present, sentinel absent).
- **Where the sentinel lives.** `<state dir>/volume-sentinels/<snapshot path>.id`, with the state dir taken from `-Daether.state.dir`, else `AETHER_STATE_DIR`, else `/var/lib/aether`, which must be on the boot filesystem and not on the data volume. A degraded disk tier (memory + DHT) passes no sentinel, so the ordinary "`/data` is not writable" boot is unchanged. If the state dir cannot be written, the snapshot stands and one WARN says the unmounted-volume guard is not recorded.
- Applies to the configured storage instances and to `streams`. Test runs point the state dir at `target/aether-state`.
