### Fixed (2026-10-18 — #1473: an unmounted volume is no longer read as a first boot at the snapshot layer)
- **A node whose disk tier is armed no longer boots on empty metadata when its volume is missing.** An unmounted but existing mount point presents an empty, listable snapshot directory, which the snapshot manager read as a first boot.
- **Mechanism.** The first successful snapshot write gives the volume an id: a random UUID in `.volume-id` inside the snapshot directory and the same id in a sentinel file OUTSIDE the volume. When nothing restores, a present sentinel whose matching `.volume-id` is absent or different refuses the boot (`VolumeNotPreviouslyWritten`, naming the snapshot path and the sentinel). No sentinel is a first boot; a remount of the right volume boots. An armed but empty snapshot directory alone never refuses. A volume written before this change is adopted at its next snapshot (marker present, sentinel absent).
- **Where the sentinel lives.** `<state dir>/volume-sentinels/<sha256 of the canonical snapshot path>-<last segment>.id`. The state dir is `-Daether.state.dir`, else `AETHER_STATE_DIR`, else `/var/lib/aether`, on the boot filesystem and NOT under the data root (the docker deployment mounts `/data`, which would put the sentinel on the guarded volume). The node image creates `/var/lib/aether` owned by the node user and the systemd unit adds `StateDirectory=aether`. The name is a hash, so two snapshot directories never share a sentinel.
- **What it guards.** Only while the state dir outlives the volume: give it a small separate volume or a bind mount to survive container recreation (see `docker-deployment.md`). With no mount it lives in the container layer and covers restarts only. If the state dir is on the same filesystem as a guarded volume, the node logs one WARN at boot that the guard is inactive, naming both paths.
- **A disk tier that does not come up at all is no longer exempt once a volume was written.** A degraded tier (memory + DHT) on a first boot is unchanged: the ordinary "`/data` is not writable" boot still works. But when the sentinel for the same snapshot directory exists, the missing tier is the unmounted volume and the boot refuses (`VolumeUnavailable`, naming the path and the sentinel).
- If the sentinel cannot be written, the snapshot stands and one WARN says the unmounted-volume guard is not recorded.
- Applies to the configured storage instances and to `streams`. Test runs point the state dir at `target/aether-state`.
