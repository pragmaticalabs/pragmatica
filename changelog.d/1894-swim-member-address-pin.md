### Security (2026-10-04 — SWIM: pin each member's address to its process identity)
- **A member's SWIM address is now pinned to its process identity, and an address change is refused and reported.** The pin is the first source address that announced the member and then answered a probe as that member. An ANNOUNCE from the pinned address behaves as before. An ANNOUNCE for a pinned member from any other address is refused whole (no reply, no probe or QUIC address change, no tombstone clear) and raises the `swim-member-address-conflict` operator warning (WARNING), throttled to one event per member per 60 s. [verified: integrations/swim `SwimAnnounceSourcePinTest` — unit level, through the real protocol with a fake transport; no multi-node proof of the event reaching `/api/events`]
- **An ANNOUNCE from an address with no pin yet earns that address one empty probe and nothing else.** Tombstone clear, introduction, the QUIC dial hint and the membership-snapshot join ack now wait for a valid ack (right sequence, naming the announced member, from the probed address). A joining node therefore gets its join ack one round trip later. [verified: `SwimAnnounceSourcePinTest.firstContact_*`]
- **Changed: the mid-life address refresh is removed.** A live process whose IP changes (for example a container reconnected to a Docker network with a new address) is no longer adopted on its next ANNOUNCE; peers keep probing the pinned address and report the conflict. A restarted process carries a new identity and is pinned afresh. Local docker-mode partition tests that reconnect a container with a new address see the refusal instead of a refresh; firewall-style partitions keep the address and are unaffected. [mechanism: `routeByAddressPin`; `SwimProtocolTest.handleAnnounce_knownMemberReAnnounceFromNewSourceIp_*`]
- No wire change: the ANNOUNCE and Ack shapes are untouched. Failure-almanac row and `OPERATOR_WARNING` code list updated.
