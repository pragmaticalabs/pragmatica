### Fixed (2026-10-18 — #2063: operator drain entries never leave DrainCommandRegistry)
- **A node that was drained, left and came back under the same id was told to drain again.** An operator-commanded drain stayed in the leader's `DrainCommandRegistry` for the life of the process: the only removal paths covered drains the topology manager started itself, and node ids come from config, so a rejoin under the same id inherited the old command. The entry is now cleared on two membership FSM edges (`AetherNode.clearOperatorDrainOnDeath`, called from the existing transition listener): into DEAD (the departure the drain was for), and out of DEAD (a drain commanded on an already-DEAD node is ignored by the FSM and left no edge of its own, so the rejoin inherited it). The entry is deliberately kept across DEPARTING back to MEMBER, which is the FSM's view refuting a live SWIM suspicion or withdrawing an undelivered drain (#1054) while the command is still in flight; clearing there stopped the leader pinging the DRAIN and the node never left. Not changed: a drained node that is restarted and returns as MEMBER before it ever reaches DEAD keeps its entry, and the per-node tracking entries for nodes that never report READY again (N2 in the ticket) are not touched. `[verified: aether/node/src/test/java/org/pragmatica/aether/node/AetherNodeOperatorDrainClearTest.java drives a real MembershipFsm through each edge]`
