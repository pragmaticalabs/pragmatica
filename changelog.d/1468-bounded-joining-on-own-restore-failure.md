### Changed (2026-10-18 — #1468: a failed consensus own-restore wedged the node in JOINING forever)
- **The fail-closed stop is now bounded and ends in a distinct exit code.** A node whose own persisted consensus history cannot be restored never activates (unchanged); it used to sit in `JOINING` with `start()` unresolved indefinitely. `Main` now arms `OwnRestoreWatchdog` before awaiting `start()`: once `RabiaEngine.ownRestoreFailure()` has been continuously present for 120 s the process logs a FATAL naming the cause and halts with exit code `74` (`EX_IOERR`). 120 s is a chosen bound, not a recovery window, because the engine's fence is permanent within the process. Responder-snapshot failures are not covered (another sync round can recover from them) and are pinned as not setting either failure. The re-persist fence (#1516) is bounded the same way: when a restored or adopted state cannot be persisted the node stays fenced, and after 120 s it logs its own FATAL line and halts with exit code `75` (`EX_TEMPFAIL`), whose supervisor guidance differs from 74: repair the storage, then restart. It samples a dedicated `restoredStateSaveFailure` rather than `authorityFailure`, because the constructor also sets `authorityFailure` and a later genesis clears it, so bounding it would halt a node that is only waiting for its cluster to form. The failure is never cleared in-process: the own-restore arm runs only after a genesis has resolved, and none installs afterwards. The wiring is pinned too: the arming call in `Main`, both accessor hops for each fence, the bound, the production clock's nanosecond-to-millisecond conversion, exit codes 74 and 75 through an injected halt, and the log flush before the halt.
