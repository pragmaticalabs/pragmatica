### Fixed (2026-11-19 — #3092, #3426: the leader-election FSM could follow a leader absent from the applied view)
- **View application in the leader-election FSM follows three invariants** (#3092, #3426). I1: an applied transport view is stored as it is, an empty one included, in every state and mode (the stored view used to keep the old content under an empty view, so local readers re-adopted an evicted leader; `Stopped` and `Passive` ignored views in cluster mode, so a readmitted worker read a replaced one). I2: after any view event, `Led` follows a leader in the applied eligible view or loses it, for `NodeAdded` and for the eviction of another node too (both used to keep an absent leader). I3: a leaderless electing node in local mode makes progress on its own election ticks and adopts a local commit of a node in the view (the commit gate on the consensus sequence, which local mode never advances, used to leave it leaderless until a quorum flap). The local manager takes one path for every view event: apply, elect from the applied view, dispatch. [mechanism: one view-application path per invariant, pinned by the unit table `ViewApplicationTableTest` (144 state x event x mode cells); not exercised multi-node]
