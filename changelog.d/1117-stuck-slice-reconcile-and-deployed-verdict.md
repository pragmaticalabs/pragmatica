### Fixed (2026-10-11 — #1117: stream-consumer slices stall in ACTIVATING/ROUTING until the 30/90 s node timers force ACTIVE)
- **The stuck-slice timers wrote ACTIVE over a committed ACTIVE.** The ROUTING (30 s) and ACTIVATING (90 s) remediation read only the node's local view, which moves only when the node's own apply delivers its notification, and wrote a bare ACTIVE put. They now read this node's own `NodeArtifactKey` from its APPLIED mirror (not a consensus read) first: ACTIVE is adopted into local state with no write; a value EARLIER in the activation chain (LOAD..ROUTING) re-drives the chain's FULL last write (ACTIVE with its endpoints and the stream-ref commands, one batch) while a committed target still names the version; DEACTIVATE, DEACTIVATING, FAILED, UNLOAD, UNLOADING, UNKNOWN or no entry is adopted (an absent entry is handled as a removal) and ACTIVE is never written over it. Every remediation line names the node, the local state and the committed state. `[verified: NodeDeploymentStateStuckReconcileTest]` The re-drive builds its stream-ref Puts from the current applied mirror; if the lost original also lands late the instance holds one reference too many and the stream outlives its holders (a leak, the safe direction; per-holder reference entries are the rc5 fix). Not repaired: a committed ACTIVE written earlier by the old bare remediation stays without stream refs.
- **"Blueprint fully deployed — all N slices active" overclaimed.** It is logged on the first ACTIVE instance of each slice and says nothing about the others. The line now reads "deployed: each of its N slices has at least one ACTIVE instance [slice: n of m instances ACTIVE]; other instances may still be activating". The SUCCEEDED outcome record carries no text and has the same meaning (at least one ACTIVE instance per slice, at the leader's last apply). `[verified: DeployedVerdictTest]`
- **Not fixed here:** why the node's last write is sometimes never answered for 30/90 s after a leader change. Three logs show a ten-second stall on the new leader's consensus worker followed by an unanswered submission; the mechanism is tracked in #2143. `[design intent - unverified]`
