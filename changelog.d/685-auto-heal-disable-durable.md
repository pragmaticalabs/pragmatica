### Fixed (2026-09-05 — #685: auto-heal disable was in-memory only and silently reverted on leader failover)
- **An operator's `aether cluster topology auto-heal disable` (#603) lived only in the leader process's `AtomicBoolean`.** A leader failover silently re-enabled auto-heal: the newly-elected leader's fresh `ClusterTopologyManager` never saw the previous leader's in-memory flag, and `status` answered from that same volatile copy — an operator could disable auto-heal, watch `status` confirm it, and have it revert with no error and no audit trail the moment leadership moved.
- **The disable/enable decision is now a durable cluster fact**, written as a typed `AutoHealStateKey`/`AutoHealStateValue` record through the same consensus-backed command path as other topology mutations, and read through on every `isAutoHealEnabled()`/`status` call instead of cached in memory [mechanism: `KVStore.getTyped` read-through; unit-proven by `ClusterTopologyManagerAutoHealDurabilityTest` — two independent `ClusterTopologyManager` instances over one shared `KVStore`, one disabling while the other, which never received the call, observes the disable and, later, the re-enable]. An absent key (a fresh cluster, or one that predates #685) answers enabled, preserving the pre-#685 default.
- **Staleness is explicit, not implied:** a read reflects the log applied LOCALLY; the disable becomes visible on a node when that node applies the committed Put — bounded by consensus latency, not zero; a node behind on apply answers the previous value until then.
- `setAutoHealEnabled` now returns `Promise<Boolean>` (prior state) instead of a synchronous `boolean`, reflecting that the write is a consensus round-trip, not a local mutation. A same-state call still writes through to the KV even when the requested value matches the prior one — the request is answered from this node's local view, which may be stale, so the write stays unconditional (#685 review round 1).
