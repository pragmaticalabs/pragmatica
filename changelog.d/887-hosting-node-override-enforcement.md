### Security (2026-09-08 — #887: blueprint security overrides never reached the hosting node's own policy decision, and never left the node that received them)
- **An operator's blueprint security override was not enforced on the node hosting the route it was meant to protect.** `HttpRoutePublisher` stored the raw, pre-override routes and applied overrides only on the path to the replicated KV entry. The local authorization decision (`AppHttpServer.findRouteSecurityPolicy` → `HttpRoutePublisher.findLocalRoute`) read the raw collection, so under the shipped `security_mode = "api-key"` a route with no declared `[security]` stance carrying a `role:admin` override resolved to the global `ApiKeyRequired` policy and never reached the role check. Any holder of any valid API key, with no admin role, was served. `[verified: aether/node/src/test/java/org/pragmatica/aether/http/AppHttpServerOverrideEnforcementTest.java]`
- **Worse, the override reached only ONE node at all.** `updateSecurityOverrides` had a single call site — an in-process call on whichever node served `POST /api/v1/blueprints`, a `taskGroup(DEPLOYMENT)` route with one migrating owner. Every other node held `SecurityOverrides.EMPTY`, so a slice hosted elsewhere published its cluster route entry built from EMPTY overrides and **no node enforced the override**, including the remote readers that were assumed to be enforcing it correctly. `[verified: aether/forge/forge-tests/src/test/java/org/pragmatica/aether/forge/BlueprintSecurityOverrideClusterWideTest.java — three real nodes, override applied via one node's management API, enforcement asserted on all three]`
- Overrides are now resolved at **request** time by the same `SecurityOverrideApplier` that builds the published entry, so one rule and one source answer both the local decision and the KV entry. `publishedRoutes` deliberately keeps the raw routes: a second, pre-resolved collection would be a snapshot that disagrees with the current overrides the moment they change, which is the shape of the original defect. `[mechanism: findLocalRoute resolves the matched route through SecurityOverrideApplier.applyOverride against the current activeOverrides]`
- Overrides are now **derived on every node from the replicated blueprint** rather than pushed to one. `AppBlueprintValue` already carried `ExpandedBlueprint.securityOverrides()` to every node, durably — what was missing was a reader. No new distributed state was introduced. The in-process push from `SliceRoutes` was removed so there is a single installer. `[mechanism: SecurityOverrideSynchronizer derives from the KV store on every AppBlueprintKey change, sorted by blueprint id so every node computes the same answer]`
- **Overrides now survive a restart or a DEPLOYMENT task-group migration.** `activeOverrides` is in-memory, so a node that restarted used to re-publish its routes with EMPTY overrides and enforce nothing, with no operator signal. The derivation is re-run on the `ClusterStateNotification.ACTIVE` edge, which is what a node sees when it restores state it never observed arriving. `[verified: aether/node/src/test/java/org/pragmatica/aether/http/AppHttpServerOverrideEnforcementTest.java — request_isRefused_whenOverrideRederivedOnActiveEdgeWithNoPutObserved]`
- An override applied while a node is already serving governs the very next request, with no redeployment and no republication of the slice. `[verified: aether/node/src/test/java/org/pragmatica/aether/http/AppHttpServerOverrideEnforcementTest.java — request_isRefused_whenOverrideAppliedWhileServerIsServing]`
- `GET /api/v1/routes` answers from the replicated KV entries, so an override changed at runtime now rewrites those entries; without it the management API would keep reporting the previous policy. Enforcement on a node changes atomically; the reported state converges after one consensus apply, bounded at 90s worst case (30s timeout × 3 attempts) and then failing loudly. During that window a **strengthening** is enforced before it is reported (the report understates protection), while a **withdrawal** is enforced before the report stops advertising the stronger policy. That second direction is bounded, not eliminated. `[verified: aether/aether-invoke/src/test/java/org/pragmatica/aether/http/HttpRoutePublisherOverrideResolutionTest.java — ReportedStateTracksEnforcedState]`
- **Not closed by this change, and still reachable.** Under `security_mode = "api-key"` or `"jwt"`, a `STRENGTHEN_ONLY` override to `authenticated` (strength 10) against an effective policy of `ApiKeyRequired`/`BearerTokenRequired` (both 20) is a weakening the strength comparison still permits, because `aether-invoke` cannot see `aether-config`'s `SecurityMode` from either call site. This change moved **where** the override rule is consulted, not **what** it decides. A guard named `STRENGTHEN_ONLY` that permits a weakening is tracked on #866. `[design intent — unverified]`
- **Conflicting override policies across several active blueprints are no longer silently resolved.** The previous behaviour was last-writer-wins and differed per node. A genuine conflict is now logged naming the blueprints and falls back to `STRENGTHEN_ONLY`; a single contributing blueprint's policy is used unchanged. `[verified: aether/node/src/test/java/org/pragmatica/aether/http/SecurityOverrideSynchronizerTest.java — DeterministicAcrossNodes]`
