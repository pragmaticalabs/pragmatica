### Fixed (2026-09-19 — #1267: consumer reconcile passes were not serialized, so an older pass could detach what a newer one attached)
- **`StreamConsumerManager.reconcile()` had no mutual exclusion, and it runs on two threads: the periodic tick and the registration-change listener.** A pass that read the declarations before a registration landed could finish after the listener's pass attached that registration's partitions. Its `dropStale` then detached them, and the declared consumer stayed detached until the next tick. The interleave is reachable. A test parks the older pass at its declaration read, registers a consumer on a second thread, and releases the older pass: on the unfixed code all four partitions end up detached. [mechanism: `StreamConsumerManagerTest.ReconcilePasses.reconcile_keepsAttachedPartitions_whenAnOlderConcurrentPassFinishesLast`, RED at `ccba0dba5` (`[]` where `[0, 1, 2, 3]` was expected)]
- One pass runs at a time. A trigger records a request and then queues on a monitor. Whichever thread next holds the monitor runs ONE pass for every request recorded so far, so triggers that arrive during a pass coalesce into a single follow-up pass, which reads state as of after those triggers. A pass that throws still releases the monitor, so reconciliation cannot wedge. Callers that arrive during a pass wait for it rather than return. [mechanism: with the serialization removed, this is the only one of the 38 `StreamConsumerManagerTest` tests that goes RED. Unit-level with a latch-forced interleaving, not a live multi-node run]
- **Cost:** the registration-change listener runs on the KV notification thread, which can now wait for an in-flight tick pass before it runs its own. In the worst case it waits about two passes where it used to run one. A burst of triggers during a busy pass still costs only one follow-up pass. [mechanism: `StreamConsumerManagerTest.ReconcilePasses.reconcile_runsExactlyOneFollowUpPass_forABurstOfTriggersDuringABusyPass` counts two declaration reads for a busy pass plus five triggers. It goes RED when every caller runs its own pass]
- **`stop()` now waits for an in-flight pass, and no pass runs after it.** `stop()` sets a `stopped` flag, then does its detach sweep under the pass monitor, and a pass that finds the flag set attaches nothing. Before, a pass already past its snapshot could attach after `stop()` had detached everything, and a later tick could re-attach as well. `stop()` may now wait for one in-flight pass. [mechanism: `stop_leavesNothingAttached_whenAPassInFlightFinishesAfterStopWasCalled` and `reconcile_attachesNothing_afterStop`. Both were RED at `098606ae9` (`[1, 2, 3, 0]` still attached)]
