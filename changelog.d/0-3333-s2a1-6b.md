### Changed (2026-11-25 — #3333: a hot window or retention share below the seal and ring floors is refused at parse)
- **Behaviour change, refusals at deploy and at activation:** a stream declaration is now held to the seal and ring floors, on the values the stream will run with (a default counts as a value), and the first failing check is the refusal; nothing is clamped. In order: `hot.max_bytes` below 2 x the seal run size (2 MiB) or `hot.max_count` below 2 x the seal run events (8 192) is refused (`hot-window-below-seal-runs`, naming the key and the smallest valid value); `hot.max_bytes` below `max_event_size` is refused (`hot-window-below-max-event`); a replay-window share below two merged segments (8 MiB), below two seal runs of records (`max_count / P` under 8 192), or below one maximal event is refused (`retention-share-too-small`, naming the key that sets the share and its smallest valid value for this partition count); `hot.max_count` above the index capacity of the ring's first data region is refused (`retention-count-unindexable`; a `[retention]` `max_count` is not what is checked). The share is the smallest of `max_bytes / P` and `(max_count / P) x max_event_size` under `mode = "any"`, the largest under `all`; an age bound makes it not computable, so under `all` with an age bound the byte and event checks are skipped. Products saturate instead of overflowing. These checks run before the `not-yet-available` check. A stream that declares nothing but `partitions` is unaffected. [mechanism: unit-tested, `StreamConfigParserBoundsTest`, `DeclarationBoundsTest`, `StreamResourceValidatorTest.DeclarationRuleIds`]
- **Behaviour change for existing declarations:** a `[hot]` `max_count` below 8 192 and a `[retention]` `max_count` below 8 192 per partition, which parsed before, are now refused. The create-time checks of the stream manager stay as the second line. [mechanism: unit-tested, `StreamConfigParserBoundsTest`]
