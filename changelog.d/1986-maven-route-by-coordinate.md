### Fixed (2026-10-18 — #1986: Maven repository routing depended on the URL segment count)
- **A Maven push was routed to the DEPLOYMENT owner or handled locally depending on how many segments the group id had.** `ARTIFACT_PUT` declared a fixed four trailing parameters, so an artifact file of a two-segment group (`org/example/...`) never matched and was handled on whichever node took it, while a two-segment group's `maven-metadata.xml` (and `.sha1`) matched with mis-parsed parameters and was forwarded.
- Repository paths are now read by their coordinate: the group is every segment before the coordinate tail, so one operation resolves to one route for groups of 1, 2 or 3+ segments, for artifact files, `maven-metadata.xml*`, `DELETE` and `/repository/info/` [verified: `RouteMatcherMavenTailTest`]. A metadata PUT/POST resolves to `ARTIFACT_PUT`/`ARTIFACT_POST` with an empty `version`. Write-once was never at risk (decided by consensus `bindContent`).
- A group whose first segment is `artifacts` (`/repository/artifacts/demo/lib/1.0.0/lib-1.0.0.jar`, group `artifacts.demo`) is routed by coordinate like every other group; only `GET /repository/artifacts` (the list route) keeps its own route. The segment before an artifact-level `maven-metadata.xml*` is read as an artifact id when it parses as one (so `org/s2/3scale/maven-metadata.xml` is artifact `3scale`), the same reading the Maven protocol handler applies [verified: `RouteMatcherMavenTailTest`].
- The multi-node push through every node is exercised by `EmberForwardedMavenPushTest` [verified: ember-shard-1, 2 tests, 0 failures].
- Behaviour change: artifact and metadata GETs for groups of two or more segments are now forwarded to the DEPLOYMENT owner (any node used to serve them locally), and jar PUT bodies cross the forwarder.
