### Fixed (2026-09-14 — #850: stale-entry sweeps used a core-only liveness set, so a live worker's placement rows were removed on every reconcile)
- **Confirmed, not just hypothesised: the three reconcile-time stale-entry sweeps diffed KV rows against `activeNodes()`, which is `MembershipFsm.coreCountedMembers()` — worker-free by construction — so every `NodeArtifactKey`, `NodeRoutesKey` and `SliceNodeKey` row a LIVE worker owned classified as stale on every `reconcile()` tick and on every leader activation.** The worker's `NodeArtifactKey` removal is answered by its own NDM with `forceCleanupSlice` (the slice is unloaded while serving), and the CDM's `sliceStates` view lost the placement, so the same tick re-placed it onto core (`reconcileBlueprint` runs before the sweeps). [mechanism: `ClusterDeploymentState.Active.activeNodes()` → `ctx.coreCountedMembersSupplier()`; `StaleEntryCleaner.cleanupStaleSliceEntries` / `cleanupStaleNodeArtifactEntries` / `cleanupStaleNodeRoutes`; `NodeDeploymentState.Active.handleNodeArtifactRemove` → `handleSliceValueRemove` → `forceCleanupSlice`] [verified: `ClusterDeploymentStateWorkerRemovalTest.LiveWorkerFootprint` — four cases red at `2005ea7d2` (each sweep alone, and `reconcile()`), green after]
- The sweeps now diff against the nodes that own placements: counted core members plus the workers registered in `workerNodes`. A worker enters that set when its WORKER `ActivationDirectiveKey` commits and leaves it only through `handleNodeRemoval` — the worker-leave channel (#731) or the dead-restored-worker sweep — which is the same path that clears its rows directly, so a registered worker's rows are never stale and a departed worker's still are. [mechanism: `StaleEntryCleaner.placementNodes()`] [verified: `LiveWorkerFootprint.staleSweeps_departedWorker_stillRemoveItsRows` — a sweep that keeps every row reddens exactly this control; reverting the hunk reddens exactly the four live-worker cases]
- **Keeping the rows exposed a second core-only read (review of this PR): `getCurrentInstances` and `hasActiveInstance` filtered `sliceStates` to `activeNodes()` too, so an `instances=1` slice held by a live worker was not counted and `reconcileBlueprint` allocated a second instance on core — at the base that was a migrate-then-sweep churn, with the rows kept it would have been a permanent 2-ACTIVE steady state.** Both now read `Active.placementNodes()` (the one set the sweeps use), so a worker-hosted instance counts for reconcile, scale-down, undeploy and the apply-completion verdict, and a departed worker's does not. [verified: `LiveWorkerFootprint.reconcile_liveWorkerHoldsTheOnlyInstance_placesNoSecondCoreInstance` — red before, green after; restoring the core-only reads reddens exactly it (and the donor test below); `reconcile_departedWorkersInstance_isReplacedOnCore` pins the inverse] `[unverified: the apply-completion verdict (`everyDeclaredSliceActive`) with a worker-only placement — read-only change, no fixture drives it]`
- With worker instances counted, a rebalance could have chosen the worker as the donor and pulled its placement onto core; the donor is now restricted to allocatable (core) hosts, since the load a rebalance levels is the core load. `stateKeyFor`-style single-writer semantics are untouched; scale-down may now unload a worker-hosted instance, which is the instance semantics the count implies. [verified: `ClusterDeploymentStateRebalanceOnScaleUpTest.rebalance_neverPicksAWorkerAsDonor` — removing only the donor filter reddens exactly it, with the core-side move still landing as its control]

It now walks `placementNodes()` too, so a worker-hosted orphan gets the same UNLOAD a core-hosted one does.
