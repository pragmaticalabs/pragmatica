### Changed (2026-10-20 — #241: community sizing moves into the committed cluster config)
- **The per-community target size and viability floor were per-node configuration**, so a leader failover to a node configured differently changed the floor and the target for every community. Both now come from an optional `[community_policy]` table in the committed cluster config (`max_size`, `viability_floor`, `max_communities`, `dissolve_grace_seconds`, `growth`, `allow_below_rf`); a cluster without the table keeps using the node-level sizing. A mistyped value, an out-of-range number or an unknown key refuses the apply, a declared community may not take a derived id (`<source>-w-<number>`) or exceed the 200 ceiling, and a policy change is a modification in the apply plan. Pre-GA breaking change: a declared community id of the derived shape is now refused. [verified: `CommunityPolicyParserTest`, `ClusterDeploymentStateCommunitySizingTest`] A cluster whose committed config has no `[community_policy]` table keeps using the node-level sizing, so its floor still follows the node a leader runs on; add the table (even empty) to make it committed.
