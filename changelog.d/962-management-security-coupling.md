### Fixed (2026-10-18 — #962, #1121: Management API security coupling undocumented, refusals unnamed, and a false "refused" claim for security_mode none)
- **The Management API shares `[app-http] security_mode` and `api-keys` with app-HTTP, authorizes on a different axis, and its refusals named neither.** The coupling is kept (both planes check the same keys and the same cluster bootstrap admin key; a separate management setting would change config semantics) and is now stated in `management-api.md` with an example of a key that passes on one plane and fails on the other (`roles` versus `authorization_role`). Every management refusal now names the plane (`Management API ...`) and, for authorization, the axis [verified: `ManagementServerSecurityCouplingTest`].
- **`security_mode = "none"` leaves the Management API fully open; the #573 comment and changelog claim that `denyUnlessPublicValidator` refuses non-public routes there was false.** The management server never consults a validator when security is disabled (local, forwarded, websocket and Maven push paths). The dead validator and the false comment are removed from `AetherNode`, and the startup WARN now says the plane is fully open. This corrects the #573 entry ("The management plane now uses `denyUnlessPublicValidator`...") for the `none` arm; the entry's other claims stand. The open behaviour is pinned [verified: `ManagementServerSecurityCouplingTest.securityDisabled_anonymousPush_isServedWithoutConsultingTheValidator`].
- `management-api.md`: the default `authorization_role` is `VIEWER` (it said `ADMIN`), and the "no keys means open" sentence is replaced by the fail-closed default.
