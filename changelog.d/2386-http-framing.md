### Fixed (2026-10-25 — #2386: HTTP/3 and HTTP/1.1 framing follow-ups: partial dispatch on broken framing, connection-specific fields, duplicate Host)
- **An HTTP/3 request stream that broke RFC 9114 framing could still reach the handler with its valid prefix.** Netty drops the offending frame and raises the error on the stream, but when the bad bytes and the stream's `FIN` arrived in one read, the transport still delivered the input-shutdown event after the stream was closed, and the handler dispatched what it had buffered: a request whose second trailer section, or DATA after the trailers, was refused was served without it. The handler now marks a stream rejected on any error Netty raises on it, which Netty does before it drops the frame and so before the input can end. [verified: `integrations/net/http-server` `Http3FramingViolationTest` (a real HTTP/3 client; each broken stream sends its last bytes and the `FIN` in one STREAM frame), `Http3RequestHandlerTest#framingErrorBeforeInputEnds_isNeverDispatched`]
- **A body that did not match its `content-length` was dispatched.** Netty checks the two only when the input ends, after the event the handler dispatched on. The handler now dispatches on the read-complete event that follows, which Netty withholds on a mismatch. [verified: `Http3FramingViolationTest` `bodyShorterThanContentLength_isNeverDispatched`, `bodyLongerThanContentLength_isNeverDispatched`; `Http3RequestHandlerTest#inputShutdownWithoutReadComplete_isNotDispatched`]
- **A request stream that ended inside a frame was dispatched as complete.** RFC 9114 §7.1 makes it a connection error of type `H3_FRAME_ERROR`; Netty's frame codec passed on the bytes of a DATA frame cut short and dropped the rest of a cut frame without an error. A guard ahead of the codec now follows the frame boundaries and, when the input ends inside a frame, raises `H3_FRAME_ERROR` on the stream and closes the connection with that code. [verified: `Http3FramingViolationTest` `streamEndingInsideADataFrame_isNeverDispatched`, `streamEndingInsideATrailerSection_isNeverDispatched`, `streamEndingInsideAFrameHeader_isNeverDispatched`; `Http3FrameBoundaryGuardTest` for 1-, 2-, 4- and 8-byte varints and frames split across reads]
- **The HTTP/3 response writer wrote connection-specific and pseudo-header fields the application set.** RFC 9114 §4.2 forbids `Connection`, `Keep-Alive`, `Proxy-Connection`, `Transfer-Encoding` and `Upgrade` in an HTTP/3 message, `TE` in a response, and pseudo-header fields other than the protocol's own. A client refused the whole response for `connection`, `te` or an unknown pseudo-header, received the others, and an application `:status` replaced the real status. The writer now drops these fields, matching names case-insensitively (folded with `Locale.ROOT`), and keeps every other header. [verified: `Http3ResponseConnectionFieldsTest`, a real HTTP/3 client, also under a `tr-TR` default locale]
- **HTTP/1.1 accepted a request with more than one `Host` line.** RFC 9112 §3.2 requires a 400. Netty's decoder keeps every line, so the server now counts them, case-insensitively, and answers 400 and closes the connection without dispatching; a WebSocket upgrade with two `Host` lines is refused the same way instead of upgraded. A request with one `Host` is unchanged. [verified: `HttpDuplicateHostTest`: a real HTTP client (Netty's codec, which writes each line as given) and a raw socket; two lines differing in case; the same value twice; the upgrade]
