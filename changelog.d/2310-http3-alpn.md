### Fixed (2026-10-19 — #2310: no HTTP/3 client could complete a request against a node: no ALPN token, and response header names that were not lowercase)
- **The management and app HTTP/3 listeners never served a standard HTTP/3 client.** QUIC requires ALPN, and every context the node built for them (self-signed, configured certificate, rotated certificate) offered no token. A client offering `h3` therefore had its handshake refused, and the connection closed at the idle timeout.
- `AppHttpServer` and `ManagementServer` now build their QUIC server contexts with `Http3.supportedApplicationProtocols()` (`h3`), at start and on certificate rotation. The rotation pre-check in `TlsRotation` builds the same context. `QuicSslContextFactory.createSelfSignedServer` gains an optional ALPN varargs argument, and its existing callers are unchanged. [verified: `aether/node` `AppHttpServerH3AlpnTest`, `ManagementServerH3AlpnTest`: a standard HTTP/3 client gets a status from each listener on all three paths]
- **With the handshake fixed, every node HTTP/3 response still failed.** The HTTP/3 response writer sent header names as handlers set them, for example `X-Request-Id` from the app server and `Cache-Control` from the management server. HTTP/3 field names are lowercase (RFC 9114 §4.2), and Netty refuses the whole HEADERS frame when one is not. The response was lost and the stream went unanswered until the idle timeout. `Http3Server`'s writer now lowercases the names. [verified: `integrations/net/http-server` `Http3ResponseHeaderNamesTest`, and both node tests above, which carry those headers]
- Cluster transport contexts were already correct: they carry their own cluster protocol token.
