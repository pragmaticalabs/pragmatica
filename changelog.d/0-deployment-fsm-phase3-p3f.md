### Changed (2026-10-23 — deployment state machine rewrite, phase 3 P3-F)
- **The FSM2 core suspicion window and core removal bound are longer: these are production timeouts under FSM2.** The core view is MEMBER + SUSPECT, so the window now counts every term a dead core stays listed: the sampling interval, a tick, the probe lead (`(maxCores - 1)` periods), two probe timeouts and the membership's `splitTimeout`. `maxCores` is the configured `coreMax`, or the cluster size when it is unset `[guess]`. The removal bound counts each wait once, so it equals the window. At the defaults (`SwimConfig.DEFAULT`, `splitTimeout` 15 s), `coreSuspicion` goes from 246 s to 264.6 s at three cores and 266.6 s at five, and `coreRemoval` from 261 s to the same 264.6 s / 266.6 s. They drive rule (b) (when a listed core counts as alive) and the departure backstop. LEGACY is unchanged. The values are pinned exactly at the defaults with the derivation, beside a model built from SWIM's own constants, and a core listed exactly that long is never counted.

### Added (2026-10-23 — deployment state machine rewrite, phase 3 P3-F: engine marker restore and mixed clusters, retired identities, admission seam)
- **A restore leaves the deployment engine marker as the backup has it.** The restore's finish removes a marker the backup does not carry (a pre-phase-3 backup restores a LEGACY cluster) and replaces one it carries differently, in the same transaction as the incarnation and the `RESTORED` marker. The path where a leader without `[backup]` mints both keys mid-restore cannot finish on this branch yet (the restore-finish fix lands on `release-1.0.0-rc5` first); its two arms are disabled beside an enabled tripwire that goes red when it finishes.
  [verified: `aether/node/src/test/java/org/pragmatica/aether/node/backup/BackupRestoreCoordinatorTest.java`]
- **A terminated node's directive and departure record leave together, and a refused retirement is retried.** Under FSM2 the cluster topology manager's confirmed reap (B18) and the operator `--force` clear (B19) remove the node's `ActivationDirectiveKey` and `NodeDepartureKey` in one leader transaction, record first, each expecting the value read; a refused attempt is retried, re-reading both, only while the departure record is still the DEPARTED record first read (same epoch and process incarnation), or absent with the directive first read. A re-admitted record (ADMITTED) ends the retry and leaves the record and the directive in place. The retry also ends when it commits, when neither key is left, or when the node stops. A retirement still refused after two minutes raises the operator warning `termination-retirement-overdue` once, and `termination-retirement-resolved` when it ends. Under LEGACY they remove nothing. Community placement COMPLETE removes the record in its own transaction too, and a refused COMPLETE is retried by the next pass, which removes the directive and the record only while the record is DEPARTED or absent. A source tripwire is red when a new file deletes a directive (#1842's writer must retire the record with it).
  [verified: `aether/aether-deployment/src/test/java/org/pragmatica/aether/deployment/cluster/TerminationRetirementTest.java`, `aether/node/src/test/java/org/pragmatica/aether/node/NodeReplacementRealRegistryReapTest.java`, `aether/node/src/test/java/org/pragmatica/aether/node/deployment/RetirementGateTest.java`, `aether/node/src/test/java/org/pragmatica/aether/deployment/cluster/fsm2/RetiredIdentityReadersTest.java`, `aether/node/src/test/java/org/pragmatica/aether/deployment/cluster/fsm2/B18ReapDeleteReadersTest.java`, `aether/aether-deployment/src/test/java/org/pragmatica/aether/deployment/cluster/CommunityPlacementReconcilerTest.java`, `aether/node/src/test/java/org/pragmatica/aether/node/DirectiveDeletersTripwireTest.java`]
- **The deployment engine reads tokens and incarnations through one admission seam**, built before membership and bound to it late; a read before membership is bound is counted, a booted node counts none, and the routes' writer token comes from the seam.
  [verified: `aether/node/src/test/java/org/pragmatica/aether/node/DeploymentWiringBootTest.java`, `aether/node/src/test/java/org/pragmatica/aether/node/deployment/AdmissionSeamReadersTest.java`, `aether/node/src/test/java/org/pragmatica/aether/node/deployment/Fsm2RoutesTest.java`]
- **The engine marker is pinned across processes.** Ember takes a per-node engine override; a Heavy forge class runs a misconfigured observer newcomer in each direction (it refuses itself, writes nothing of its engine, and no other node exits) and FSM2 members that are up before the lineage mint (they wait and never refuse). The `CommunityKey` writers, the cluster FSM and the community placement reconciler, both real and on one store, are pinned not to lose a write in any order.
  [verified: `aether/forge/forge-tests/src/test/java/org/pragmatica/aether/forge/Fsm2EngineMarkerMixedClusterTest.java`, `aether/node/src/test/java/org/pragmatica/aether/deployment/cluster/fsm2/CommunityKeyWritersInterleaveTest.java`]
- **Named limit.** A newcomer that leads is covered at unit level only (a mismatching node activates nothing before it exits): Ember cannot restart an admitted voter with another engine.

### Removed (2026-10-23 — deployment state machine rewrite, phase 3 P3-F)
- **FSM2 consumes no `SelfShutdown` input** (it is never produced): a stopping node writes nothing, and its peers depart it through `NodeRemoved`, as under LEGACY.
