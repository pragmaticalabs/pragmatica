### Fixed (2026-10-28 — #686, #1726: the `aether cluster apply` ledger could be lost or torn)
- **The apply ledger (`apply-state.json`) was written with a plain truncate-and-write and its failures were discarded**, so a full disk or a kill mid-write left a torn file that resume and rollback then refused to read, and an apply whose first write failed went on to create billed VMs with no ledger behind them. The ledger is now schema 2 and is written durably (temp file, `force`, atomic rename, directory `force`); a failed write is a typed failure, and an apply whose ledger cannot be written stops before it executes anything. [verified: `ApplyStateDurabilityTest`, `ApplyOrchestratorTest$LedgerTests`]
- The schema-2 ledger carries the apply id (a lowercase ULID), the phase, the planned actions, per-node VM rows (`INTENDED` through `TERMINATED`), and node-number reservations, in place of the per-wave statuses that nothing ever updated. A ledger of any other schema, or with an unknown phase or state, is refused by name and left untouched. [verified: `ApplyStateTest`]
- A successful apply whose finished ledger cannot be removed now reports a warning instead of staying silent; the exit status still reflects the apply. [verified: `ApplyOrchestratorTest$LedgerTests.executeAndPersist_successButTheLedgerCannotBeRemoved_stillSucceeds`]
- The ledger write uses a unique temp file per write, so concurrent writers (two CLI processes on one cluster) no longer tear each other's file, and every control character in a recorded string is escaped so a ledger that was saved can always be read back. Only the integer `2` is accepted as the schema version (`2.0`, `2.9`, `2e0` are refused by name). [verified: `ApplyStateDurabilityTest.save_concurrentWriters_neverFail_andAReaderNeverSeesAnUnreadableLedger`, `ApplyStateTest.roundTrip_survivesEveryControlCodePoint_quotesBackslashesAndSurrogatePairs`, `ApplyStateTest.schemaVersion_fractionalOrExponentOrOutOfRangeForms_areRefused_namingTheSchema`]
- Reading the ledger removes the ledger's own `apply-state-*.tmp` files left by a killed writer, only those older than 10 minutes, and logs each removal; a file in flight (a concurrent writer's) is never touched. A ledger that cannot be read at all (permissions, an I/O error) is now reported as "could not be read", not as "refused", and a refusal says it was left untouched once. [verified: `ApplyStateDurabilityTest.read_sweepsTheLedgersOwnTempFilesOlderThanTheBound_andLogsEach`, `read_keepsATempFileInsideTheBound_soAWriterInFlightIsNeverTouched`, `ApplyStateLedgerRefusalTest$Reading.read_ioFailure_isReportedAsUnreadable_notAsARefusal`]
