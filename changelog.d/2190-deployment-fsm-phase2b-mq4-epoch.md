### Changed (2026-10-13 — #2190: deployment state machine rewrite, phase 2b follow-up: the leader-assigned admission epoch)
- **The admission epoch is the leader's, in the committed `NodeDepartureValue`, not membership's.** An admission writes `ADMITTED(committed + 1)` expecting the record value it read; a departure keeps the epoch of the admission it ends; a first admission is `ADMITTED(1)`. `Admission` carries the process only. A same-process heal is therefore re-admitted (J3 has no epoch comparison), where it fell into J9 for ever when every epoch was 0. Nothing is wired to the FSM: this changes no behaviour of a running cluster.
  [verified: `aether/node/src/test/java/org/pragmatica/aether/deployment/cluster/fsm2/AdmissionEpochTest.java`]
- **A committed DEPARTED is superseded only by evidence the leader observed after its own `Rebuild`**: a join input or C11f's re-admission, or (cores) one full suspicion window of continuous listing in its core SWIM view. The `Rebuild` seed never supersedes; a removal input and a C17s submission clear the evidence. C17b is deferred for a departed core that the leader's core view still lists, until the window resolves. A worker is re-admitted by C11f on a post-`Rebuild` roster or `localAlive` sample only for a STALE record or a record committed before the rebuild, never for a departure this leader decided (a removal input processed after `Rebuild` makes the departure its own). A listed core whose DEPARTED record names another process than the one membership admitted stops being pending once its window has resolved, and C17b proceeds. The suspicion window must be positive (`AbsenceBounds` refuses 0), so a `Rebuild` alone never promotes a core.
  [verified: `aether/node/src/test/java/org/pragmatica/aether/deployment/cluster/fsm2/JoinedEvidenceTest.java`]
- **A departure record leaves only through R-4.3.3** (a termination-confirmed directive removal): the step-10 record GC is removed, and an R-4.3.3 that is refused, lost, failed or decided while the leader is suspended is derived again from the mirror (under the guard: still departed, no directive) instead of being dropped. **Named limit:** a deposition or a `Rebuild` discards a pending R-4.3.3, and the record of that one terminated id is kept (growth of the kind MQ-4 already accepts for every ever-admitted id; no correctness effect, because the id cannot return). The end state moves the record removal into the termination authority's own directive-removal transaction (phase 3).
  [verified: `aether/node/src/test/java/org/pragmatica/aether/deployment/cluster/fsm2/AdmissionEpochTest.java`]
- `RoutedEvent.ActivationBlocked` carries the owning blueprint as a typed id, the artifact coordinates and the attempt count of the indexed schema record; a submission is released as lost after `Settings.submissionExpiry` (default the consensus `applyTimeout` plus 5 s); the divergence timeouts come from `Settings`; every correlation id names the process that minted it.
  [verified: `aether/node/src/test/java/org/pragmatica/aether/deployment/cluster/fsm2/SettingsSourcedTest.java`]
