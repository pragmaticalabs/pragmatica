### Added (2026-11-07 — #2450 A3-1: catalog seam and pure catalog core)
- **The content store's naming half is a `Catalog` seam.** Which objects exist, their names and their metadata now go through one internal interface; the store keeps the bytes (writers, manifests, chunk reads, block credits). `LocalCatalog` is the existing ref table, moved behind the seam, and every existing `ContentStore*Test` passes unchanged. One local behaviour did change, for the better: `delete` now reads the object's manifest first and removes the object from the catalog as one step that re-reads the entry. Before, a delete racing a rename could leave the new name bound to a deleted object, and deleting an object whose name binding was unreadable dropped the entry, then failed, and never released the manifest's credit. Now neither happens: the delete leaves no binding behind, and an unreadable binding fails it with `ENTRY_PARSE_FAILED` and nothing changed. No setting is added. [verified: `ContentStoreDeleteAtomicityTest`, red against the pre-seam store, and the existing `ContentStore*Test` suites]
- **The pure core the cluster catalog (A3-2) will commit with**, not wired to anything yet:
  - a copy-on-write B+tree of catalog pages stored as blocks (`CatalogPage`, format 1, envelope kind `P`), fanout 1000 by default: a million keys loaded at once fit in depth 2. A change rewrites only the pages on the paths to the keys it edits, once per page however many of its keys it edits, and every earlier root stays readable. Pages that only shrink are not merged with their neighbours. [verified: `PageTreeTest`]
  - a catalog root block (`CatalogRoot`: version, object tree, name tree, committed bytes, object count; envelope kind `R`);
  - one multi-mutation commit (`CatalogCommit`: create, patch, bind, remove): all of a commit's mutations land in one new root or none do, so a rename changes the entry, the new name and the old name in one step. A commit rebuilt on a newer root (the rebase after a lost CAS) checks its preconditions again there and keeps the winner's changes. [verified: `CatalogCommitTest`]
- **A catalog contract suite** (`CatalogContract`) runs against the local catalog and, through a test-only in-memory root, against the core; the cluster store runs it in A3-2. It pins finished-call properties only: a local rename still briefly carries both names, a cluster rename will not. [verified: `LocalCatalogContractTest`, `TreeCatalogContractTest`]
- **Limits of this slice:** no consensus, no tier storage of pages and no `metadata` setting: nothing runs the core outside tests until A3-2. Pages that shrink are never merged, so a tree emptied in places keeps its depth (only a root with one child collapses). Superseded pages are left for the A4 mark-sweep. The local catalog overwrites an entry on a second insert of one id, while the core refuses it; object ids are fresh per write, so the contract suite does not pin either.
