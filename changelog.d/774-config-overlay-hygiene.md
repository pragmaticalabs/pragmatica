### Fixed (2026-10-28 — #774: dynamic-configuration overlay and applier hygiene, PR-1 of the Watched/Live work)
- **A consistent read of the config overlay.** `DynamicConfigurationProvider` brackets every overlay write with a version counter (odd while a write runs; shared with the provider `reload()` returns) and offers `atomically(read)`: a read accepted only when no write started or finished while it ran, retried a bounded number of times and otherwise FAILED with `OVERLAY_KEPT_CHANGING` - never a torn result. `asMap()` and `overlayMap()` (the `/config/overrides` listing) use the same rule; they were copies taken while the applier was mid-sequence. [verified: `DynamicConfigurationProviderAtomicallyTest`, `DynamicConfigurationProviderSnapshotTest`]
- **`setConfig` / `setNodeConfig` / `removeConfig` / `removeNodeConfig` no longer write the overlay a second time.** The commit's own `onConfigPut` / `onConfigRemove` already did, inside `KVStore.mutate`; the continuation could put an older value over a later commit, silently (it notified nobody). [verified: `DynamicConfigManagerStaleContinuationTest`]
- **A throwing applied-listener no longer aborts the listeners behind it.** `DynamicConfigManager.notifyApplied` runs each listener inside `Result.lift` (logged, next listener still runs); before, the exception surfaced in the KV router's dispatch on the applier thread. [verified: `DynamicConfigManagerListenerIsolationTest`]
