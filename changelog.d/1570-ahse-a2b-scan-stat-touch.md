### Added (2026-11-07 — #1570 AHSE A2b: tier scan, stat and touch; ensureHeld)
- **Storage tiers can list, stat and refresh their blocks.** These are the operations the reclaim phase (A4) sweeps with. Nothing in a node calls them yet.
  - `StorageTier.stat(id)` returns the block's stored size and the time it was last written or refreshed: the file's modification time on a local disk, the provider's `Last-Modified` on S3 (whole seconds), the tier clock in memory. It returns none only when the tier does not hold the block.
  - `StorageTier.scan(shard, cursor, limit)` lists one page of a `KeyShard`. A shard is one of up to 256 contiguous runs of the block hash's first byte, so a disk tier walks only that run's directories and an S3 tier lists only that run's key prefixes. Pages come in ascending block-id order. Only a full page carries a cursor. Anchors, partial files, the mount claim and other non-block objects are never listed.
  - `StorageTier.touch(id)` moves the block's write time to now without the caller rewriting its bytes. On disk it sets the modification time and forces the file. On S3 it is a CopyObject of the object onto itself (metadata directive REPLACE): the provider rewrites the object and the node sends no bytes. It returns false and creates nothing when the tier does not hold the block.
  - The in-memory DHT tier keeps no write times and does not provide these operations. It refuses them with `OperationUnsupported` and never answers "empty" or "absent", so a sweep cannot mistake it for an empty tier.
  - [verified: `TierScanStatTouchContract` on memory, disk, S3 over an in-memory client and S3 on MinIO; `KeyShardTest`; `S3ClientTest`]
- **`StorageInstance.ensureHeld(id, tier)`** makes one tier of the instance hold a block, written or refreshed no earlier than the call. A tier that holds the block is touched. A tier that does not is written directly from another tier's copy, after that copy's hash is checked. It changes no reference count and moves no snapshot epoch. It is the re-seed of boot reconciliation and the freshness refresh of cluster GC. [verified: `StorageInstanceEnsureHeldTest`, `RemoteTierS3IntegrationTest`]

### Fixed (2026-11-07 — #1570 AHSE A2b)
- **A re-seed of a block whose record survived but whose shared copy did not now lands the block** (gap G2 of the upload-overhaul spec). For example, after a whole-cluster restart empties the in-memory DHT, the block is written again from the surviving disk copy. A `put` of content that is already recorded deduplicates onto the record and writes nothing, so a re-seed through `put` left the shared tier empty. `put` keeps that behaviour; re-seed and refresh use `ensureHeld`. [verified: `StorageInstanceEnsureHeldTest`, RED at rc5 `23c0bd8f6b` with the re-seed made by `put`]
- **A block promoted into the memory tier no longer counts as a metadata mutation.** Promotion recorded the copy as a change to the block's record, so every promoted block moved the snapshot trigger. Read load could then force snapshots (C-08 under read promotion). The copy is now recorded as an observation, like a read. [verified: `PromotionIsNotSnapshotStateTest`, RED at rc5 `23c0bd8f6b`]
