### Fixed (2026-09-13 — #270 R6: a malformed `@Http` URI threw out of `get`/`post`/… instead of failing the promise)
- **`JdkHttpClient` built every request through `Network.parseURI(uri).unwrap()`**, so a path or `base_url` that does not parse escaped `get`/`post`/`put`/`patch`/`delete`/`getBytes` (and the `*Json` methods over them) as a synchronous `IllegalStateException`, across the `Promise` boundary the client's contract promises. A second producer the ticket did not name: a URI that parses but has no scheme (`example.com/no-scheme`) passed the unwrap and threw `IllegalArgumentException("URI with undefined scheme")` from `HttpRequest.Builder.uri` — same symptom, different line.
- The request is now built as a `Result`: everything that touches the caller's input — the `base_url` join, `URI.create`, the `HttpRequest.Builder` scheme and header checks — runs inside one `Result.lift`, and a failure becomes the new `HttpClientError.InvalidRequest(uri, detail)` (`Cause.Terminal`: the same arguments produce the same refusal) on the returned promise, with `detail` = the exception's one-line message. The backend is never reached with a malformed request. A **null path** lands there too, with or without a `base_url` — round 1 ran the join before the lift, so a null path threw `NullPointerException` synchronously when a base was configured while failing the promise without one (review of #1080, SF-3); and round 1 built `detail` from `Causes.fromThrowable`, whose message is the whole stack trace, so every `InvalidRequest` carried ~90 lines (SF-2). `URI.create` is used instead of `Network.parseURI` for that reason — the latter's cause is a `fromThrowable`. [verified: `JdkHttpClientMalformedUriTest` (`aether/resource/http`) — 13 pins, one per request method plus `getJson`, a malformed `base_url`, and a null path with and without a base, each asserting the call does not throw, the promise fails, and a counting `HttpOperations` saw zero sends; `#malformedUri_failsAs_terminalInvalidRequest_withOneLineDetail` and `#schemelessUri_failsAs_terminalInvalidRequest` assert the cause IS `InvalidRequest`, `isTerminal()`, and `detail` has one line (SF-1: round 1 had no pin reading the cause). Red at the base: `IllegalStateException: Unwrap error: … URISyntaxException` (7) and `IllegalArgumentException: URI with undefined scheme` (1) and the base-url case; a well-formed control reaches the backend exactly once. Mutations, each reverting one hunk and reddening a distinct named set: mapping replaced by a generic cause → the two type pins; base join hoisted before the lift → `get_withNullPath_andBaseUrl_failsThePromise_doesNotThrow`; detail built from `Causes.fromThrowable` → the two one-line-detail pins]. Every `await` in the pin class carries a 5 s timeout (N-2), so a wedged promise reddens rather than hangs.
- `HttpClientError` (`aether/resource/api`) gains one record; it is a sealed interface and nothing outside the two modules switches over it (repo grep: zero `case HttpClientError.` / `switch` sites), so the addition is not a signature change for any dependent. [mechanism: additive sealed member; `aether/node`, the only `resource-http` dependent, test-compiled clean against it]
- The other `unwrap()` the ticket cites, `jdkHttpClient()`'s `HttpClientConfig.httpClientConfig().unwrap()`, is left: that factory and its six overloads return `success(new HttpClientConfig(…))` unconditionally at this tip and cannot fail, and the no-arg `jdkHttpClient()` is package-private with a single test-only caller (`HttpClientTest`) — a fold there would have a dead branch. [mechanism: read at `HttpClientConfig.java`; caller enumerated by repo grep]
- `Result.lift` catches `Throwable`, so an `Error` raised while building the request also lands in the promise as `InvalidRequest` — the core library's contract, shared with the base's `Network.parseURI`; stated, not changed. After the fold the send path cannot throw to the caller; whether a backend's own `sendAsync` can leave the promise unresolved is `integrations/net/http-client`'s pre-existing shape (review of #1080, N-4), outside this change.
- **R7 is NOT in this change and is stated as left:** the TLS/mTLS/proxy configuration surface, per-request timeout override, and `Content-Type` respecting the body type / caller headers replacing defaults are a feature (owner comment 2026-08-26: "Deferred post-GA: TLS configuration surface"). The JSON `Content-Type` header on `post`/`put`/`patch` is unchanged.
