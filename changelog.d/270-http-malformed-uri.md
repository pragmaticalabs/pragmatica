### Fixed (2026-09-13 — #270 R6: a malformed `@Http` URI threw out of `get`/`post`/… instead of failing the promise)
- **`JdkHttpClient` built every request through `Network.parseURI(uri).unwrap()`**, so a path or `base_url` that does not parse escaped `get`/`post`/`put`/`patch`/`delete`/`getBytes` (and the `*Json` methods over them) as a synchronous `IllegalStateException`, across the `Promise` boundary the client's contract promises. A second producer the ticket did not name: a URI that parses but has no scheme (`example.com/no-scheme`) passed the unwrap and threw `IllegalArgumentException("URI with undefined scheme")` from `HttpRequest.Builder.uri` — same symptom, different line.
- The request is now built as a `Result` — `Network.parseURI` for the parse, `Result.lift` around `HttpRequest.Builder` for the scheme and header checks the JDK performs — and a failure becomes the new `HttpClientError.InvalidRequest(uri, detail)` (`Cause.Terminal`: the same arguments produce the same refusal) on the returned promise. The backend is never reached with a malformed request. [verified: `JdkHttpClientMalformedUriTest` (`aether/resource/http`) — 9 pins, one per request method plus `getJson` and a malformed `base_url`, each asserting the call does not throw, the promise fails, and a counting `HttpOperations` saw zero sends; red at the base with `IllegalStateException: Unwrap error: … URISyntaxException` (7) and `IllegalArgumentException: URI with undefined scheme` (1) and the base-url case; a well-formed control reaches the backend exactly once. Mutation: reverting `JdkHttpClient` to the base reddens exactly the 9 pins, control stays green]
- `HttpClientError` (`aether/resource/api`) gains one record; it is a sealed interface and nothing outside the two modules switches over it (repo grep: zero `case HttpClientError.` / `switch` sites), so the addition is not a signature change for any dependent. [mechanism: additive sealed member; `aether/node`, the only `resource-http` dependent, test-compiled clean against it]
- The other `unwrap()` the ticket cites, `jdkHttpClient()`'s `HttpClientConfig.httpClientConfig().unwrap()`, is left: that factory is `success(new HttpClientConfig(…))` unconditionally at this tip and cannot fail — a fold there would have a dead branch. [design intent — unverified: read, not probed]
- **R7 is NOT in this change and is stated as left:** the TLS/mTLS/proxy configuration surface, per-request timeout override, and `Content-Type` respecting the body type / caller headers replacing defaults are a feature (owner comment 2026-08-26: "Deferred post-GA: TLS configuration surface"). The JSON `Content-Type` header on `post`/`put`/`patch` is unchanged.
