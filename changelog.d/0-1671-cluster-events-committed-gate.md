### Fixed (2026-10-29 — #1671: a KV-derived cluster event could be raised twice or dropped across an ownership handover)
- **The cluster-events owner gate read the node-local view, so two nodes straddling a handover could both raise a fact, or neither** (#1671). The facts derived from a committed KV notification (deployment started/completed/failed, community and roster changes) are now gated on the committed `StreamPartitionOwnershipKey` of the cluster-events partition as of that notification (in commit order, so every node decides from the same state); with no record, the lowest member of the installed voter configuration raises it. Facts raised from anywhere else (ISR transitions, connections, access denials, scaling, config and blueprint events) keep the node-local gate and its residual duplicate or drop. [verified: `ClusterEventAggregatorCommittedGateTest`]
