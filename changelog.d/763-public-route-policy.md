### Fixed (2026-09-05 — #763: a route declared `public` was treated as undeclared and inherited the global auth policy)

- **A route with no `[security]` section at all could not be distinguished, at request time, from one explicitly declared `default = "public"`** — `RouteConfigLoader` collapsed both cases to `RouteSecurityLevel.PUBLIC` during codegen, so `AppHttpServer`'s `isExplicitPolicy` check had nothing left to key off. The ticket's own cite (`AppHttpServer.isExplicitPolicy`) was not wrong, only incomplete — the actual defaulting happened one layer earlier, in codegen. `RouteSecurityLevel`/`SecurityPolicy` gained a third state, `Unspecified`, distinct from `Public` and `Authenticated`: an undeclared route now inherits the server's global policy (auth required when the global policy requires it), an explicitly `public` route bypasses the global policy for exactly that route, and an explicitly authenticated route is unchanged
  [verified: `aether/node/src/test/java/org/pragmatica/aether/http/AppHttpServerRouteSecurityPolicyTest.java` — real `AppHttpServer` in API_KEY mode, three states, real `HttpClient`].
- `Unspecified` is a compile-time/codegen-only concept — no route is ever SERVED carrying it; resolution to a concrete policy happens once, at registration
  [mechanism: `RouteMetadataExtractor.resolveSecurityPolicy` resolves before the route reaches the server; an unresolved value reaching request time would fail closed to "inherit the global policy", never "public" — no such path exists today].
- **A second site carried the same defect**: `RouteMetadataExtractorImpl.resolveSecurityPolicy`, used for hand-written/programmatic routes rather than codegen-produced ones, also defaulted an undeclared route to `publicRoute()` instead of `unspecified()`. Fixed and pinned by its own test
  [verified: `aether/aether-invoke/src/test/java/org/pragmatica/aether/http/RouteMetadataExtractorSecurityPolicyTest.java`].
- **Two of the three HTTP security validators had a fail-open `default` arm**, not merely a non-exhaustive one: `ApiKeySecurityValidator` and `JwtSecurityValidator` granted access unconditionally for any policy value their explicit `case`s didn't name — in practice reachable only by the `Unspecified` sentinel or a dead placeholder type, since every real policy constant is already handled by an explicit case. Unreachable in production (the server resolves `Unspecified` away before dispatch), but a fail-open trap for any direct caller. Flipped to deny via a new `SecurityError.UNRESOLVED_POLICY`
  [verified: `ApiKeySecurityValidatorTest#validate_denies_forUnspecifiedPolicy`, `JwtSecurityValidatorTest$PolicyVariantTests#validate_denies_forUnspecifiedPolicy`].
  A third validator, `KvStoreApiKeyValidator`, has a structurally different default arm (delegates to a real credential check, matching the existing documented "unconfigured = open" pattern) and was deliberately left unchanged.
- Docs updated: HTTP adapter reference — `PUBLIC` declaration semantics and the three-state resolution.
