### Fixed (2026-09-05 — #763: a route declared `public` was treated as undeclared and inherited the global auth policy)

- **Action required if you run `security_mode = "api-key"` or `"jwt"`.** A route whose `routes.toml`
  has no `[security]` section used to answer `200` unauthenticated; after this fix it inherits the
  global `security_mode` and answers `401`/`403` instead (that is the defect this ticket fixes — see
  the next bullet). 16 non-test `routes.toml` files in this repo are in that state today, all under
  `examples/` and `aether/e2e-tests/`. Add `[security]` / `default = "public"` to any of them whose
  routes must stay open. `security_mode = "none"` deployments are unaffected.
- **A route with no `[security]` section at all could not be distinguished, at request time, from one explicitly declared `default = "public"`** — `RouteConfigLoader` collapsed both cases to `RouteSecurityLevel.PUBLIC` during codegen, so `AppHttpServer`'s `isExplicitPolicy` check had nothing left to key off. The ticket's own cite (`AppHttpServer.isExplicitPolicy`) was not wrong, only incomplete — the actual defaulting happened one layer earlier, in codegen. `RouteSecurityLevel`/`SecurityPolicy` gained a third state, `Unspecified`, distinct from `Public` and `Authenticated`: an undeclared route now inherits the server's global policy (auth required when the global policy requires it), an explicitly `public` route bypasses the global policy for exactly that route, and an explicitly authenticated route is unchanged
  [verified: `aether/node/src/test/java/org/pragmatica/aether/http/AppHttpServerRouteSecurityPolicyTest.java` — real `AppHttpServer` in API_KEY mode, three states, real `HttpClient`].
- `Unspecified` is a compile-time/codegen-only concept — no route is ever SERVED carrying it; resolution to a concrete policy happens once, at registration
  [mechanism: `RouteMetadataExtractor.resolveSecurityPolicy` resolves before the route reaches the server; an unresolved value reaching request time would fail closed to "inherit the global policy", never "public" — no such path exists today].
- **A second site carried the same defect**: `RouteMetadataExtractorImpl.resolveSecurityPolicy`, used for hand-written/programmatic routes rather than codegen-produced ones, also defaulted an undeclared route to `publicRoute()` instead of `unspecified()`. Fixed and pinned by its own test
  [verified: `aether/aether-invoke/src/test/java/org/pragmatica/aether/http/RouteMetadataExtractorSecurityPolicyTest.java`].
- **Two of the three HTTP security validators had a fail-open `default` arm**, not merely a non-exhaustive one: `ApiKeySecurityValidator` and `JwtSecurityValidator` granted access unconditionally for any policy value their explicit `case`s didn't name — in practice reachable only by the `Unspecified` sentinel or a dead placeholder type, since every real policy constant is already handled by an explicit case. Unreachable in production (the server resolves `Unspecified` away before dispatch), but a fail-open trap for any direct caller. The `default` arm is now **deleted, not merely denied** — both switches are exhaustive over the sealed `SecurityPolicy` hierarchy with an explicit `Unspecified` case returning a new `SecurityError.UNRESOLVED_POLICY`, so the next constant anyone adds is a compile error rather than a silent fail-open
  [verified: `ApiKeySecurityValidatorTest#validate_denies_forUnspecifiedPolicy`, `JwtSecurityValidatorTest$PolicyVariantTests#validate_denies_forUnspecifiedPolicy`; compile-time exhaustiveness — removing either validator's `Unspecified` case no longer compiles].
  A third validator, `KvStoreApiKeyValidator`, has a structurally different default arm (delegates to a real credential check, matching the existing documented "unconfigured = open" pattern) and was deliberately left unchanged.
- **`SecurityOverrideApplier`'s `strengthen_only` check was meaningless on undeclared routes**: it compared `newPolicy.strength()` against the route's raw declared strength, and `Unspecified`'s is `-1` — so any override, including a downgrade to `public` (strength `0`), passed the "strengthen only" check. The applier cannot see the deployment's global security mode at publish time (`aether-invoke` does not depend on `aether-config`), so it cannot compute the route's true effective strength. It now judges only the DIRECTION of the change on such a route: an override to `public` is refused (it is the floor under every global mode, so it can only weaken); every other override is applied
  [verified: `SecurityOverrideApplierTest$StrengthenOnlyPolicyTests` — `unspecified -> public` rejected, `unspecified -> authenticated` and `unspecified -> role:admin` applied; reverting the guard turns the latter two red].
- **Known residual on the above, stated plainly.** Under `security_mode = "api-key"` (the default), an override to `authenticated` (strength `10`) on an undeclared route whose effective policy is `ApiKeyRequired` (strength `20`) is a weakening this rule still permits. Closing it requires the override path to know the global security mode, which is a design change deferred past rc4. Declare `[security]` explicitly on any route where the distinction matters
  [design intent — unverified: no test covers the residual, because the current code permits it by construction].
- **A remote node's route could govern a local route's security decision.** Policy lookup consulted remote routes whenever the LOCAL route carried no explicit policy — but remote matching is by PREFIX, and `computeRouteTable` excludes a remote route only on exact `method:pathPrefix` identity. With `Public` now an adoptable explicit policy, a broader remote prefix (`/api/v1/pricing/`) could supply a `public` policy to a narrower undeclared local path (`/api/v1/pricing/analytics/`) and the local route would be served with no credential. This is reachable in the partially-migrated state this very changelog's "action required" instructions produce — parent slice migrated, child not yet. A matched LOCAL route now governs its own policy outright: `Unspecified` means "inherit the global policy", never "ask a remote node". Dispatch was already local-first, so the policy decision now agrees with the route that actually serves the request
  [verified: `AppHttpServerRouteSecurityPolicyTest#dispatch_doesNotAdoptRemotePolicy_whenLocalRouteMatchedButUndeclared` — live `AppHttpServer`, real `HttpRouteRegistry` carrying a remote public parent prefix; reverting the hunk turns 401 into 200].
- **`SecurityPolicy.asString()` and `strength()` kept fail-soft `default` arms** (`default -> "API_KEY"`, `default -> 20`) while the validators two methods away had theirs deleted. `SecurityPolicy` is sealed over seven records and both switches covered six, so the arms were live, not dead: a newly added state would have been silently persisted to the KV store as `"API_KEY"` and scored `20` — a fabricated wire value and a fabricated strength, on the override-comparison and cross-node resolution paths. Both `default` arms are removed and every case is handled explicitly
  [verified: adding a new sealed state fails compilation at both switches ("the switch expression does not cover all possible input values"); restoring the `default` arms makes that same state compile silently].
- **`SecurityPolicy.fromString`'s `"UNSPECIFIED"` case had no test** and could be deleted with the whole suite green. Without it, an `UNSPECIFIED` entry read back from a remote node falls through `parseRoleOrDefault` to `apiKeyRequired()` — an explicit policy, which is then adopted instead of the global fallback
  [verified: `SecurityValueObjectsTest#fromString_unspecifiedDeserialization` and `#fromString_unspecifiedRoundTrip_throughAsString`; deleting the case turns both red].
- **Mixed-version wire note — read before upgrading.** `NodeRoutesValue.RouteEntry.security` is a persisted `String` whose value domain gains `"UNSPECIFIED"`. A node running an older build lacks the `fromString` case, falls through `parseRoleOrDefault`, and resolves the value to `apiKeyRequired()`. That is fail-closed in DIRECTION — the route demands a credential rather than becoming public — but it is a behaviour change across versions: the older node enforces `api_key` on a route whose owner declared nothing and expected the global policy. **This is not a statement that mixed-version clusters are safe.** Aether does not support rolling upgrades (#666/#434: no join-time version check, no wire negotiation); the supported path is full-cluster stop, upgrade, start. Recorded here because the value domain changed, not because a mixed-version cluster is sanctioned
  [mechanism: `SecurityPolicy.parseRoleOrDefault` returns `apiKeyRequired()` for any unrecognized value; see `aether/docs/reference/known-limitations.md`].
- **Round-trip gap**: codegen's `RouteSecurityLevel.toConfigString()` could emit `"unspecified"` into the generated manifest, but `RouteSecurityLevel.parse()` had no matching case and would fail with "Unknown security level: unspecified". Added the missing case. Also operator-visible: `GET /api/v1/routes` and the dashboard now report `UNSPECIFIED` (not `PUBLIC`) for a route with no `[security]` section
  [verified: `RouteSecurityLevelTest` — parse/toConfigString round trip for all four states].
- Docs updated: HTTP adapter reference — `PUBLIC` declaration semantics and the three-state resolution.
