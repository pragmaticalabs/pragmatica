### Fixed (2026-09-23 — #1481: the integration harness destroyed the evidence of a failed cloud run, and an aborted run reported success)
- **A failed cloud bootstrap deleted every VM before anyone could read why.** `run-tests.sh` called `aether cluster bootstrap` without `--keep-on-failure`, so on 2026-09-23 a formation that reached 4 of 5 cores was rolled back with its cloud-init and node logs. The new `--keep-on-failure` harness flag forwards to both bootstrap calls and, on any non-zero exit (an interrupt included), skips teardown, prints the per-cluster reaper commands (the kept VMs are billable), and still closes the PG firewall. A green run still tears down. [verified: cloud smoke run `--suites 00 --keep-on-failure`, 13/13 passed, rc 0, teardown destroyed all 5 resources] [mechanism: preserve path observed on an abort BEFORE provisioning — so "VMs kept after a real failure" is shown by the branch taken, not by a surviving VM; flag forwarding to both bootstrap calls shown against a stub CLI]
- **A run aborted by `set -u` exited 0.** macOS `/bin/bash` 3.2 loses an unbound-variable abort's status whenever an EXIT trap runs — it enters the trap with `$?`=0 and exits 0 (1 without a trap) — so capturing `$?` cannot catch it. Success is now proven only by reaching the final `exit`; a 0 without it becomes 1. [mechanism: three-arm run aborting at the same unbound expansion — the previous script exited 0, this one exits 1 with and without the flag; deleting the `RUN_REACHED_END=true` line makes a green run exit 1]
- **One failing teardown step no longer aborts the rest of teardown.** errexit stayed on inside the EXIT handler, so a failing remote teardown step ended the handler early (status 255, later steps skipped). The handler now runs with errexit off and re-raises the run's own status. [mechanism: reviewer probe on a stubbed remote teardown]
- Limitation: on a full run cluster A is still reaped before cluster B's bring-up, so the flag cannot keep A after a failure in A's suites. [design intent — unverified]
