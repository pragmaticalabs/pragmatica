### Fixed (2026-09-29 — #1408: `jbct:package-slices` dropped a slice dependency silently when it matched no packaging rule)
- **`jbct:package-slices` now fails the build when a slice declares a dependency that would reach no `[slices]` entry.** A consumer compiled without `-Aslice.groupId` / `-Aslice.artifactId` got a package-derived coordinate for its sibling provider. The goal matched only `groupId:artifactId-` and dropped it without a word, the runtime read an empty `[slices]` section, and the slice died at load with a `NoClassDefFoundError` naming the provider interface. The failure names the interface, the emitted coordinate and the two compiler options. A dependency is accounted for when it is a sibling this module packages, or when a direct Maven slice dependency's manifest declares its interface. [verified: jbct/jbct-maven-plugin/src/test/java/org/pragmatica/jbct/maven/PackageSlicesDependencyReconciliationTest.java; and by a real `mvn package` of `examples/step-composition` with its two `-A` options removed — the rc4 plugin exits 0 with no `[slices]` section and three package-derived coordinates, this plugin refuses naming all three]
- Every other slice build in this repository still packages: the 23 slices in the root reactor and the 13 standalone blueprint/example projects, including the four whose manifests declare slice dependencies (`place-order`, `step-composition`, `banking/transfer`, `pricing-engine`).
- **Behaviour change: an unreadable jar on any DIRECT dependency now fails `jbct:package-slices`**, whether or not that dependency is a slice. The goal must open each direct dependency's jar to learn whether it provides slices. When the read fails, the build stops with `Cannot read <groupId:artifactId> (<file>) to find its slice manifests: …` instead of treating the jar as "no slices". That silence used to turn an unreadable provider into a refusal telling the user to add a dependency they already declare. Operator action: re-resolve or rebuild the named artifact (a truncated download in the local repository is the usual cause). Transitive dependencies are not opened, so an unreadable transitive jar is unaffected. [verified: `PackageSlicesDependencyReconciliationTest.processManifest_unreadableDirectDependencyJar_refusesNamingTheJar_notAMissingDependency`]
