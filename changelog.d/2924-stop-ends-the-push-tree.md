### Fixed (2026-11-09 — #2924: KV backup git started a pre-push hook after stop() returned)
- **`KvBackupService.stop()` returned while a push that was already past its guard was still alive**, and git could fork its pre-push hook milliseconds later (a hook started 6-8 ms after the return in 5 of 160 loaded runs, 284 ms on CI). `stop()` now closes the backup repository to git first, so no git starts after it and a git starting concurrently is either registered (and killed) or refused, then freezes (`SIGSTOP`) the whole process tree of the push in flight, reading it again until a read after the freeze adds nothing, and kills it. It returns when the tree is dead, within the repository's command timeout. [mechanism: `GitProcesses` takes one lock for spawn and close; a frozen process forks no child] [verified: `KvBackupStopFlushRaceTest#stop_returnsOnlyWhenThePushTreeIsDead_soNoHookStartsAfterIt`, `GitProcessesTest#kill_leavesNoChildOfATreeThatKeepsForking`]
- A tree that is not dead within the bound is reported, not passed off as a clean stop: a WARN log and `BACKUP_STOP_FLUSH_FAILED` (a push may still land after the stop; the next successful flush closes the warning). A hook that detaches itself from the process tree (a double-forked daemon) is outside what a parent-child walk can find. The remote stays unchanged by an interrupted push (git's atomic ref update, #2956) [verified: `KvBackupStopFlushRaceTest#stop_duringAPush_leavesTheRemoteUnchanged`].
