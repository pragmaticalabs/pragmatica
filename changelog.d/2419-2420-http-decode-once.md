### Fixed (2026-10-25 — #2419: HTTP/3 did not percent-decode the path or query; #2420: management path parameters were decoded twice)
- **The same request target reached a handler differently over HTTP/1.1 and HTTP/3.** HTTP/3 passed `path()` and `queryParams()` through undecoded, so `GET /echo/a%2Fb/c%41?x=a%20b%2Bc` was `/echo/a/b/cA` with `x=[a b+c]` over HTTP/1.1 and `/echo/a%2Fb/c%41` with `x=[a%20b%2Bc]` over HTTP/3. Both transports now build the path and the query from one decode, with `+` literal in the path and a space in the query. [verified: `integrations/net/http-server/src/test/java/org/pragmatica/http/server/RequestTargetParityTest.java`]
- **A management path parameter was decoded twice.** The server decoded the path, and `RouteMatcher.match` decoded each parameter again, so `GET /api/v1/deploy/%2541` handed the handler `A` instead of `%41`, and `a%2Bb` arrived as `a b`. The matcher now takes the decoded path as it is, and the consumer-group rebuild route no longer decodes its group a third time; a group name may contain `%`. Over HTTP/3 the second decode would have started once HTTP/3 decoded the path, so both land together. [verified: `aether/node/src/test/java/org/pragmatica/aether/api/ManagementPathParamTransportParityTest.java`, over a real HTTP/1.1 listener and a real HTTP/3 listener]
- **A request target with a malformed percent-escape (`/x%zz`, `/x%`, `?a=%zz`) is answered 400 on both transports and never dispatched.** Over HTTP/1.1 the decoder's exception used to close the connection with no response. [verified: `RequestTargetParityTest`]
