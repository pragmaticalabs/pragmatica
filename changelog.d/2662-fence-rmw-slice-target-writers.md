### Fixed (2026-11-05 — #2662: read-modify-write writers of a slice target could revert a republish or re-create a deleted blueprint's target)
- **Four writers of `SliceTargetKey` read a target, derived a value and issued a plain put**, so commit order decided the outcome: a put committing after a blueprint delete re-created the target of a deleted blueprint, and one committing after a republish reverted the target to the version it was derived from. The deployment manager (start and rollback), the A/B test manager (create, conclude, rollback), the scale route and the autoscaler now each write ONE leader transaction whose mutation expects the exact target value read and which witnesses the target's owning blueprint at its committed value; the applier refuses the transaction if either moved, whatever the commit order.
- **Absent target, per writer.** Deployment start and the scale route create a missing target only when the owning (or declaring) blueprint is committed, witnessed by it; otherwise the write is refused. Deployment rollback and A/B rollback skip a base whose target or owner is gone (logged), and the deployment or test still ends. A/B variant deployment and winner promotion refuse an absent target to the caller. The autoscaler never creates a target.
- **Refused writes.** Deployment, A/B and scale writes carry an explicit operator intent (version, instance count), so a refused write is rebuilt from a fresh read and resubmitted, at most five times, then fails as contended. The autoscaler's count is derived from the target it observed (its count, cap and floor), so a refused scaling write is dropped, not rebuilt, when the committed target differs from the observed one: the next control-loop tick recomputes the decision from the committed target. An operator scale made while a decision was in flight stands, and a lowered cap is never exceeded. The drop is logged at INFO.
