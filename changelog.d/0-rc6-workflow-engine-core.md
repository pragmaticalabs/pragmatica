### Added (2026-11-05 — rc6 §4: workflow engine core, internal)
- **Workflow engine core** (rc6 §4.2–§4.4, internal; no workflow kind, API or CLI uses it yet). A workflow run is a committed record (`WorkflowRunKey` → `WorkflowRunValue`: kind, params, step index, attempts, effects, deadline, state `RUNNING`/`WAITING`/`PAUSED`/`DONE`/`FAILED`/`ESCALATED`, conflict keys). **Admission is one leader transaction** that creates the run and claims every conflict key expecting it absent: at most one admitted workflow holds a given key at a time, and a refused admission names the holder's run id [mechanism: a consensus-committed claim created only if absent and deleted only in the transaction committing the run's `DONE` or `FAILED`; [verified: `WorkflowAdmissionTest` — unit level, real KV applier, not multi-node]]. The leader reconciler commits the issue of a step's effect before performing it and re-checks an issued effect by its postcondition, re-issuing only after the step's settle window; attempt, elapsed-time and effect budgets escalate the run with a `workflow-escalated` operator event naming the unobserved postcondition (raised at most once per owner tenure by the cluster-events owner, a hand-off can duplicate or lose it, see `0-rc6-f2b-l1a`; the committed run keeps the incident as its detail), and the escalated run keeps its claims until it is resumed or abandoned (the operator verbs arrive with the workflow API, rc6 f2b) [verified: `WorkflowPilotTest` — unit level, leader change modelled by the committed leader record]. The effect is performed only while the node still leads; an accepted effect can still run on a deposed leader concurrently with a later attempt, so executors must be fenced and idempotent per (run id, step index); settle and deadline hold modulo inter-node clock skew. Wire tags 2220–2224.
