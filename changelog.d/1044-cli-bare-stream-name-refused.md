### Fixed (2026-09-13 — #1044: the CLI's bare stream name silently addressed an empty `system:` ring)
- **`aether streams read|status|publish|delete <bare-name>` returned an empty result for every application stream, and exited 0.** A bare name defaulted to `system:<name>:1.0.0`, which `StreamEngineKey` reduces back to a bare engine key — while engine-key qualification (#1040) moved application streams to `<blueprint-namespace>:<stream>:<version>`. The command succeeded against a ring that holds nothing, so an operator asking where their events had gone was told, in effect, that there were none. Measured on a live 5-node cluster with 20 events present, contiguous from offset 0: the bare name returned **0 of 20**, the full identity **20 of 20**, same cluster and instant. [verified: `aether/tests/integration/suites/02-chaos/test-stream-replica-failover.sh` — the harness reads by full identity and reports `all 20 markers readable post-failover`]
- A bare name is now refused with a message naming the form to retype — the caller's namespace **and** the `system:<name>:1.0.0` spelling the bare form used to mean — plus a pointer to `aether streams list`, which prints the catalog address of every stream. A refusal that does not say what to write instead only relocates the problem. [mechanism: `StreamAddressResolutionTest.resolveStreamAddress_bareName_namesTheFullFormAndTheSystemSpelling` asserts both remedies are present in the failure, not merely that it failed]
- **`system`-namespace streams remain reachable, spelled in full** — the change removes an ambiguous shorthand, not a capability. [mechanism: `resolveStreamAddress_fullSystemAddress_stillResolves`]
- This repo had already made the argument, for the neighbouring route: the non-`--local` replicas endpoint deliberately has no bare-name convenience because "a stream identity that could silently mean two different engine keys is worse than requiring the caller to say which one". That reasoning was written before the condition became true for these four commands.
- **The test that pinned the old behaviour was replaced rather than deleted.** `resolveStreamAddress_bareName_defaultsToSystemNamespaceAtDefaultVersion` was correct about the code and wrong about the requirement — it specified the defect. The replacement records why. [mechanism: reverting the resolver alone reddens exactly the two new bare-name tests, with `Success(system:orders:1.0.0)` in the failure message]
