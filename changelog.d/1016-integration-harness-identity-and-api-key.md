### Fixed (2026-09-13 — #1016 follow-up: the dual-cluster integration harness could not form a cluster, and its stream assertions were measuring the wrong thing)
- **The docker/remote integration suite could not form a cluster at all on the release tip.** #1016 removed the built-in ADMIN credential from the published node image and compensated by adding `AETHER_API_KEYS` to `docker-compose.yml` — but the dual-cluster harness runs on `docker-compose-a.yml` and `docker-compose-b.yml`, and neither received the line. Every readiness probe returned `AUTH_FAILURE reason=Invalid API key` for the full 360s window on both clusters, then teardown; no suite ran. All three files declare `AETHER_CLUSTER_SECRET`, so they are otherwise parallel. [verified: `aether/tests/integration/suites/02-chaos` — formation went from a 360s timeout on both clusters to 9s and 13s]
- **Stream assertions addressed a stream that no longer exists, then searched it for a string that cannot appear.** Two independent stale premises, layered so only one was observable at a time.
  - *Addressing.* The 2026-09-02 catalog migration moved stream routes to `/streams/{ns}/{stream}/{version}/<verb>`; the harness kept calling the pre-migration flat shape, which does not 404 but MISROUTES — `RouteMatcher` buckets by `(method, segment count)`, and the 6-token `/streams/replicas/{name}/{partition}` lands in the same bucket as `STREAMS_METADATA`, which absorbs it as `namespace="replicas"`, `version="{partition}"`. Measured against a live node: `500 "Resource version must match MAJOR.MINOR.PATCH"`, while a well-formed-but-absent triple returns `500 "Stream not found"` — same handler, different failure, which is what identifies the misroute. `lib/cluster.sh` now resolves the catalog coordinate from the live catalog (`stream_coordinate`, `stream_identity`) rather than hard-coding a spelling that can rot the same way. [verified: `aether/tests/integration/suites/02-chaos/test-stream-replica-failover.sh` — publish went from 0/20 to 20/20]
  - *Encoding.* Completeness was counted by grepping each marker's **Base64** form, on this file's own stated premise that "the READ path Base64-ENCODES it back (`EventRecord.fromRawEvent`)". That premise is false: measured at both layers on a live cluster, `GET /api/v1/streams/{ns}/{stream}/{version}/read/0` and `aether streams read <identity> 0 --format json` both return `data` RAW — raw marker present once, Base64 form zero times. Every completeness assertion was therefore searching for a string that could not appear. The defect was MASKED until the addressing fix landed, because before it the read reached a different ring and returned no events at all. [verified: same suite — `all 20 markers readable post-failover (1s)`, `all 5 post-repair markers readable (1s)`]
- **An assertion that scored an error state as a pass.** `assert_ne "$owner" "none"` is vacuously true for the empty string, so an unresolved HRW owner logged a PASS immediately after the neighbouring `assert_ne "$owner" ""` correctly FAILED on the same value. Replaced with a positive check that the owner is a real NodeId. [mechanism: the replacement fails on `""` and on `"none"`, where the original failed on neither; observed passing on an empty owner in the 2026-09-12 run]
- **`aether streams read` and its siblings default a bare name to the `system` namespace**, which after engine-key qualification (#1040) can never address an application stream. The harness now passes full `namespace:stream:version` identities. The CLI's bare-name convenience is left as-is and is worth its own issue: it silently resolves to a different engine key than the caller means, which the same file already argues against for the non-`--local` replicas route ("a stream identity that could silently mean two different engine keys is worse than requiring the caller to say which one"). [design intent — unverified: no change was made to the CLI here]
- **Cloud full-drain recovery is now diagnosable when it fails.** `_cloud_full_drain_recover`'s re-bootstrap ran with `--timeout 300` and without `--keep-on-failure`, so a failure deleted all five fresh VMs along with the cloud-init and node logs explaining it — observed on 2026-09-12, where the rebootstrap reached "All nodes healthy" and then failed the quorum gate with nothing left to read. Raised to 600s and preserved on failure, with a WARN naming the reap command since the kept VMs are billable. [mechanism: `--keep-on-failure` is an existing `aether cluster bootstrap` flag, verified present on the CLI under test; the failure path itself has not been re-run]
