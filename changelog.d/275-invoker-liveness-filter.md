### Fixed (2026-09-14 — #275: slice-to-slice routing had no liveness filter, so a call to a dead node hung for the invoker timeout)
- **Slice-to-slice endpoint selection never consulted membership.** `SliceInvokerImpl` picked from `EndpointRegistry`, a projection of committed `NodeArtifactKey` rows that outlive a dead node until the cluster deployment manager's removal cleanup lands, so a new invocation was round-robined (or affinity-pinned, or failed over) onto a node membership already knew was gone and waited out the 20s `DEFAULT_TIMEOUT_MS`. The HTTP forward path had `AccessibilityFilter` (`MembershipFsm.reachableMembers`: every member not co-confirmed DEAD) since the H7 fix; the facade path had nothing. [mechanism: `SliceInvokerImpl.selectEndpoint` / `selectEndpointWithAffinity` / `selectEndpointWithFailover` at `2005ea7d2` read the registry only; `handleNodeDeparture` retries only in-flight invocations, after `NodeRemoved`]
- `SliceInvoker.setAccessibilityFilter(AccessibilityFilter)` (default no-op on the interface, overridden by the production invoker) is wired in `AetherNode` to the same filter the forwarder uses. Every selection path now skips a registered endpoint whose node the filter rejects: plain selection becomes the excluding round-robin, an affinity target that is inaccessible yields to that filtered selection, and failover excludes inaccessible nodes together with the ones that already failed. Computed per call from the registry's current rows, so a node's return is seen on the next call. [verified: `SliceInvokerLivenessFilterTest` — four cases (request/response, fire-and-forget, affinity, failover) red without the filtering logic, green with it; removing only the affinity filter reddens exactly the affinity case, removing only the failover exclusion reddens exactly the failover case]
- **The exclusion is scoped to the candidate set each arm actually draws from — the weighted-routing pick spans every version of the base, so a version-scoped exclusion could not narrow it.** During an active deployment both the plain and the failover arm hand selection to `EndpointRegistry.selectEndpointWithRouting`, which builds its candidates from `findEndpointsForBase` — all versions — and splits them old/new. The exclusion was computed from `findEndpoints(slice, …)`, the invoked version only, so a co-confirmed-DEAD node hosting only the OTHER version was named by nothing, the "anything excluded?" fast path saw an empty set, and the weighted pick handed out the dead node. That is the ticket's hang, on exactly the path a rolling deployment exercises. `selectEndpointWithRouting` now takes the excluded set and drops those endpoints **before** the old/new split, and the invoker computes it over `findEndpointsForBase` for both routed arms. [mechanism: `SliceInvoker.inaccessibleNodesForBase` / `excludedNodesForBase` feed the new `EndpointRegistry.selectEndpointWithRouting(…, Set<NodeId> excludeNodes)`; the 5-arg overload remains as a default delegating with an empty set] [verified: `SliceInvokerRoutingLivenessFilterTest` — reverting both production files to the pre-fix head reddens 5 of its 7 cases; neutering only the registry's candidate filter reddens 6; handing only the plain arm an empty exclusion reddens 4 and handing only the failover arm a version-scoped one reddens exactly `weightedRouting_failoverFirstAttempt_neverSelectsDeadNodeHostingOnlyTheOtherVersion` — disjoint red sets, so the two call sites are pinned independently. No mutation reddens `SliceInvokerLivenessFilterTest`, so this hunk is independent of the single-version arms]
- **Excluding a dead node no longer costs the deployment its weighted split.** The old code bypassed the weighted pick entirely once anything was excluded, falling back to a round-robin over the invoked version — so a single dead node anywhere in the base silently served 100% of traffic from one version while the deployment believed a canary was running. Now the routed arms stay routed and simply carry the exclusion. [verified: `SliceInvokerRoutingLivenessFilterTest.weightedRouting_stillSplitsAcrossVersions_whenAnUnrelatedNodeIsDead` — both live versions are still selected with a third node dead]
- **All candidates filtered out is an absence of endpoints, not an instance failure.** On the retry path a first selection that comes back empty reached `handleAllEndpointsFailed`, which published an `AllInstancesFailed` event with an empty attempt list and no cause, and failed the call with the untyped `AllInstancesFailedError("0 nodes attempted")` — telling an operator the instances failed for a call that never left the node, with a non-transient cause for a situation a replacement node resolves. It now fails with the transient `SliceInvokerError.NoEndpointsError` and publishes no event. [verified: `SliceInvokerRoutingLivenessFilterTest.weightedRouting_everyHostInaccessible_retryReportsNoEndpointsAndPublishesNoFailureEvent` — neutering the guard reddens it] [verified: `SliceInvokerRoutingLivenessFilterTest.weightedRouting_everyHostInaccessible_failsWithoutSending` — the plain path fails with zero sends, no fallback onto the filtered-out node]
- `[known: the filter cannot beat detection latency]` — a silently dead node is still selectable until SWIM co-confirms it DEAD, exactly as on the HTTP forward path; what closes is the window between DEAD and the KV row cleanup, and the affinity/failover/routed arms that previously ignored liveness altogether. `[unverified: end-to-end on a multi-node kill — pinned at the invoker's transport boundary only]`
- The deliberate reading of "reachable": NOT co-confirmed DEAD. A DEPARTING drainer and a SUSPECT member are still selectable — they are up and serving in-flight work, and the caller carries its own timeout — so only terminal DEAD drops out of selection. [verified: `MembershipFsmTest.ReachableMembersForEndpointSelection` (`departingMember_isStillReachable`, `suspectMember_isStillReachable`, `deadMember_isNotReachable`), alongside the pre-existing `ReachableMembers.reachableMembers_includesObservedAndDeparting_excludesOnlyDead`; narrowing `reachableMembers` to the DHT-routable set (which excludes DEPARTING) reddens exactly the two DEPARTING cases]
- **The production wiring is now pinned by a tripwire, because nothing else could see it.** `SliceInvoker.setAccessibilityFilter` is a `default` no-op on the interface and the invoker's field defaults to `AccessibilityFilter.IDENTITY`, so a wired invoker and an unwired one are identical until a node actually dies — deleting the single call site in `AetherNode` leaves **all 1449 `aether/node` tests green**, and the invoker-level pins cannot see it either because they set the filter on their own fixture. `InvokerAccessibilityFilterWiringTest` asserts the call edge exists, using the same bytecode reachability scanner `AlertingWiringLivenessTest` uses for #957. [verified: deleting `sliceInvoker.setAccessibilityFilter(accessibilityFilter)` from `AetherNode` and recompiling `aether/node` reddens it; restoring returns it to green — green/red/green, not reasoning]
- `[unverified: what the wiring test cannot assert]` — the scanner sees call edges, not arguments, so nothing pins that the filter handed to the invoker is the SAME instance the HTTP forward path consults, nor that its body is correct. A node-level behavioural pin would need a boot test; that remains open, and the forwarder's own filter argument has the identical hole, which predates this change.
- Not changed (findings 2 and 3 of #275, both API/wire design): remote failures still collapse to `RemoteInvocationError(String)` — a typed cause across `InvokeResponse` is a wire-format change; timeout/retry are still not caller-configurable on `SliceInvokerFacade` — a public API change. Both left for a ruling. `[design intent — unverified]` The plain `invoke` path's "no endpoint" outcome is still the untyped `NO_ENDPOINT_FOUND` rather than `NoEndpointsError`; that belongs to finding 2's cause taxonomy.
