### Fixed (2026-09-06 — #886: a block written and never read was invisible to demotion)

- **A block written through the write-through path and never read back now stays a demotion candidate.** Before, `StorageInstance.trackNewBlock` finalized the block by an unconditional `createLifecycle` (a plain map `put`) that replaced the record the cache-tier promotions had just added their presence to, so the metadata named the durable tier alone while the bytes sat in the memory tier. `DefaultDemotionManager.selectCandidates` reads `listBlocksByTier(MEMORY)`, so it could not see the block however far over its high watermark the tier was; only a later read repaired the record, which is why every write-then-read test stayed green. `trackNewBlock` now updates the existing record in place
  [verified: `StorageInstanceWriteOnlyDemotionTest#writeOnly_blocksAreListedUnderMemoryTier` and `#writeOnly_demotionTickMovesBytesOutOfMemory` — six blocks written, none read, a real `DefaultDemotionManager` tick against the instance's own `MetadataStore`; with the production hunk reverted the listing is empty and the tick moves 0 bytes].
- **The mechanism differs from the ticket's, the consequence does not.** The record is not absent when `recordTierPresence` runs: `handlePut` claims the block first (`claimBlock`, a `putIfAbsent` of the initial lifecycle record), and `computeLifecycle`'s `computeIfPresent` applies the cache presence to that claim. What lost it was the overwrite one step later. The claim is therefore treated as THE lifecycle record: it names the tier the active write policy writes first, and finalization is an idempotent add on it, never a re-create. `computeLifecycle` itself is unchanged and still update-only, because `createRef`/`deleteRef` rely on an unknown block staying unknown
  [mechanism: `StorageInstance.sentinelFor`/`initialTier` and `trackNewBlock`; reordering the promotion after finalization was rejected because a cache-tier failure would then leave a real record that `releaseClaim` cannot remove, and a retry would deduplicate into a second refcount instead of rewriting].
- **A reference counted while the write was still in flight now survives finalization.** A second `put` of the same content during the first write's window deduplicates onto the claim (refcount 2, returned as success before the first writer's bytes land). The base re-create replaced that record and dropped the count back to 1, an under-count that would let GC collect a live block once either reference was dropped. Repaired by the same in-place update, not by separate code
  [verified: `StorageInstanceWriteOnlyDemotionTest#writeThrough_duplicatePutWhileWriteInFlight_refCountSurvivesFinalization` — the durable tier's `put` is held open until the duplicate has been counted; with the production hunk reverted the finalized record reads refcount 1].
- **Write-behind was never affected; its record keeps the same tier set and refcount, now pinned to exactly `{MEMORY}`.** Its claim already named the fast tier, so a write-only block was listed under `MEMORY`; the sentinel now names that same tier instead of the durable one, and finalization adds it idempotently. The durable tier is never declared present until a read finds the drained bytes there
  [verified: `StorageInstanceWriteOnlyDemotionTest#writeBehind_writeOnly_blockIsListedUnderFastTier` asserts `presentIn()` is exactly `{MEMORY}` for every block; a sentinel naming the durable tier finalizes as `{MEMORY, LOCAL_DISK}`, declaring disk residency for bytes still queued, and turns the test red].
- **What does change on every finalized record, both policies: `createdAt` and `lastAccessedAt` now carry the claim instant, not the finalization instant.** The record is the claim, so its timestamps are the claim's; the base re-create stamped both again when the write landed. The difference is one write latency, and it shifts `AGE`/`LRU` ordering by that latency and nothing else
  [mechanism: `BlockLifecycle.withTierAdded` copies every field of the record it updates; `sentinelFor` stamps both at claim time].
- **Residuals, stated plainly.** (1) `WriteBehindQueue` never records durable-tier presence when it drains, so a write-behind block's record never gains the durable tier until a read finds it there; pre-existing, not #886, not fixed here. (2) The read path's `recordTierPresence` is also update-only, so a block found in a tier with no local lifecycle record (a shared tier populated by another node, or after a metadata restore) records nothing; no cache fill happens on that path, so nothing becomes invisible to demotion. (3) A successful put still always leaves a record: if the claim vanished mid-write (`restoreLifecycles` clears the map) the fallback re-creates a durable-only record, and that one block is then back in the #886 state, its MEMORY presence unrecorded until a read finds it
  [mechanism: `trackNewBlock`'s `onEmpty` branch; no test drives a restore concurrent with a write].
  (4) On the write-through path a cache-tier `put` failure fails the whole put after the durable write already succeeded, because `flatMap` propagates it; the "skipped" log message on that path describes behavior that does not exist. With two tiers the claim is released and the bytes are orphaned on disk with no record. Pre-existing, not #886, filed separately. (5) A concurrent duplicate `put` returns success from deduplication while the first writer's tier write may still fail; the caller then holds an id whose bytes exist nowhere and whose record survives `releaseClaim` at refcount 2. Pre-existing, not #886. (6) `TierManagementIntegrationTest` still seeds a memory-only lifecycle record directly instead of writing through the instance (its comment names this defect as the reason); whether to convert it is a separate decision, since the instance path also leaves a disk copy and changes what the round trip exercises.
