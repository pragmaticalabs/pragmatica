### Changed (2026-11-18 — #3334: stream declaration model on `StreamConfig`; `StreamConfigValue` wire flag day)
- **Breaking, wire (pre-GA flag day):** `StreamConfig` gains an optional last component, `declaration` (the stream's `[retention]`, `[truncation]` and `[hot]` sections and `expected_ingress`), and the committed `StreamConfigValue` moves from wire tag 1647 to 2920. Tag 1647 stays pinned under a retired name that resolves to no class, so it is never reused. No decoder for the old tag is kept, so a node of this release refuses an older node's `StreamConfigValue` on an unknown tag (`UnknownTypeTagException` naming 1647), and an older node refuses this release's (naming 2920). [mechanism: `SystemTags` pins 2920 to `StreamConfigValue` and 1647 to `StreamConfigValueRetiredRc6`; the wire baseline `aether/node/src/test/resources/wire-assignment-baseline.txt` records the TAG line for 2920, and 1647 is pinned only in `SystemTags.java`; `StreamDeclarationWireTest` pins both directions]
- **Upgrade impact of the flag day (pre-GA: no migration path is provided).** Persisted consensus state, or a KV backup, written by an older release that holds ANY stream config is unreadable as a whole on this release, not only that one value: the snapshot map is decoded in one pass and the first old `StreamConfigValue` fails all of it. Every cluster holds such values, because the system stream is a stream. Consequences: a node of this release started on that persisted state stays in JOINING and never activates, and exits after 120 s (`EXIT_CONSENSUS_RESTORE_FAILED`), so under a supervisor it restarts in a loop [mechanism: `KVStore.restoreSilently` decodes the whole map (a decode probe of the old map on this release threw the unknown-tag error), then `OwnRestoreWatchdog` exits after 120 s; the exit itself was not run, so it is unverified]; a node that installs a snapshot from a peer holding an old value stays Syncing and retries [mechanism: `RabiaEngine` snapshot-install failure path; not run, unverified]; a restore of an older KV backup under `[backup] restore = "auto"` refuses the whole document and ends in `backup-restore-blocked` [mechanism: `BackupEntryCodec.decode` refuses the whole document; not run, unverified]. So a cluster of the previous release cannot be upgraded in place, and its backups cannot be restored with `restore = "auto"`. The exit is the same as for the rc4 to rc5 flag day: a new cluster on this build started with `[backup] restore = "fresh"` (the old state and streams are not carried over; see "Backups across releases" in the backup runbook). Nothing else was run or is claimed.
- **Known limit of the flag day: tag 710 is unchanged.** `StreamConfig` keeps its tag, so an OLD node decodes a bare new `StreamConfig` without error and ignores the trailing declaration byte (probe: decoded), while this release reading a bare old one throws an untyped `IndexOutOfBoundsException`. This is safe only while `StreamConfigValue` is the one carrier of a `StreamConfig` on the wire, which it is today; a mixed-version cluster is not supported, so it does not matter for an upgrade. [mechanism: a verifier probe decoded the bare new bytes on the old codec; no test in the repository pins it]
- Nothing parses or enforces the declaration yet: every `StreamConfig` built by this release carries `none` (each factory and `DEFAULT` pass `none`; the copy methods carry the receiver's value over), so stream behaviour is unchanged. The declaration's defaults (`max_age` 24 h, `max_bytes = max(1 GiB, P x 2 x seal_merge_bytes)`, `mode` any, the hot window from `RingGeometry`) are defined in `DeclarationDefaults`. [mechanism: unit-tested only, `StreamConfigTest.Declaration`, `StreamDeclarationWireTest` (node codec round trip), `DeclarationDefaultsTest`]
