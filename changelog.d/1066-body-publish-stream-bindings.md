### Fixed (2026-09-13 — #1066: stream slices deployed through the TOML body publish never bound)
- **`POST /api/v1/blueprints` — the route behind `aether blueprint apply` and Forge's deploy route — wrote no stream bindings.** `BlueprintService.publish(String)` stored the blueprint and its apply-start outcome but never `BlueprintStreamBindingsKey`; only `publishFromArtifact` (`/api/v1/blueprints/deploy`) did. Since #1040 made `BlueprintStreamAddresses` refuse an owning blueprint without bindings, a stream publisher or stream-access slice deployed this way failed to load (`… published no stream bindings`) and rolled the blueprint back, and a declarative consumer loaded but was never subscribed. Measured on one Heavy stream class: 9/9 green at `7ca6d671f^`, 66 binding errors and a rollback at `7ca6d671f`; eight Heavy stream classes errored the same way in CI.
- The body publish now derives the bindings from each slice jar's `META-INF/resources.toml` — where every `[streams.*]` declaration of a body-deployed blueprint lives, since the body TOML is a bare slice list — and puts them in the SAME consensus batch as the blueprint, as the artifact path does. That preserves the ordering `StreamAddressError` relies on: the FSM writes a slice target only after applying its blueprint, so no node sees a slice target without its bindings. [verified: `BlueprintPublishOwnershipTest.StreamBindings.publish_storesBindingsForStreamsDeclaredOnlyInsideSliceJars`, `publish_putsStreamBindingsInTheSameBatchAsTheBlueprint`, `publish_letsPublisherAndDeclarativeConsumerResolveTheirStreams`]
- **Both paths store identical bindings for the same blueprint, by construction.** They call one derivation (`BlueprintServiceInstance.streamBindings`), and the jbct plugin packages one module `resources.toml` as both the blueprint jar's and every slice jar's `META-INF/resources.toml`, so the distinct slice declarations are exactly the text the artifact path reads. [verified: `StreamBindings.publish_andPublishFromArtifact_storeIdenticalBindings_forTheSameBlueprint`]
- **No fallback was reintroduced.** An alias no slice declares still fails with `StreamAddressError.UnboundStreamAlias` once bindings exist. [verified: `StreamBindings.publish_leavesAnUndeclaredAliasFailingLoudly`]
- New refusals on the body publish, both before any command is applied: slices from different modules that bind one alias to different addresses (`conflicting-stream-declaration`) — `addressFor` would otherwise answer with the first and misbind the other slice silently — and a slice jar that cannot be read for its declarations, which would otherwise bind a subset. [verified: `StreamBindings.publish_isRefused_whenSlicesBindOneAliasToDifferentAddresses`, `publish_isRefused_whenASliceJarCannotBeReadForBindings`]
- **Heavy stream fixtures now address the ring by its engine key.** Once the body publish wrote bindings, seven of the nine Heavy stream classes reached lookups that had been unreachable since #1041: `replicaSnapshot`/`read` by the bare `[streams.X]` alias — for which HRW still names an "owner" whose replica set is empty forever, so placement never settled and four classes timed out — a WAL filter on a directory named `test-events` where the engine writes `<namespace>:test-events:1.0.0`, and a placement assertion premised on "one host owns at most one of five partitions", which HRW never promised (under the qualified key `dcp-5` owns two). The first correction, `0f27e5540`, qualified only the two declarative-consumer classes' constants — the ones whose `setUp` gate was the first to fail — and left the other seven at the bare alias; all nine now derive the key from their blueprint id through one helper (`TestArtifacts.streamEngineKey`), and the placement test asserts the forwarded count HRW actually yields for the observed host instead of the pigeonhole. Test-only; the production bare-alias fallback in `BlueprintStreamAddresses.engineKeyFor` is untouched. [verified: all nine `@Tag("Heavy")` stream classes green in-JVM, one class per fork; the `StreamCrashDurabilityTest` qualification reverted alone reproduces the CI red at its WAL assertion]
- Corrected three comments that placed Forge outside blueprint deployment (`BlueprintStreamAddresses.engineKeyFor`, `StreamAddressResolver`) or named only the artifact path in the same-batch argument (`StreamAddressError`). Forge's Ember nodes are real `AetherNode`s that register the resolver and deploy through the body publish, which is why this defect reached Forge.
- [unverified: role hints] Both paths derive with EMPTY role hints. `publishFromArtifact` aggregates hints from `META-INF/slice/*.manifest` inside the blueprint jar, and neither `GenerateBlueprintMojo` nor `PackageBlueprintMojo` puts manifests there (0 of the 50 `*-blueprint.jar` in a local repository carry one). So the spec §11.1.1 consumer default (`latest`) never applies at deploy; every unpinned alias binds at `1.0.0`. The body path matches that deliberately, because taking hints from slice manifests would make the two paths disagree on exactly those aliases. This is pre-existing and unchanged here; fixing it means changing both paths together.
- [unverified: resourcesConfig embedding] The body publish still does not embed the slice `resources.toml` into the stored `ExpandedBlueprint` the way `publishFromArtifact` does (`applyResourcesConfig`). Only the bindings key is brought to parity.
