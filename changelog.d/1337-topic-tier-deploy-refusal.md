### Fixed (2026-10-20 — #1337: a context subscriber on a topic an ephemeral publisher publishes is now refused at deploy)
- **A blueprint whose ephemeral publisher and context-taking subscriber share a topic is refused when it is published.** The subscriber's `(T event, MessageContext context)` handler needs a durable topic, and each jar reads the topic's durability from its OWN `resources.toml`, so the two jars compiled and loaded and the first delivery failed. `TopicTierPreflight` now runs with the other blueprint pre-flights, reads the publisher's durability from the same view the slice loader binds its sections from (an absent section is the ephemeral default, as at runtime) and matches publisher and subscriber on the declared topic, as the pub/sub validator does. The response (400) names the topic, the publishing slice and the subscribing method. [verified: aether/aether-deployment/src/test/java/org/pragmatica/aether/deployment/validation/TopicTierPreflightTest.java, aether/aether-deployment/src/test/java/org/pragmatica/aether/deployment/cluster/BlueprintPublishOwnershipTest.java, aether/forge/forge-tests/src/test/java/org/pragmatica/aether/forge/TopicTierMismatchForgeTest.java]
- **The topic-subscription row records the tier its handler requires.** `TopicSubscriptionValue` gained `tier` (`UNDECLARED`, `ANY`, `DURABLE`; a handler the slice processor marks `context=message` is `DURABLE`). It took a NEW wire tag, 2169 (its enum 2170), and tag 1655 keeps decoding the previous one-component shape as a row with an `UNDECLARED` tier, so a snapshot or persisted state written by an earlier build still restores. An ephemeral publisher reads the tier from the row and refuses a `DURABLE` subscriber before any RPC, as the same `TopicTierMismatch` with the same counter and operator warning; a row without a tier is still refused by the bridge. [verified: aether/node/src/test/java/org/pragmatica/aether/node/TopicSubscriptionValueWireCompatibilityTest.java — the old bytes are real output of the previous encoder]
- [limit: a subscriber deployed on its own, around a blueprint, after an ephemeral publisher is already running is not seen by the deploy check; it is caught per delivery at runtime. Slices deployed one by one never share a topic address (it is namespaced by the owning blueprint), so no supported route reaches it today]
